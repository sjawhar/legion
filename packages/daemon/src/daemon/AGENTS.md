# Daemon Module

The daemon is Legion's durable coordinator. It consumes webhook envelopes from core NATS and a durable per-repo JetStream consumer, persists `LegionState`, publishes derived role events through Envoy, and owns every Legion process's lifecycle through one `Runtime` (`runtime-tmux.ts` on a single host, `runtime-kubernetes.ts` as pods).

**Operational contract:** the daemon must run under a supervisor that restarts it on a non-zero exit — tmux alone is not one, and a durable-lane failure after a reducer has mutated live state exits the process deliberately (see `events.ts`'s `fatal` hook) expecting exactly that restart. Every GitHub App's bot git identity (`github-apps.ts`'s `TokenManager`) is resolved once with the App's own JWT — never an unauthenticated request — and cached per app id for the process lifetime (it never changes), so a crash-restart loop never burns through the shared IP's unauthenticated GitHub rate limit re-deriving it. Exactly one daemon may run per project at a time: `instance-lock.ts` enforces this with a kernel advisory lock — an exclusive, non-blocking `flock` reached through `bun:ffi` from the C library (`libc.so.6`; `libSystem.B.dylib` on macOS; any other platform is refused at acquire time naming the platform), held on an open, close-on-exec descriptor of `<state_dir>/daemon.lock` for the daemon's lifetime — so every daemon for a project must share the same `state_dir`. The kernel drops the lock when the process dies, so a crashed daemon leaves nothing to reclaim and no spawned process (the private tmux server included) can hold it past the daemon's death; the daemon never renames, links, or unlinks that file (a fresh inode under the same name would be an unlocked file), `release()` only closes the descriptor and is idempotent, and the pid written into the file is informational — it names the holder in the `Legion daemon already running for this project (pid N, lock file X)` refusal, re-read for a bounded moment (20 × 25 ms) when a contender loses to a holder that has not written it yet, after which the refusal says the holder's pid is not recorded yet.

## HTTP API

The localhost-only Legion API lives in `api.ts`.

See `api/state.ts`. |
| `POST /legion/v1/process/started` | Register a root process with transcript-derived architect role backing. |
| `POST /legion/v1/process/exit` | Authenticated architect exit that releases an admission slot or marks its root process dead. |
| `POST /legion/v1/issues/status`, `/waves/release`, `/gates/register` | Scoped architect writes (any status in its tree; `release_wave` PATCHes `todo` for every key in `issues`; `gates/register` records the root spec document's id (lowercased — Dispatch emits its UUIDs lowercase and the reducers match with `===`) and version from `dispatch_request_approval`'s result as the design gate (`{artifactId, version}`; a body naming the retired `askId` field, or missing either field, is a 400 that names the field). A gate that would be closed after the write is opened without an event in two cases, each publishing `{type:"design-approved"}` through `routeActive` (the issue's active phase worker, else the tree's architect), best-effort, since the state already carries the approval for catch-up: when `config.gates.design` is `off`, the daemon approves the gate at that version itself (boot approves every registered-but-closed gate of an active tree the same way, so turning the gate off unblocks trees parked under it); otherwise it reads the issue from Dispatch once (`getIssue`, `seedGateFromDispatch`) and seeds the gate from the registered document's `approval` — `approved` at the latest version opens it, `stale` records the older approved version and leaves it closed, any other state records no approval, and Dispatch's `latest_version` raises `latestVersion` in every case — because a human approval that landed before registration (from the document header, or from the Inbox between `dispatch_request_approval` and `register_gate`) was ignored by the reducer for a document no gate named yet and is never re-emitted. A failed read is a 502 recording nothing, so `register_gate` retries; a document the issue does not carry is a 404 naming both) — and the controller capability may additionally set `todo`\|`backlog`\|`icebox` on any project issue via `/issues/status`. |
| `POST /legion/v1/worker-session`, `/grants`, `/git-credential`, `/gh-token` | Durable architect and worker capability recovery, and credential grants. |
| `POST /legion/v1/worker/started` | Registers a headless phase worker's session against its daemon-minted boot token; mints its session capability, git identity lease, and records its tmux/socket locator and a hash of its boot token on the claim (so `/worker-session` can rebind it after a daemon restart). Never writes the issue's active phase (`state.phases[issue]`); a registration for a role that is not the active phase and has no queued assignment logs one line and changes nothing else. A registration is accepted when `sessionId` is unset at its generation, including after a restart before its first registration, or from the recorded session, which reissues a secret. A different session at the same generation is refused 403 `Invalid worker boot token` on the in-memory and persisted-hash paths, logs `foreignRegistrationLine` with both sessions and ready status, and writes nothing. It never probes liveness: a dead worker gets a new generation and boot token. (LEGION-95.) |
| `POST /legion/v1/worker/ready` | Verifies the worker's session capability and sends its queued prompt (`pendingAssignment`, `{ kind: "assignment" \| "catchup", task }`, cleared once the worker's turn is observed to start — never on the shim's acknowledgement alone; state v25 -> v26 — `migrateV25State` in `legion-state.ts`, after LEGION-33's pure v24 -> v25 bump — classifies each bare string a pre-upgrade daemon persisted there by its payload: JSON whose `type` is `catchup-worker` is a `catchup`, anything else an `assignment`) as an OMP RPC `prompt` frame over the worker's `legion worker-shim` socket. Delivering an `assignment` makes the role the issue's active phase; a `catchup` does not — and a `catchup` queued for a phase-worker role that is no longer the active phase by the time ready arrives (`isBystanderCatchup`) is dropped instead of prompted — and the relaunched pane is retired on the spot exactly as `retireIdleWorker` retires a finished worker (graceful `shutdown` frame with kill-pane fallback, locator cleared, `ompSessionFile` carried into `resumeSessionFile`, ready confirmed and `launchFailures` reset because the boot did succeed, persisted), since a fresh pane that is never prompted emits no `agent_end` and would otherwise sit at `runState: unknown`, counted against `worker_cap` and never idle-retired; one `dropping queued catch-up … at ready and retiring the relaunched pane` line is logged, and the role's next `spawn_worker` resumes the same agent with `--resume`. A prompt the worker acknowledges but starts no turn on within `worker_rpc_timeout_seconds` with its socket still up (`PromptNotStarted`, `reason: "no-turn"`) still confirms the boot — it did succeed: registered, ready, socket answering — but leaves the task on the claim, places the role on the promotion queue (`queueUnstartedPrompt`), counts against `promptFailures`, and logs one `<token>: worker <token> acknowledged the prompt but started no turn within <N>ms (…); boot confirmed, task queued for promotion` line — and, when that failure is the third on a pane whose claim already took one prompt-failure retirement, the terminal one: `worker-died` to the architect instead of `worker-queued` (the delivery bullet below); the confirming `get_state` seeds the fresh client idle, so the next drain retries it. A prompt whose shim socket closes before any turn starts (`reason: "socket-closed"`) is a worker that died right after acknowledging, not one that swallowed the prompt: the route confirms, cancels, and queues nothing (one `…; boot left unconfirmed for the socket-close handler to retire` line), leaving the claim an unconfirmed boot with its `pendingAssignment`, and the socket-close handler (`onWorkerClientClosed` → `retireUnconfirmedBoot`, queued behind the same role lock) alone retires it — locator cleared and its `worker_cap` slot released, `launchFailures` counted, the task re-queued and relaunched cold with `--resume` (`worker-started`), or `worker-died` at the threshold. Confirming it instead would send that handler to `retireUnconfirmedBoot`'s confirmed-claim early return and strand a dead locator holding a slot with the task on it. |
| `POST /legion/v1/worker/spawn` | Architect-only: spawns a phase worker for `{issue, role, task}` — resumes an already-live worker over its socket (`resumed`: the worker's turn was observed to start; an acknowledgement no turn follows within `worker_rpc_timeout_seconds` answers `queued` instead, the task queued for promotion and counted against `promptFailures` — the HTTP answer is still `queued` when that count crosses the retire threshold; whether the retirement relaunches or ends in `worker-died` is the delivery bullet's rule), respawns a dead one with `--resume` (`spawned`), opens a fresh pane (`spawned`), or — at the configured running-worker cap — enqueues the task for promotion once a slot frees (`queued`), in priority order — see `workerPriority` in `worker-admission.ts`. Once the process manager has accepted the spawn and before the result is returned (whichever of the three it was), it PATCHes the issue's Dispatch status via `spawnStatus` (`workers.ts`) in exactly two cases, reading the status as the daemon knows it — `knownIssueStatus`: a pending write of its own in `state.pendingStatusWrites` while the echoed `state.issues[issue].status` still equals the write's `statusAtRecord`, else the echoed status; resync's own supersession fence (`retryPendingWrite`), so a human's move echoed after a failed write is never outranked by it. First, an `implementer` spawn while `state.prs` holds an entry for the issue with `reviewDecision === "changes_requested"` and the known status is not already `in_progress` → `in_progress` (a corrective round, whether a Legion reviewer or a human requested the changes) — and, second, a `role: architect` spawn (a child's sub-architect; the root's own architect is refused 400 by this route) while the known status is `todo` → `in_progress`. A child is never admitted as a tree of its own: its `todo` transition emits no `admit` while an ancestor holds a tree that is not `lingering`/`closed` (`reduceIssueUpdated` → `liveAncestorTree`, `legion-state.ts`), so the first sub-architect spawn is the child's admission and writes the `in_progress` that `spawnTree` writes for a root on its first admission only (`resume: false`) — a resurrection of a dead root (`resume: true`, the one path through `resurrectDeadTree`) relaunches the same recorded session and writes no status at all, so the issue keeps whatever the lifecycle left it at (`testing`, `needs_review`, `retro`, or a human's `todo`). No spawn starts a root; every other spawn writes nothing: the `.legion/` deletion push and retro leave the status where the review put it, and a phase-worker spawn on an active issue a human moved back to `todo` never overrides it (a sub-architect spawn for such a child writes `in_progress` again — for a child, that spawn is its admission). A refused spawn (403/409/400) writes nothing. |
| `POST /legion/v1/phase/complete` | Authenticates via a short-lived grant (`{grantId, summary}`, resolved read-only — the same grant mechanism `/git-credential` and `/gh-token` use, never a live session secret) rather than a session capability. Verifies the claim for the grant's (issue, role) still belongs to the grant's session (409 `Grant does not match the worker currently holding this role` otherwise) and that the issue's active phase still matches (409 `Phase for <issue> is no longer owned by this worker` otherwise), then captures and clears the phase synchronously — before the publish `await`, so a second concurrent completion for the same phase always 409s on that check instead of both publishing — and publishes `{type:"phase-complete", issue, role, summary}` to the tree's architect role. Before publishing, it also PATCHes the issue's Dispatch status via `phaseCompleteStatus` (`workers.ts`): implementer → `testing` only when the issue's status as the daemon knows it (`knownIssueStatus`, defined in the `/worker/spawn` row above, so a Dispatch outage between the `in_progress` write at admission (`spawnTree` on a root's first admission — never on its resurrection, which writes nothing — the first sub-architect spawn for a child) and this completion does not swallow the `testing` write, while a human's later move does) is `in_progress` — the same role's later completions (the `.legion/` deletion push, a conflict-forced rebase, retro) leave the status untouched, so `retro` is never followed by `testing`; tester → `needs_review`; and reviewer → `retro` unless `state.prs` holds an entry for the issue with `reviewDecision === "changes_requested"`, in which case it returns to `in_progress` for a corrective implementer instead. A non-404 publish failure restores the captured phase and returns 502 (idempotent retry). A 404 no-holder never drops the completion: the phase is recorded as `phases[issue].completed = {summary, at}` instead of cleared, and the response is 202 — `overseerCatchup` replays it to a reconnecting architect, and `routeActive` treats a completed phase as no active phase (routes to the architect) until a fresh assignment overwrites the record. A save failure restores the captured phase and returns 500 (retry redoes the whole attempt). |
| `POST /legion/v1/controller/ready` | Controller lifecycle. |

## Operational invariants

- Role lanes use core NATS; the daemon holds no events. A role-lane delivery exception or a durable lane's 404 no-holder probes the worker's own locator and, if dead, resumes the same agent through it (`--resume`, never fresh) and sends it a state-derived catch-up instead of replaying the missed event; the controller is a role holder like any other, so a controller exception (`no_holder` or `delivery_failed`) calls `ensureController` the same way. `/controller/ready` (`onControllerReady`) always drains every queued `ControllerPendingNotice` first, then runs a **forced** resync (`runResync({ force: true })`) that bypasses the `resyncIntervalMs` throttle (while still recording `now` as the new `lastRunAt`) — a freshly respawned controller must never trust the interval to have already elapsed, since the respawn itself may be the fallout of the *previous* controller crashing on an anomaly the interval would otherwise still be suppressing. A reducer-derived `kind: "controller"` effect that 404s is recorded as a `ControllerPendingNotice` exactly like a Slack mention, except a `triage` payload — the one payload the forced resync's `reportRootAnomalies` always regenerates for an untriaged root, so recording it too would double-deliver it. Every notice the daemon itself sends to a role topic — `phase-complete`, the overseer and worker catch-ups, `resync`, and `ProcessManager`'s `worker-queued`/`worker-started`/`worker-died`/`launch-failed`/`revive-failed` and redelivered exception payloads (`ProcessManagerDeps.publishRole`) — goes through the listener's `POST /v1/messages/publish` (`envoyPublish`), which wraps it in an envelope and routes it to the live holder. Never a bare `nats.publish` of the JSON on the role subject: the listener validates every role-lane message as an envelope and drops a bare payload with `listener invalid envelope: event_id is required`, so such a notice reaches nobody (which is how, before LEGION-60, an architect told `worker-queued` never received the `worker-started` it was told to wait for).
- Root processes and the controller are tmux windows under global admission control. The daemon stores tmux window IDs; names are cosmetic, escaped issue labels.
- Process failure recovery is exception-driven. A root is trusted only when its recorded pane is live, running OMP, and still the process its locator recorded — the pane's root pid plus that process's `/proc/<pid>/stat` start ticks, captured by `TmuxRuntime.spawn` and re-checked by its one chokepoint, `verifyPaneProcess`, before any probe, any daemon-issued `kill-pane`, and any window reuse; a pane whose process is not the recorded one (a pane id reissued by a recreated tmux server, or a locator persisted before identity tracking) probes `dead` with `reason: "not-recorded-process"` and both identities in `detail`, which `ProcessManager` logs once at the decision point; a dead root is resurrected under a generation lock. The periodic resync (`runResync`, `resync.ts`) is the designated backstop for a root that dies with nothing routed to it: every run emits a `{kind: "probe", tree}` effect (`onProbe`) for each active, ready-confirmed, located tree, independent of whatever anomalies the same run reports — so a root whose recovery would otherwise depend on some unrelated event happening to touch its tree is still probed and, if dead, resurrected within one resync interval. A probe the runtime could not complete is neither verdict: a `list-panes` that fails for a reason that does not prove the pane gone (`tmux.lookupPane`'s `failed`, e.g. a client killed by the runner's timeout, `server not responding`) makes `TmuxRuntime.probe` throw rather than answer alive or gone, and every probe caller logs and retries later without clearing anything — the resync `onProbe` on its next tick, the boot watchdog by re-arming its interval, the controller and root registration deadlines by re-arming themselves (including when it is the resurrection's own re-probe that throws, after the deadline's probe already found the root dead — the resurrection's stop cannot throw out, `removeTreeProcess` logs a stop failure and clears the locator in `finally`: `escalateOrRetryUnconfirmedRoot` catches the retry, logs once, and re-arms the same generation's deadline while the tree is still active and unconfirmed, since the resync backstop probes only confirmed roots; a `spawnRoot` throw inside the same retry has already queued or launch-failed the tree, so the re-arm is declined and the log says so), the linger sweep on its next pass; `handleException` only logs, naming the role token — the core-NATS exception lane has no redelivery, so that log is the whole record and the retry is whichever of the others reaches the root next.
- A freshly-spawned root's confirmation is watched by a bounded per-tree registration deadline, exactly like the controller's own (`armControllerRegistrationDeadline`/`ensureController`): `workerBootTimeoutSeconds * workerBootRegistrationDeadlineIntervals` after `spawnTree` records a fresh locator, so a root whose OMP dies or hangs before ever registering (a bad `omp_launch_prefix`, a provider outage) is not left invisible until some unrelated routed event happens to probe it. `/process/ready` carries the root's own generation and is rejected 409 on a mismatch against the tree's current one (exactly like `/process/started`), and — not `/process/started` — is what cancels the deadline and sets `TreeState.readyConfirmedAt` (`confirmRootReady`, persisted before the route responds): the overseer catch-up wake `onTreeReady` emits only at ready, so a root that registers but never reaches `ready` is still unconfirmed. Unlike the controller's single in-flight wait, this is tracked per tree and bound to the exact generation armed for: a stale timer from a superseded spawn, a confirmed ready, or a disposed daemon is recognized by re-checking the wait's generation, `readyConfirmedAt`, and a `disposed` flag after every await, never trusted once at entry. On expiry, a still-unconfirmed tree on the same generation is re-probed fresh — a dead pane and a still-alive-but-never-confirmed one (retired first, mirroring `spawnTree`'s own stale-generation retire path) both count toward `launchFailures` through the same shared accounting, escalating to `launch-failed` (revoking the architect capability, releasing the admission slot, publishing the controller escalation) at `MAX_LAUNCH_FAILURES` instead of resurrecting forever, since `spawnRoot`'s own success path no longer resets `launchFailures` on a mere pane-open — only a confirmed `/process/ready` does. A stop failure re-arms the same generation's deadline rather than stranding it with nothing left to retry. Canceled on `closeTree`, `beginLinger`, and daemon `dispose()`, exactly like the controller's own wait; `readyConfirmedAt` is itself persisted (`migrateV20State` backfills it for every already-active, already-launched tree on upgrade so a live upgrade never retires a healthy root) precisely so a boot-time `reconnectRoots` pass can re-arm the deadline for any active tree with a locator that never confirmed before the restart — the in-memory wait map itself does not survive one. The controller's own deadline (`retireAndRespawnStuckController`) retires a still-alive, never-registered controller and respawns it through `ensureController`; when that controller's window was the private session's only one, its pane closing tears session and server down, and the graceful stop confirms before tmux has finished doing so — the respawn survives the session dying under it that way, because `tmux.openWindow` re-asks `has-session` after a failed `new-window` and recreates the session on one second attempt (the `tmux.ts` row above, LEGION-89); a respawn that fails for any other reason is logged once as `[legion] failed to retire and respawn a stuck controller:` with the thrown error, whose message always ends in tmux's stderr or `tmux printed nothing on stderr`.
- A lingering or closed root releases its admission slot, gracefully stops every process recorded for the tree (its own and every worker's — a `{type:"shutdown"}` frame over each one's `legion worker-shim` socket, its pane killed directly only if it fails to close within the configured timeout, or immediately if its shim is unreachable or already confirmed gone — and never at all when the pane no longer runs the process the locator recorded: the graceful shutdown is skipped only for a `gone` verdict, so a still-live legacy root is still asked to exit over its own role-scoped socket, while the runtime refuses the kill (`refuseKill`) and the locator clears as if the pane were already gone; a locator without a pane id is the same identity-less case, never a throw — and never at all when the pane could not be verified either way: a `list-panes` that fails for a reason that does not prove the pane gone (`tmux.lookupPane`'s `failed`, e.g. a client killed by the runner's timeout) makes `TmuxRuntime.stop` throw `ProcessStopFailed` exactly like a failed `kill-pane`, so the tree stays `lingering` for the sweep to retry with its locator untouched — the probe side of the same verdict is in the process-failure-recovery bullet above), clears its locator, and removes its role claims. The linger sweep also removes session windows not recorded by a tree or controller.
- `DaemonConfig` supplies all lifecycle defaults: admission cap, worker cap, recursion depth, linger duration, resync interval, retry limit, the two stop timeouts (`workerStopTimeoutSeconds`, default 10; `treeStopTimeoutSeconds`, default 60), worker boot timeout (`worker_boot_timeout_seconds`/`LEGION_WORKER_BOOT_TIMEOUT_SECONDS`, default 120), worker RPC timeout (`worker_rpc_timeout_seconds`/`LEGION_WORKER_RPC_TIMEOUT_SECONDS`, default 5), the idle-retire window (`worker_idle_retire_seconds`/`LEGION_WORKER_IDLE_RETIRE_SECONDS`, default 600; the literal `0` disables the timer; at most `MAX_TIMER_SECONDS`, below; a blank, `-0`, padded, or otherwise non-canonical value is a startup error naming the key), and the slow-command budget (`slow_command_timeout_seconds`/`LEGION_SLOW_COMMAND_TIMEOUT_SECONDS`, default 300): the per-attempt runner timeout for both boot probes and for every workspace-provisioning command (`jj git clone`/`fetch`, `jj workspace add`, the git config writes) — anything that waits on OMP start-up, the network, or a credential helper. The command runner's generic 30 s stays for GitHub API reads — plus the runtime selection: `runtime` (`tmux`|`kubernetes`, default tmux; `kubernetes` requires the `runtime.kubernetes` block and selects `KubernetesRuntime`), `daemon_url` (default `http://127.0.0.1:<port>` under tmux, where any other value is refused as an inherited outer pane's `LEGION_DAEMON_URL`; required under kubernetes; what every spawned process receives as `LEGION_DAEMON_URL`), and `bind` (`127.0.0.1` unless `runtime: kubernetes`). Every duration setting — `worker_stop_timeout_seconds`, `tree_stop_timeout_seconds`, `worker_boot_timeout_seconds`, `worker_rpc_timeout_seconds`, `resync_interval_seconds`, `worker_idle_retire_seconds`, `slow_command_timeout_seconds`, and `linger_hours` — is bounded by one constant, `MAX_TIMER_SECONDS = 2147483` (`config.ts`; `MAX_TIMER_HOURS = 596` for `linger_hours`): the largest whole number of seconds whose millisecond delay fits the signed 32-bit delay `setTimeout` accepts, beyond which Bun clamps the delay to 1 ms and the timer fires at once. A larger value from the file or its `LEGION_*` variable is a startup error, `<key> must be at most <bound>` (`legion start --check-config` reports the same), never a clamp. The root/controller registration deadline is the product `worker_boot_timeout_seconds × worker_boot_registration_deadline_intervals` in one timer, so that product is bounded the same way (`worker_boot_timeout_seconds * worker_boot_registration_deadline_intervals must be at most 2147483`). `linger_hours` is a deadline timestamp swept by the linger interval, not a timer delay; it carries the same bound so every duration key obeys one rule. A command the runner killed at its budget comes back with `timedOut: {limitMs, elapsedMs}` (exit 143) so no caller reports a kill as `Command failed (exit N)` with empty detail; one it killed because the caller's `signal` aborted comes back with `aborted: true` instead — the caller gave the command up, and nothing about the command is being reported. At most one of the two is present, the first kill to land deciding which.
- Boot never resurrects trees; it only reconciles admission so slots opened by a raised cap promote queued issues in order — after dropping every queue entry whose issue is `done`, `backlog`, `icebox`, or `triage`, or has no issue record, logged `[legion] dropped <KEY> from the admission queue at boot: Dispatch status "<status>"` / `... at boot: unknown issue`, so a stale head of the queue is never promoted.
- A waiting issue leaves the line with its status. `isStaleQueuedStatus` (`legion-state.ts`) is the one rule -- true for `triage`, `icebox`, `backlog`, `done`; false for `todo` and every daemon-owned status; exhaustive over `IssueStatus` -- and three paths apply it: `reduceIssueUpdated`/`reduceIssueClosed` emit `{kind: "dequeue", issue}` when such a status lands on an issue that holds an `admission.queue` entry or a `queued` tree record (root or child; an active tree still lingers instead), dispatched by the durable lane to `ProcessManager.dequeue` before the save so queue and status persist together; `reconcileAdmission` sweeps the queue at boot before demote/promote; `runResync` sweeps it after `healStatusDrift` through the same effect, logging `dropped <KEY> from the admission queue at resync: <reason>`. `dequeue` splices the queue entry, deletes the tree record only when it is `queued` (active, lingering, dead, launch-failed, and closed records belong to the linger, close, and launch-failure paths), persists, and is a silent no-op when the issue holds neither. A daemon-owned status on a queued entry is never stale: it is the shape boot's demote loop produces. A later `todo` admits the issue again exactly like a never-seen root. The controller's queue view is `GET /legion/v1/state`, so it is clean once the state is; no state version bump.
- Children never take admission slots. A `todo` transition emits `admit` only for a parentless issue, or for a child whose nearest ancestor with a tree holds a `lingering`/`closed` one, or has none (an orphan, admitted as a root with a `log` effect naming the parent — nearest wins, so a grandchild under a lingering legacy child tree is an orphan even under an active root, exactly as `rootForIssue` would refuse the root's `spawn_worker` for it). A child whose nearest ancestor tree is live (`queued`/`active`/`dead`/`launch-failed`) is owned by that tree's architect, which runs it as a sub-architect phase worker (`spawn_worker` with `role: architect`: counted against `worker_cap`, `LEGION_TREE` the root, `LEGION_ISSUE` the child, prompt `roles/architect.md`); the parent's own `child.status` event is the architect's wake. The one ownership predicate is `liveAncestorTree` (`legion-state.ts`), shared by `reduceIssueUpdated` and the boot repair below so the two cannot disagree. `issue.closed` lingers the issue's own active tree whether or not it has a parent, so a child tree a pre-LEGION-57 daemon created releases its slot when the child closes. Boot repair (`ProcessManager.adoptOwnerlessChildTrees`, called before `enableLaunches()`, idempotent): every child tree that holds no process — `queued`, `launch-failed`, or `active` with no recorded locator — whose issue has a live ancestor tree is removed from `trees`, `admission.queue`, and `admission.active`, together with the child's stale root-architect `roles` entry (revoked through `revokeRoleClaim` — left in place, its `sessionId` would become the parent's first sub-architect spawn's `expectedSessionId` and 409 that spawn at `/worker/started`), its Dispatch status untouched, one log line each (a second line names any worker claims with recorded panes an earlier confirmed generation of that root left behind: they keep `LEGION_TREE=<child>`, so their tree-scoped credential routes 404 until retired) (`removed the <status> root tree for <child> at boot … (LEGION-57)`); it runs before `reconcileAdmission` so no promotion consumes a queued child and no active-no-locator child is demoted, requeued, and relaunched as a root in the same boot, and because a `launch-failed` child left in place would refuse the parent's `spawn_worker` forever now that the controller's `todo` no longer re-admits it. After `replayHeldRecoveries()` the daemon publishes the reducer's own `child-adopted` payload (`childAdopted`, `reducers.ts`) to each such parent's architect through the same best-effort path as the boot gate-off wake (`publishWakeEffects`, `api/routes/issues.ts`; a 404 no-holder is silent: the resync probe resurrects a dead root and its architect reconciles released children from state). A `dead` child tree, or an `active` one with a locator, is left alone until its issue closes.
- Boot ordering in `startDaemonLocked`: environment and runner, the Dispatch token file, the plugin contract check (`verifyLegionPluginContract`, awaited — a local manifest read, never load-sensitive), then both OMP probes *start* (not awaited); `tokenManager.getToken` for the implement App and then the review App (both required — a missing one refuses startup here), state load, gate-off handling, NATS, `ProcessManager`, the event pump, the API, the worker-stream listener, `reconnectWorkers`, `pruneSecretFiles`, the pending-controller-notice drain/spawn (its `ensureController` is held by the launch hold and replayed after it); then the **launch hold** — `await probes` — and only after it passes `adoptOwnerlessChildTrees()` (still under the hold) → `enableLaunches()` → `reconnectRoots()` → `reconcileAdmission()` → `reconcileWorkerAdmission()` → `replayHeldRecoveries()` → the `child-adopted` publishes for every adoption, the timers, and the signal handlers. `reconnectWorkers` runs after the API so a dead confirmed worker's capability revoke has an `api` to go through (the invariant is the `api`-before-`ProcessManager` bullet below). `startDaemon` resolves only after the hold releases and boot admission has settled; consequently `legion start` writes its legions-registry entry — and `legion status <team>`/`legion stop <team>` first see the daemon — only once the probe has passed, while the API port (known from config) answers throughout and the supervisor owns the process. A definitive probe failure at the hold runs `stop()` (which closes everything already opened and releases the instance lock) and rejects.
- The launch hold (`ProcessManager.launchesEnabled`, false until `enableLaunches()`): while it is on, every path that would open a tmux pane instead queues or is held and answers `queued` — a root `admit()` and `advancePromotionSweep()` treat the cap as full (the tree goes on `admission.queue`), `WorkerAdmission.launchOrQueue`/`resumeOrQueueExisting` enqueue (so `spawnWorker` and `resumeWorker`, the exception/404 recovery, return `{status: "queued"}` and publish `worker-queued`), `resurrect()` records the tree in `heldResurrects` and logs `[legion] resurrection of <tree> held until the OMP probe passes`, and `ensureController()` sets `heldControllerRequest` and logs `[legion] controller launch held until the OMP probe passes`. The probe passing runs the same promotion drains the worker cap uses plus `replayHeldRecoveries()` for the held resurrections and controller launch. A live idle worker's resume (`resumeOrQueueExisting`) is held the same way: its new task queues and is prompted once the probe passes, since prompting a pane is also a launch decision. Paths that only stop or kill panes (`closeTree`, `beginLinger`, `stopProcess`) or that merely connect to a pane that survived the restart (`workerReady`, `controlDirective`, `markTreeReady`) are not gated — the hold is about starting work in panes, not about observing them. The API answers throughout.
- Per-claim reconnect isolation: `reconnectWorkers` reconciles every located claim in isolation — a throw while handling one (a capability revoke failing, a tmux call rejecting) is logged as `[legion] failed to reconcile worker <token>:` with the error, that claim is left exactly where the throw found it (its locator still recorded, so it still counts as running and a later probe can retry it), and every other claim's reconcile still runs and is awaited before boot continues. `reconnectRoots` arms each tree's registration deadline the same way, logging `[legion] failed to reconcile root <tree>:`. `index.ts` keeps its outer `worker reconnection failed` catch only as a last resort.
- Workspace clone (`packages/workspace`, `ensureRepoClone`): a missing repository is cloned into a temporary sibling `<repo>.clone-XXXXXX` in the same parent and renamed into place only after `jj git clone` exits 0 and `.jj` exists; on any failure the temporary directory is removed, so a clone the runner killed, or a daemon crash interrupted, never sits at the final path looking finished. An existing final directory without `.jj` (left by an older daemon) is removed and re-cloned, logged as `[legion] removing incomplete clone at <dir> (no .jj) before cloning again`. Every provisioning command carries the slow budget, and one the runner killed fails as `Command timed out after <limit> s (ran <wall> s): <cmd>` at its budget or `Command aborted: <cmd>` on the caller's `signal` — never as `Command failed (exit 143)`; `RunResult` mirrors the runner's `timedOut`/`aborted` markers, though no provisioning caller passes a `signal` today. The root's launch failure is counted as before. Leftover `.clone-*` siblings are inert and deliberately not swept (a sweep would race a concurrent in-flight clone). The issue bookmark `legion/<KEY>` is touched only by `createWorkspace`, and provisioning never runs a `jj bookmark` command on a workspace that already exists: it neither moves nor re-creates the bookmark, so a bookmark the fetch deleted because its merged pull request's branch is gone stays deleted (LEGION-28: re-creating it put the issue's branch on unrelated commits), and a bookmark a worker left elsewhere stays there; the implementer's push step (`jj bookmark set` + `jj git push --bookmark`) owns every later move. Before every fetch — after `ensureRepoClone`, on every provisioning, since the production clone predates the rule — provisioning reads the clone's per-repo setting with `jj config get git.abandon-unreachable-commits -R <clone>` (`runChecked`; the read records no operation and snapshots nothing, verified on 0.44.0 and 0.45.1) and, only when the trimmed output is not `false`, writes it with `jj config set --repo git.abandon-unreachable-commits false -R <clone>`, so the write lands once per clone and the steady state never writes: jj rewrites that file in place, not atomically, and every jj command on the box parses it at start-up (a read that caught the file holding only `[user]` has been seen live). A failed read or write stops provisioning before the fetch, the one destructive step, and is counted as a launch failure like any other provisioning failure. jj keeps that per-repo setting not inside the clone but at `$XDG_CONFIG_HOME/jj/repos/<config-id>/config.toml` (`~/.config/jj/repos/…` under the daemon user's config directory; the id is `<clone>/.jj/repo/config-id`; `jj config path --repo -R <clone>` names it), merged into whatever else the file holds (nothing else, once a repository-scoped `user.*` has been removed — identity rides each pane's `JJ_USER`/`JJ_EMAIL`), read by every workspace of the clone (their `.jj/repo` points at the clone's) and by a pane's own `jj git fetch`, because panes run as the daemon's user with its `HOME`/`XDG_CONFIG_HOME` (both on the pane allow-list) — a process under another home sees jj's default, `true`. The post-merge contract (LEGION-84): after an issue's pull request merges and GitHub deletes `legion/<KEY>`, the next provisioning's fetch deletes the matching local bookmark (`bookmark: legion/<KEY>@origin [deleted] untracked`) and nothing else — no `Abandoned N commits`, no rebase of a live working copy (`jj op log --op-diff` for that fetch shows only the two bookmark sections) — so a worker resumed on a merged issue finds its workspace exactly as it left it: not stale, every file on disk, its pushed commits still beneath `@`, the bookmark gone, and `main@origin` carrying the squash commit of the same change; work that needs a new pull request starts from `jj new main@origin`. A finished issue's branch commits stay visible in every workspace's `jj log` until its workspace is removed (LEGION-104). `createWorkspace` first resolves the bookmark, before any other command — `jj log -r 'bookmarks(exact:legion/<KEY>)' --no-graph -T 'commit_id ++ "\n"' --ignore-working-copy -R <clone>`, one commit id per line, none / one / several on jj 0.44 and 0.45 alike for a missing, a normal, and a conflicted bookmark (a deleted local bookmark whose remote row survives lists none) — and a failed command or more than one commit throws, naming the bookmark, before anything is pruned, added, or registered: a `--revision legion/<KEY>` add for a name jj cannot resolve still registers the workspace, parented on the root commit, before reporting the error, and the next resume would adopt that empty workspace silently; the failure repeats on every resume until a human resolves the bookmark. Exactly one commit is the add revision (`jj workspace add … --revision <commit id>`, the id not the name) and no bookmark command runs; none means `main`. A brand-new workspace and one jj still registers but whose directory is gone start from that same resolution: prune, add, and on `already registered|exists` a flag-free `jj workspace forget <name> -R <clone>` (jj has no `--cleanup`/`--force`; the `git worktree prune` after it cleans the colocated worktree), prune, add again at the same revision. Only when nothing resolved does the add end with `jj bookmark set legion/<KEY> -r @` on the fresh working copy, and only when the registration had to be forgotten is one line logged (`[legion] bookmark legion/<KEY> is gone (…); re-added the forgotten workspace <dir> at main, creating the bookmark on its fresh working copy`) — a brand-new issue has no bookmark to miss.
- A fix attempt (`PrState.fixAttempts`, judged against `max_fix_attempts`) is a new head that arrives — by the PR's synchronize webhook or by resync's GitHub read — on a PR whose last settled verdict is red AND whose push webhook did not classify it handoff-only: every path in the push's `changed_paths` under `.legion/`, `changed_paths_truncated` `"false"`, list non-empty (`classifyPush` in `reducers.ts`; the listener forwards the paths, the daemon owns the `.legion/` rule). The push and synchronize webhooks for one commit arrive in no promised order, and the answer is the same either way: push first, the classification is remembered in `PrState.pendingPush` (one slot keyed by sha, latest push wins) and consumed by `resetPrHead` when that exact head arrives; synchronize first, the head is counted and `PrState.headCounted` records it, then a handoff-only push for that head takes the attempt back and forgets a `pr-blocked` published for that count (`blockedAttempts` deleted when it equals the pre-decrement count), so the next real fix publishes it again. A push the daemon cannot classify counts as before this rule existed and says why through the `log` effect (`[legion] fix attempt: <repo>#<n> (<KEY>) push <sha> to <branch> could not be classified as handoff-only (<reason>); it counts against max_fix_attempts`): no `changed_paths_truncated` key means the listener predates LEGION-33; `"true"` means the list was capped at 100 unique paths; no `changed_paths` key with `"false"` means the push listed no commits (`payloadJSON` drops the empty string, so the truncated flag — never the paths key — is the "new listener" marker). A push mixing `.legion/` and other paths counts, silently. A push on a branch with no registered PR (`prByBranch` is the only filter — no `refs/heads/legion/` prefix guard) is ignored. Resync counts a head it discovers as before unless a pending classification names that head, in which case the same rule applies. `pr-blocked` is published once per exhausted count — `reduceCiEmission` records `PrState.blockedAttempts` and never republishes for the same count on a later red verdict, whatever the head.
- The design gate is a human's approval of the root issue's spec document in Dispatch, pinned to a document version: `state.gates[issue] = {artifactId, latestVersion, approvedVersion?}` (`DesignGate` in `legion-state.ts`), open exactly when `approvedVersion === latestVersion` (`designGateOpen` — the one function every reader asks; `catchup.ts` sends it as `gates[issue].open`). Three Dispatch issue events drive it once registered, all matched on `payload.artifact_id` against the gate's `artifactId` (`reducers.ts`) — an approval that landed before registration is picked up by the registration's own Dispatch read instead (`/gates/register` above): `artifact.approved` records `approvedVersion` and wakes the architect with `{type:"design-approved"}` only when the gate is then open (an approval below `latestVersion` is recorded silently); `artifact.changes_requested` deletes `approvedVersion` and wakes `{type:"design-changes-requested", version, reason, author?}`; `artifact.version` (named or unnamed) raises `latestVersion` and wakes nothing — a spec edited after approval closes the gate until the new version is approved. `ask.answered` no longer touches the gate. The decoder (`dispatch-events.ts`) rejects an artifact event missing `artifact_id`, a positive integer version, or — for changes requested — a non-empty `reason` as poison, so a reducer never throws on one. There is no non-human path to open the gate (the registration read only copies an approval a human already wrote): `gates.design: off` in the daemon config is the operator's only bypass, and the root architect learns the policy from one sentence `processes.ts` (`designGateFragment`) appends to the addressing part of its system prompt — sub-architects get none, since the root approval covers the tree. State v27 → v28 (`migrateV27State`, after LEGION-33's pure v24 → v25 bump, LEGION-37's v25 → v26 pendingAssignment step, and LEGION-27's v26 → v27 locator-identity bump, all of which left the gate records untouched) converts the old `{designAskId, designApproved}` records by reading each kept gate's issue from Dispatch once at boot (`specArtifactResolver`: the primary artifact's id and highest version) — kept when the tree record exists and is not `closed`, dropped otherwise with a log line naming the issue — and refuses to start, naming the issue, when that read fails; the migration and `register_gate`'s approval read (`seedGateFromDispatch` in `api/routes/issues.ts`) are the only Dispatch reads outside `resync.ts`.

- Phase workers (planner/implementer/tester/reviewer/merger, and sub-architects for child issues) run headless — `omp --mode rpc` behind a `legion worker-shim` process — one tmux window per issue, one pane per worker. The issue's first worker opens the window; every later worker on that issue splits into a recorded window of that issue only while some recorded pane in it still verifies as its recorded process (`TmuxRuntime.probedWindowId`) — otherwise it opens a fresh window, remembered in-memory for the next spawn, and no locator's `tmuxWindowId` is ever rewritten: a locator's window id is where its pane lives, and each stale locator clears through its own probe. Closing a tree stops every process gracefully through its own shim socket first (never SIGTERM), each one's pane killed directly only if it fails to close within the timeout — so a sibling worker that shuts down cleanly in the same window is never collaterally killed by one that hangs.
- `spawn_worker` always resumes the same agent for an existing phase: a live claim below the running-worker cap gets the new task prompted directly over its socket (`resumed` — once its turn is observed to start; see the delivery bullet below for the acknowledgement no turn follows) — at the cap, an idle-live claim's task queues instead without touching its locator (see the cap bullet below); a claim whose boot has not yet registered through `/worker/started` gets its task queued as `pendingAssignment` without launching a second pane (`resumed`); a dead claim with a recorded OMP session file respawns with `--resume`; only a role with no claim at all gets a genuinely fresh spawn. `/worker/ready` only delivers a queued task when both the caller's session id and generation match the claim's current ones, so a stale respawned session can never drain a newer claim's pending work. The one place a new active phase is written is the delivery of an architect assignment (`promptExistingWorker` with `kind: "assignment"`, prompted straight into a live worker or delivered from the claim's `pendingAssignment` at `/worker/ready`; `/phase/complete` only deletes, restores, or marks the record completed); a bare `/worker/started`, a reconnect, and the daemon's own `catchup-worker` prompt (`resumeWorker`) never write it. A catch-up is not sent to a phase-worker role that is neither the active phase nor holding a pending assignment (a sub-architect is always eligible: it parks for the life of its subtree and has no other recovery path), and never replaces a pending architect assignment (dropped with one log line, checked again inside the role's lock). The same bystander rule applies at delivery time (`isBystanderCatchup` in `legion-state.ts`): a queued `catchup` for a phase-worker role that has stopped being the active phase while it waited — behind the cap (`promoteQueuedWorker`, both the idle-live prompt branch and the cold relaunch branch: the queue entry is consumed, the pending cleared, no pane opened or prompted) or behind a boot (`/worker/ready`, above, where the relaunched pane is also retired so it never holds a `worker_cap` slot with nothing to do) — is dropped with one log line; an `assignment` in the same position is delivered as ever, and an architect's catch-up is always delivered. The predicate is defined once, `isBystanderRole` in `legion-state.ts` (`role !== "architect" && !isActivePhase(...)`), and shared by `resumeWorker`'s pre-check, `isBystanderCatchup`, and `/worker/started`'s registration log. The phase changes on a relaunch only through the architect's next `spawn_worker`.
- A finished phase worker does not stay resident until its tree closes. Each idle transition of a worker's cached shim client (`agent_end`, or a reconnect's `get_state` seeding `isStreaming: false`) arms a per-role idle-retire clock (`armIdleRetire`, `worker_idle_retire_seconds`, default 600; the literal `0` never arms it; at most 2147483 — the largest whole number of seconds whose millisecond delay fits a 32-bit timer, beyond which the runtime would clamp the delay to 1 ms and retire every finished worker at once); at expiry, inside the token's `mutateClaim` critical section, the daemon re-checks that the client is still cached and idle, the claim is ready-confirmed with a locator, the claim's role is not `architect` (`claim.role === "architect"` in `retireIdleWorker`, an explicit role check — not a judgement on the phase record: a sub-architect *is* `phases[child].phase` from the delivery of its assignment (`promptExistingWorker` writes the phase for every assignment) until it spawns the child's first phase worker, whose assignment supersedes it, so the not-active-phase check below would pass on every idle of a sub-architect that has moved past that point, and the root architect never holds a phase at all; both park by design between wakes for the life of their subtree, so each wake to a retired one would relaunch it through the no-holder recovery — one relaunch per wake costs more than one idle process per child issue), the tree is neither closing nor closed, no `pendingAssignment` is queued, and `phases[issue]` is absent, `completed`, or names another role (judged per role: an idle implementer retires while the tester runs on the same issue) — then performs exactly `markWorkerDeadLocked`'s retirement: graceful `shutdown` frame (kill-pane fallback), locator cleared, `ompSessionFile` carried into `resumeSessionFile`, persisted, `launchFailures` untouched. A decline on the active-phase or `pendingAssignment` check re-arms the clock inside the same critical section, so such a worker is retired within one further window once the phase moves on or the queued task drains; every other decline (running, architect, closing/closed tree, missing claim/locator/confirmation, replaced client) leaves it unarmed — a running worker's own next idle transition arms. The resulting socket close reaches `onWorkerClientClosed` → `markWorkerDead`, whose locator-identity re-check makes it a no-op; no `worker-died` is published. The next `spawn_worker` for the role resumes the same agent with `--resume`, and a retired claim occupies no `worker_cap` slot. A daemon restart's `reconnectWorkers` seeds already-idle workers' run state from the shim, so a deployment sheds its resident finished workers one window after the upgraded daemon starts. `dispose()` clears every armed clock. An architect reaches a finished worker only through `spawn_worker`; a direct `envoy_publish` to a retired role's topic is rejected with 404 by the listener at publish time.
- `config.workerCap` bounds only running or currently-prompted phase workers and sub-architects — never the root architect or controller, which are admitted separately via `state.trees`/`state.controllerLocator`. At the cap, a task for a role whose pane is already live and idle (between tasks, not dead) queues in `state.workerAdmission.queue` without touching its locator, instead of prompting it past the cap; a role with no live pane queues the same way, its claim's locator cleared. Each promotion re-derives the running count fresh and re-checks the current cap under a single admission lock before deciding, so a queued idle-live worker is prompted in place once a slot frees and a queued cold claim launches fresh — both promoted in priority order (`workerPriority`; FIFO within a tier), one at a time — a burst of fresh implementers never starves the testers, reviewers, and mergers queued behind it, which is what let work in progress grow without bound before (Sami, 2026-09-13).
- A prompt to a live worker — a queue promotion, `spawn_worker`'s direct prompt, or `/worker/ready`'s delivery — is delivered only when the worker's turn is observed to start: the first `agent_start` frame on its connection, or a `get_state` answer with `isStreaming: true`, within `worker_rpc_timeout_seconds` of the shim's acknowledgement (`WorkerRpcClient.prompt()` returns a `PromptReceipt`; `ProcessManager.awaitTurnStart` races it on the injectable clock). The shim's `{success:true}` is not delivery: OMP acknowledges before the turn starts and, since fork commit 0e57a6ca, can accept a message that starts none — which is how LEGION-10's queued task vanished with the phase written and the worker idle. Only a started turn commits the bookkeeping (`commitPromptDelivery`: queue entry removed, `pendingAssignment` cleared, `phases[issue]` written for an assignment, `promptFailures` reset, persisted). An acknowledgement no turn follows while the socket stays up is a prompt failure exactly like a refusal (`PromptNotStarted`, `reason: "no-turn"`): the client's run state is restored silently (`receipt.abandonWait()`, never firing its idle trigger — a transition-fired restore would retrigger promotion synchronously mid-failure, an unbounded retry storm), `promptFailures` counts one more, one log line names the token and the observation (`get_state: isStreaming=false` or `get_state failed: …`; the receipt is consulted again after that call however it ended, so an `agent_start` that lands while `get_state` is in flight is a started turn), the entry stays queued with its task — the two direct paths queue it (`queueUnstartedPrompt`) — and no drain is triggered on the spot, so a merely slow worker is not re-prompted at once; the retry is the next drain (an idle/dead event, the 60 s sweep). A socket that closes before the turn starts (`reason: "socket-closed"`, observation `socket closed`) is the worker's death, never a prompt failure: no site counts it, the late-start continuation is not left (nothing more arrives on that connection), and the socket-close handler alone retires the worker — `markWorkerDead` for a confirmed claim (the queued and direct paths, where the task stays queued so that retirement's own drain relaunches it cold), `retireUnconfirmedBoot` for the ready path's unconfirmed boot (see the `/worker/ready` row) — so one event has one handler. At `MAX_LAUNCH_FAILURES` the worker is retired (`recordPromptFailure` → `retireDeadClaim`, i.e. `retirePromptFailedClaim`: graceful shutdown with kill-pane fallback, locator cleared, session file kept), `promptFailures` returns to zero and the claim's `promptRetires` counts one more — one line `[legion] <token>: retiring after 3 prompts with no turn started; relaunch cycle <k> (bound 2)` — and the still-queued assignment falls through to a fresh cold launch with `--resume` on the next drain, `launchWorker` carrying `promptRetires` onto the relaunched claim. That cycle is bounded (LEGION-93): at `MAX_PROMPT_RETIRES` (2, judged `>=`) the retirement is terminal — the role's queue entry is removed, `pendingAssignment` stays on the claim, no `worker-queued` is published for that failure, and exactly one `worker-died {issue, role}` reaches the tree's architect (`publishWorkerDied`, skipped only when the tree is gone or closing: `isTreeGone`, the close path owns that claim) — so a worker that keeps acknowledging prompts and starting nothing ends in the same verdict a boot that never confirms does, instead of relaunching forever. Both counters are cleared only by a started turn (`commitPromptDelivery`, in-bound or late), never by a relaunch or an architect's `spawn_worker`: after a `worker-died`, the architect's next spawn of the same still-broken agent is one cold launch, three prompts, and `worker-died` again — its own spawn is the retry. A refused prompt counts in the same `promptFailures` (LEGION-60), so a persistently refusing worker reaches the same bound. A `StopFailed` from the retirement's stop leaves the locator, the queue entry, and `promptRetires` untouched (the in-memory `promptFailures` stays at the threshold), and the next drain's failure retries the retirement without burning a cycle. A turn that starts after the bound is the same task and is committed at that moment (`commitLateStart`, guarded by session, locator, the task compared by value, and the tree still alive: queue entry removed, pending cleared, phase written, failures reset, `worker-started` published) with no second prompt — a retry already in flight is refused by OMP (`AgentBusyError`) and its own bound then fails silently into the same accounting. A restart mid-promotion leaves the entry queued with its task, and boot's `reconcileWorkerAdmission` re-prompts it once `reconnectWorkers` seeds the client idle.
- `closeTree` tracks in-flight teardown only in memory (`ProcessManager`'s `closingTrees` map), never in the persisted `TreeState.status` — a crash mid-close leaves the durable status exactly where it was (`active`/`lingering`), so boot never needs a dedicated recovery path; the periodic linger sweep simply retries. `spawnWorker`/`workerReady` reject a closing tree with `TreeClosingError` (409); a process `closeTree` cannot confirm stopped (a real `kill-pane` failure, not the routine "already gone" race) raises `StopFailed` (502), keeps that claim/locator untouched, and leaves the tree `lingering` instead of `closed` for the sweep to retry.
- A freshly-launched worker's boot is watched (`WorkerBootWatchdog.arm`) against `worker_boot_timeout_seconds`, but that value is an observation interval, never a hard SLA: at each interval, a boot whose ready path is still unconfirmed is probed (`Runtime.probe` — for tmux, its pane still running the process its locator recorded, pid and `/proc` start ticks — or a reachable/answering shim socket) before anything happens — a live pane or socket just re-arms the watch, touching neither the claim nor `launchFailures`, however many intervals pass. Only a boot whose recorded process is gone — or whose pane is present but no longer that process — *and* whose socket refuses a connection is retired, counted as a launch failure, and either retried (same pending task, `--resume`) or escalated to `worker-died` at `MAX_LAUNCH_FAILURES`. A retirement whose stop could not be confirmed (`ProcessStopFailed`: the pane would not die, or could not even be listed) clears nothing — `retireWorkerLocator` rethrows before the locator or the accounting is touched — and re-arms the watch for one more interval instead of ending it, so the boot is retired on the next interval once the stop lands rather than left unwatched until a restart — unless the watch was cancelled, the watchdog disposed (`cancelAll()`), or a newer arm took the token while the retirement was in flight: that watch is finished, never looped, so no timer, dial, probe, or second retirement outlives `cancelAll()`. `launchFailures` itself is reset only once `/worker/ready` durably confirms the boot (`readyConfirmedAt` set, in both the pending-prompt and connect-only cases) — never by `/worker/started` registration alone, so a worker that keeps registering a fresh session but never reaches ready confirmation still accumulates failures across generations and escalates instead of resetting every relaunch.
- A phase worker's shim reaches the daemon one of two ways. The tmux runtime's `legion worker-shim --socket <path>` listens on a unix socket the daemon dials (`connectWorkerRpc`). `legion worker-shim --connect tcp://<host>:<port> --boot-token-file <path>` is the reverse: the shim dials `worker_stream_port` (`LEGION_WORKER_STREAM_PORT`, default `port + 1`, validated as a TCP port distinct from `port`; a port already in use fails startup naming `worker_stream_port`), sends its boot token in one `hello` line, and spawns OMP only after the daemon's `hello_ack` — so a worker never runs unobserved and a rejected token never starts one. The daemon gives each connection `worker_rpc_timeout_seconds` to complete its hello (rejected as `hello timeout` otherwise, exactly like an unknown, stale-generation, already-bound, or malformed one), so an idle or dripping pre-hello connection never holds a file descriptor open indefinitely. While OMP lives, a dropped stream is redialed with exponential backoff from 200 ms capped at 5 s, `hello` is re-sent, and frames produced during the gap are delivered from the shim's bounded backlog in order after the next ack; the same 1000-frame bound and one-time drop log apply in both modes. The two flags are mutually exclusive; an unreadable or blank token file is a CLI error before anything is spawned. The stream carries the same NDJSON RPC protocol as the unix socket (`rpc_chunk` reassembly, drain-aware writes, run-state tracking are shared); `hello`/`hello_ack` are the only frames the shim itself consumes besides `shutdown`; any other line the daemon sends before its `hello_ack` is not forwarded either — the shim drops it with a `[worker-shim] ignoring a frame received before hello_ack` log, since no OMP child exists yet to receive it.
- `api` before any `ProcessManager` call (`startDaemonLocked`, `index.ts`): no `ProcessManager` method runs before `api = startLegionApi(...)`. The manager's `mintControllerCapability`/`mintBootToken`/`mintWorkerBootToken`/`revokeSessionCapability` deps read `api` by reference, and every path into them — a dead worker's retirement (`retireWorkerLocator` → `revokeRoleClaim`), `ensureController`, root and worker launches — is reachable only afterwards. `reconnectWorkers` therefore runs after `api` is assigned (its retirements revoke through it) and, awaited, before `enableLaunches()` (promotion trusts the probed running-worker count); `pruneSecretFiles()` and the pending-controller-notice drain/spawn follow it in that same window. The API is already accepting requests while the probe runs; that is safe because every retirement re-validates its claim under `mutateClaim(token)`, an unprobed claim counts as running, and promotion stays gated.

## GitHub Apps

Legion acts on GitHub through two GitHub Apps, chosen per Legion role by `appRoleForLegionRole`
(`github-apps.ts`, the one role-keyed table — exhaustive over `LegionRole`, so a new role does not
compile until it is placed): the `planner`, `tester`, `reviewer`, and root and sub-`architect`
roles run as the **review** App (`github_apps.review` in `legion.yaml`; `legion-reviewer[bot]`),
and the `implementer` and `merger` run as the **implement** App (`github_apps.implement`;
`legion-implementer[bot]`). Both Apps are required, twice over: `loadGitHubApps` (`config.ts`)
refuses a `legion.yaml` whose `github_apps` lacks either role (`github_apps.<role> is required`,
before any private-key command runs, so `legion start --check-config` catches it), and
`startDaemonLocked` leases one token from each (`getToken("implement", …)` then
`getToken("review", …)`) before state is loaded, so a key that cannot mint refuses startup with
the `TokenManager` error instead of 500ing on that role's first `legion gh`. Every credential a
pane redeems by role — `/legion/v1/gh-token` behind `legion gh` and `legion threads resolve`,
`/legion/v1/git-credential` behind `jj git push`, the git identity lease minted at
`/worker/started`, and the worker catch-up's own GitHub reads (`workerCatchup`) — goes through
that one function, so the App a command acts as is the App of the role that runs it, never a
choice the command makes. The daemon's own uses are not role-keyed at all and are the implement
App explicitly: workspace provisioning (`ProcessManager`'s `provisioningToken`, `index.ts`, the
clone/fetch of the shared repository; and `/legion/v1/provisioning-credential`, `credentials.ts`,
the same token handed to the architect capability), the CI reads (`createCiStatusFetcher`), and
the first of the two boot leases above. Consequently only the implementer and merger can push the
issue branch: the review App holds no `contents` permission, so a planner's, tester's, reviewer's,
or architect's handoff commit stays in the shared workspace and reaches GitHub on the
implementer's next push.

A phase worker's commit identity is its pane environment, never a config write. `launchWorker`
(`processes.ts`) resolves the role's App identity from the token lease
(`appRoleForLegionRole` → `TokenManager.getToken(...).gitIdentity`) before the pane opens and
sets `JJ_USER`/`JJ_EMAIL` — which jj reads over every config scope — and
`GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL`/`GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` for plain git
(`gitIdentityEnv` in `github-app-env.ts`, the same mapping `buildRoleEnv` uses for the daemon's
own commands) on every pane `launchWorker` opens — the phase workers, and the sub-architects that
`spawn_worker` opens on child issues. The architect pane `spawnTree` opens for every admitted tree
(a root issue's, or a child's once `waves/release` admits it as its own tree) and the controller
pane never commit and carry none. Those six variables are pane-only exports like the boot token:
none of them is in `PANE_ENV_ALLOW_LIST` (`environment.ts`), so a daemon started from inside a
worker pane never hands that pane's App identity to anything it spawns — the private tmux server,
the architect and controller panes — and `buildRoleEnv`/`adoptWorkingCopy` set them explicitly on
the children that do commit as an App. A token-manager
failure fails the launch (counted in `launchFailures`): no pane opens without an identity. Every
issue workspace is a `jj workspace` of the one shared clone, and jj's repository-scoped config is
a single file for all of them (`~/.config/jj/repos/<hash>/config.toml`), so an identity written
there is the author and committer for every tree's commits at once. Provisioning
(`packages/workspace`, `provisionIssueWorkspace`) probes that scope on every launch — `jj config
list --repo --include-overridden`, because `ProvisionIssueWorkspaceDeps.run` is injected and the
package cannot assume a runner that strips `JJ_USER`/`JJ_EMAIL` from the command's environment;
without the flag a value the repo file holds is hidden whenever a higher layer overrides it — and
removes a leftover `user.name` or `user.email` once, with a
`[legion] removing repository-scoped jj …` log line; nothing writes them again. The environment
settles the committer; the author needs one more step, because jj keeps a rewritten commit's
author: `jj split`/`jj describe` carve a phase's work out of the issue's working-copy commit, which
the daemon's own `jj workspace add` created under the daemon's identity and which a split never
recreates while `.omp/config.yml` sits in it. So every assignment delivery
(`promptExistingWorker`, the one write of the active phase — a fresh launch's `/worker/ready`, a
`--resume`, or a live idle worker prompted over its socket; never a catch-up) first adopts the
working copy for the role (`Runtime.adoptWorkingCopy`, under `slow_command_timeout_seconds`),
before the prompt frame and before any state write. The command is one shared builder,
`adoptWorkingCopyCommand` in `@legion/workspace` (`jj metaedit --update-author -r '@ &
description(exact:"")' -R <workspaceDir>`); where it runs is the runtime's: `TmuxRuntime` runs it on
the daemon host's workspace under the lease identity's `JJ_USER`/`JJ_EMAIL` pair (the identity
variables `jj metaedit` reads); `KubernetesRuntime` sends the
pod's shim an `adopt-working-copy` frame (`jjUser`, `jjEmail`, `timeoutMs` — never a command or a
path) over the registered worker stream, and `legion worker-shim` runs the same builder in its own
workspace (`LEGION_WORKSPACE`/`LEGION_ROOT_WORKSPACE`) and answers `adopt-working-copy-result`. The
pod's init container adopts nothing: it provisions the workspace, and the assignment adopts it. A described working copy is a
previous phase's work and keeps its author, and a failing adoption — jj's stderr, the runner's
timeout or abort report, or the shim's `ok: false` — fails the delivery so no worker is prompted
whose commits would carry the wrong author.

GitHub lets only the pull request's author or an account with write (push) access to the
repository resolve a review thread or push to its branch; the review App is neither by design — it
holds `pull_requests: write` and no `contents` permission — so it can post reviews and reply on
threads but can neither push the `.legion/` deletion commit nor resolve the threads it opened: over
git the refused push reads `remote: Repository not found.`, and the REST/GraphQL API answers
`Resource not accessible by integration`. Widening the review App is rejected by design
(LEGION-34), not because it would not work. The implementer therefore pushes the `.legion/`
deletion at the reviewer's direction, and the implementer — before every push that answers a
review — and the merger — once more before READY — resolve every thread the reviewer has accepted with
`legion threads resolve --pr <number> --repo <owner>/<repo>` (`cli/review-threads.ts`,
`cmdThreadsResolve` in `cli/index.ts`). The command redeems the caller's grant through the same
`/gh-token` path `legion gh` uses, reads every review thread over GitHub GraphQL with an injected
`fetch`, resolves each unresolved thread whose newest comment was written by the account that
opened it and begins `Accepted:` (one `resolveReviewThread` per thread), prints `resolved <url>` /
`left open <url> — newest reply by <login> is not an acceptance`, and exits 1 naming the first
thread GitHub refuses; any newest comment that is not the opener's own `Accepted:` — a
`Still open:` reply, a reply by another account, or the opener's own later follow-up — leaves the
thread open with exit 0.

Each App's private key comes from exactly one of three `legion.yaml` sources under
`github_apps.<role>` (`loadGitHubApps`, `config.ts`): `private_key` (the PEM inline),
`private_key_command` (a shell command run at config load under the daemon's own `process.env` —
it exists to read the key the launcher supplies, and is never a pane — whose stdout is the PEM),
or `private_key_secret: <NAME>` — a secretsd key holding the PEM
base64-encoded. Two or none refuse with `github_apps.<role> requires exactly one of private_key,
private_key_command, or private_key_secret`. `private_key_secret` is the form for a shared box
where panes run as the daemon's user (LEGION-77, `docs/deployment.md`): `resolvePrivateKeySecret`
runs `secrets get <NAME> --no-request`, parses `{"key","tier"}`, and refuses start-up with exactly
`App private key <NAME> is readable by agent-tier callers; move it to a daemon-only store` unless
`tier` is `human` — the check never costs a tap; then logs `[legion] requesting <NAME> from
secretsd (human tier; a YubiKey tap may be needed)`, runs `secrets get <NAME> --value`,
base64-decodes stdout, and refuses unless it begins `-----BEGIN`; the PEM is held in memory like
command output. A missing `secrets` on the launcher's PATH, an unknown key, an unparsable status,
a non-PEM value, or any secretsd refusal names `github_apps.<role>.private_key_secret` and the key,
never the material. Both `secrets` children run under the daemon's own `process.env`, like
`private_key_command`, minus exactly `SECRETSD_SESSION_TOKEN_FILE` (only that variable: `SECRETSD_SOCK` is
the broker's socket path, not a session), and inherit the daemon's stdin: secretsd scopes a
tokenless caller by `isatty(0)` plus `/proc/self/fd/0`, so the daemon must be started with stdin
on its launcher pane's terminal and its grant is that pane's, never an agent session's. There is no
daemon-imposed timeout; secretsd's own approval window is the failure. `legion start
--check-config` (`resolveSecrets: false`) validates the name (one whitespace-free token) and never
runs `secrets`. Config loads before `resolveDaemonEnvironment`, so `secrets` resolves on the
launcher shell's PATH exactly as the `sh -c` of `private_key_command` does.

## OMP invocation and daemon tools

Set `omp_invocation` in `legion.yaml` or `LEGION_OMP_INVOCATION` to the required `mise x <tool> -- omp` command that launches the root architect and controller. The default is `DEFAULT_OMP_INVOCATION` in `omp-pin.ts`:

```sh
mise x ${OMP_FORK_PIN} -- omp
```

`OMP_FORK_PIN` (`github:sjawhar/oh-my-pi@<version>`) is the repository's one copy of the OMP fork pin: `config.ts` imports it, and the worker image (`packages/daemon/docker/worker.Dockerfile`) prints it inside the build. Bump it there and nowhere else.

Launch the daemon normally with `bun run ...`, not inside that scoped `mise x` command. At startup it obtains the complete `mise env --json` environment, and resolves absolute `mise`, `jj`, `git`, `gh`, and `tmux` paths. It does **not** resolve the OMP invocation to the pinned tool's install path: every pane and both boot probes run the configured `mise x <tool> -- omp` invocation itself, with `mise` replaced by that absolute path (`resolveOmpInvocation` in `environment.ts`), so mise activates the pinned tool inside the pane — its `bin` first on PATH, its declared environment — exactly as an operator's shell does. Exec'ing `<install dir>/bin/omp` directly skips that activation and runs whatever sits in the directory; `LEGION_OMP_PATH` is the one explicit way to name a direct binary (the Kubernetes worker image, a non-release build under test). It also writes a `legion` CLI launcher to `<state_dir>/bin/legion` (mode 0755, re-execing this same daemon's own runtime/entry — see `legionCliLauncherScript` in `environment.ts`) and prepends `<state_dir>/bin` to that PATH, so `legion state`/`legion gh`/`legion credential`/`legion handoff` on an ambient pane PATH always resolve to a CLI build that matches this daemon, never a stale or unrelated install. All daemon subprocesses use those absolute tool paths; root, worker, and controller panes all receive that same complete, launcher-prepended `PATH`.

Set `omp_launch_prefix` in `legion.yaml` (an array) or `LEGION_OMP_LAUNCH_PREFIX` (a single
shell-words string, e.g. `secrets ANTHROPIC_API_KEY GEMINI_API_KEY OPENAI_API_KEY --`) to an argv
prefix the daemon prepends to every OMP invocation it builds — root, worker, and controller panes,
and the two startup capability probes below. This is how a daemon that itself carries no provider
credentials (they live in secretsd, not the daemon's own environment) gets them into the pane
process: the prefix's own exec — `secrets KEY... -- <omp invocation>` — resolves them *inside* the
pane, never on the daemon's environment or a pane's tmux `-e` argv. Empty by default (nothing is
prepended). See `withOmpLaunchPrefix` in `runtime-tmux.ts`.

Set `instructions` in `legion.yaml` (a path, resolved against `legion.yaml`'s own directory when
relative — `legion start --config` passes that directory as the loader's `configDir`) or
`LEGION_INSTRUCTIONS` (used as given; consulted only when the file omits the key, like every other
`LEGION_*` override) to a markdown file of the deployment's standing rules — required checks,
deploy and verification commands, code-owner expectations, standing Envoy roles to consult, the merge
credential. An empty value from either source is rejected at config load. Before loading state,
opening core NATS, or serving the API, the daemon reads the file once and refuses to start when it
is missing, unreadable, a directory, or blank (the message names the resolved instructions path),
then writes `# Deployment instructions (<project as written in legion.yaml>)` plus the content to
`<state_dir>/deployment-instructions.md` (`deployment-instructions.ts`); a failed write refuses
startup too, with Node's error naming that target path. Every pane it launches — root architect,
sub-architects, phase workers, controller — carries that file as the last part of its system
prompt, after the role prompt and (for roots and workers) the addressing fragment. All of a pane's
parts travel in exactly **one** `--append-system-prompt` argument, joined by blank lines: OMP's flag
is last-wins (its argv handler assigns `appendSystemPrompt`, on both the production pin
`18.1.18-sami.20260912-203541` and the repository pin `18.1.18-sami.20260912-104423`), so several
flags would hand the model only the final fragment — with `instructions` configured, a pane would
get neither its role prompt nor its addressing line nor the root's gate policy, which previously let a
real architect skip an armed gate. The value is one double-quoted shell word:
the role prompt and this file are `$(cat …)`-expanded by the pane's shell, never inlined into the
command, and the addressing text is escaped for the double quotes. `systemPromptArguments` in
`runtime-tmux.ts` is the one builder both tmux launch sites use, so they cannot drift; the
Kubernetes runtime joins the same three texts the same way into its pod command. Absent key: no
instructions part.

Every root, worker, and controller pane also receives `DISPATCH_URL` and `DISPATCH_TOKEN_FILE` when
`dispatch_url` is configured: `DISPATCH_URL` is the configured service base URL (no `/mcp` suffix),
and `DISPATCH_TOKEN_FILE` is `<state_dir>/secrets/dispatch-token`, a 0600 file the daemon writes at
startup from the `DISPATCH_TOKEN` environment variable (required whenever `dispatch_url` is set —
`resolveDaemonConfig` refuses to start otherwise; an fs failure writing the file refuses startup
too). Neither variable is exported when `dispatch_url` is unset; those panes fall back to their own
`envoy.json` dispatch config.

A pane's environment is built from an allow-list, never by stripping known secrets from the
daemon's own. `resolveDaemonEnvironment` (`environment.ts`, `PANE_ENV_ALLOW_LIST` +
`paneEnvironment`) copies exactly these daemon variables — `HOME`, `USER`, `LOGNAME`, `SHELL`,
`TERM`, `TZ`, `LANG`, `LANGUAGE`, the thirteen `LC_*` names, `TMPDIR`, `TMUX_TMPDIR`,
`XDG_CACHE_HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_RUNTIME_DIR`, `XDG_STATE_HOME`,
`OMP_PROFILE`, `PI_PROFILE`, `MISE_CACHE_DIR`, `MISE_CONFIG_DIR`, `MISE_DATA_DIR`, `MISE_STATE_DIR`,
`SECRETSD_SOCK`, `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` (both cases), `SSL_CERT_DIR`,
`SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, and `PATH` (which `mise env` then replaces) — lays the
complete `mise env --json` output over them, and drops any credential-shaped name
(`isSecretLikeName`, case-insensitive: `*_SECRET`, `*_TOKEN`, `*_GRANT`, `*_KEY`, `*_PASSWORD`,
`*_PASSWD`, `*_PAT`, `*_CREDENTIALS`, their `*_FILE` twins, and anything containing
`PRIVATE_KEY`) as a second line of defence. That object is
`paneEnv`: the environment of every command `createDaemonRunner` runs (jj, git, gh, tmux, both
start-up probes), therefore of the private tmux server the first `tmux -L legion-<project>`
command forks, therefore of every pane. On top of it a pane gets only the explicit `-e` pairs
`processes.ts`/`runtime-tmux.ts` set (the `LEGION_*` family, `ENVOY_NATS_URL`/`ENVOY_URL`,
`GIT_CONFIG_COUNT=0`, `GIT_TERMINAL_PROMPT=0`, `DISPATCH_URL`/`DISPATCH_TOKEN_FILE`, the credential
pane environment below, and the `*_FILE` secret pointers). Nothing else the daemon was started with
reaches a pane: not the GitHub App private keys (`GH_AGENT_APP_PRIVATE_KEY_B64`/
`GH_REVIEW_APP_PRIVATE_KEY_B64` — read only by the daemon's own key readers in `config.ts`,
`private_key_command` and `private_key_secret`'s `secrets get` children (`runSecretsGet`), the two
children that run under the daemon's own `process.env` on purpose), not provider
keys (they reach a pane only through `omp_launch_prefix`), not `DISPATCH_TOKEN`, `ENVOY_*`
secrets, `SECRETSD_SESSION_TOKEN_FILE`, `OMP_SESSION_ID`, `JJ_CONFIG`, `TMUX`/`TMUX_PANE`,
`SSH_AUTH_SOCK`, or an outer pane's `LEGION_*`. A `gh` child the daemon spawns for a GitHub App role
(`buildRoleEnv`) starts from `paneEnv` too, minus `GH_TOKEN`/`GITHUB_TOKEN`/`GH_HOST`/
`GH_CONFIG_DIR`/`LEGION_GITHUB_APP_*` and credential-shaped names, plus the minted `GH_TOKEN`,
`GH_CONFIG_DIR` and `GIT_*` identity. A pane that needs a variable not on the list is a bug in the
list (add the name with its reader in the group comment), never a wildcard; the daemon's own
start-up probes run under the same environment, so a missing variable OMP itself needs fails the
boot loudly instead of the first pane. `LEGION_OMP_PATH` and the other `LEGION_*_PATH` overrides
are daemon configuration read from the daemon's own environment; they are not part of `paneEnv`.

Every root, worker, and controller pane also carries the credential pane environment
(`ProcessManager.credentialProcessEnvironment`) for its whole life — never per command:
`LEGION_GRANT_FILE=<state_dir>/secrets/<role token>-grant` (`grantSecretName`), the 0600 file the
pi-envoy extension writes each bash command's freshly minted grant to before the command runs and
`legion credential`/`legion gh`/`legion handoff complete` read ahead of `LEGION_GRANT` — the daemon
never writes it, only names it here and prunes it with the pane's boot-token file when the locator
clears (`trackProcessSecrets`; the boot prune seeds the name from the live locator, so a grant file
written later in the pane's life is still reaped); `GH_CONFIG_DIR=<state_dir>/gh`; `PATH` with
`<state_dir>/worker-bin` first exactly once (`worker-bin.ts` installs the `gh` shim there at
startup, before any pane can launch; `resolveDaemonEnvironment` strips every inherited `worker-bin`
entry from the mise PATH before it resolves the daemon's tools or hands that PATH to
`ProcessManager` as `processPath` — a daemon started from inside a Legion pane inherits that pane's
shim-first PATH through `mise env` — so the daemon's own `gh` is never the shim and the one prefix
`ProcessManager` adds is the only one); and `GH_TOKEN`/`GITHUB_TOKEN`/`GH_HOST` set
empty (rendered `-e KEY=`), so no ambient token or host shadows the per-call one `legion gh`
redeems. Nothing about the credential rides the bash tool's arguments — a plugin that replaces the
bash tool (the `secretsd` plugin's legacy shim drops `env`, LEGION-52) has no effect (LEGION-54).

No secret is ever a tmux `-e KEY=VALUE` value (a transient tmux client's argv is world-readable via
`/proc/<pid>/cmdline`). Boot tokens and the controller secret travel the same way as the Dispatch
bearer: `LEGION_BOOT_TOKEN_FILE` / `LEGION_CONTROLLER_SECRET_FILE` name a 0600 file
`<state_dir>/secrets/<role token>` (`legion-<project>-<key>-<role>`,
`legion-<project>-controller`) written immediately before that pane launches, overwritten on a
respawn of the same role, and removed by the prune `ProcessManager.persist()` runs once no live
locator references it — the steady-state prune walks only the names this process wrote or
inherited (no directory listing per save); the one listing prune `index.ts` runs at boot reaps
anything a crash left behind and seeds the steady-state set with its survivors, so an inherited
file is reaped the moment its locator clears. A launch in flight holds its file exempt from
pruning (`holdProcessSecret`, a refcount: two generations of one root can be launching at once) from
before the write until its locator is in state. A boot token doubles as the pane's recovery token
after a daemon restart, so its file lives exactly as long as the pane's locator. Consumers
(`@legion/envoy-client` `resolveDispatchConfig`, the pi-envoy extension, `legion status`) resolve
`X_FILE` — trimmed contents — ahead of `X`, and a set-but-unreadable or blank file is an error
naming the variable and path, never a fallback.

Every tmux command the daemon runs targets its own private server: `tmux -L legion-<project>`
(`TmuxServer` in `tmux.ts`; the socket name equals the session name). That server is forked by the
daemon's first tmux command and therefore inherits the runner's allow-listed `paneEnv`, never an
operator shell that may carry `DISPATCH_TOKEN`; Legion panes never appear in the operator's own
`tmux list-sessions`. Attach with `tmux -L legion-<project> attach -t legion-<project>`. A
`kill-pane` whose stderr says the private server is not there — `no server running` (socket file
left behind by an exited server) or `error connecting to … (No such file or directory)` (the socket
was never created: a first boot after the upgrade step below, or after a reboot cleared
`TMUX_TMPDIR`) — counts as the pane being gone (`PANE_GONE_STDERR` in `tmux.ts`, built on
`NO_SERVER_STDERR` there — the contract both `lookupPane` and `TmuxRuntime.stop`'s kill apply): no
server on the daemon's own socket means no Legion pane exists, and a dead worker's locator must
clear on that first boot rather than hold its running-worker slot until some later launch forks the
server.
**Upgrading a live box from a default-socket daemon:** stop the daemon,
`tmux kill-session -t legion-<project>` on the default server once, start the new daemon;
`reconnectWorkers` finds every recorded socket dead and roots resurrect (`--resume`) onto the
private server. No migration code.

A pane inherits two tmux environment tables beneath its own `-e` pairs, and both outlive the
daemon. The server's **global** table is the environment the server was forked with, for its whole
life, across daemon restarts — so a daemon restarted with a narrower `paneEnv` (this allow-list,
or any later change to it) would otherwise keep handing new panes whatever an earlier daemon left
in the running server. The daemon's **session** table (`legion-<project>`) is filled by tmux's
default `update-environment` from every attaching client: an operator's
`tmux -L legion-<project> attach` copies their `SSH_AUTH_SOCK`, `SSH_CONNECTION`, `SSH_ASKPASS`,
`DISPLAY`, … in, and every pane opened afterwards inherits the operator's SSH agent. Every boot
therefore, once the probes pass and before the launch hold releases
(`TmuxRuntime.scrubServerEnvironment`): reads the global table with `show-environment -s -g`
(`environmentNames` in `tmux.ts`, over `parseShellEnvironment`: the whole output is scanned as
text, never line by line — each set entry is `NAME="value"; export NAME;` with `$`, `` ` ``, `"`
and `\` backslash-escaped inside the value and a value's own newlines left in place, each unset
marker is `unset NAME;`, and an entry closes only on the first unescaped `"` followed by exactly
`; export <the same NAME>;` — so a multi-line value's continuation line, whatever it contains
(`HOME;=x`, `key = value`, the `=`-padded last line of a PEM), can never read as a name and no
per-name probe is ever sent; any other shape is a parse failure naming the table and the byte
offset, never the text there), empties the session's `update-environment` option (`set-option -t
legion-<project> update-environment ''`, `disableEnvironmentUpdates`) *before* reading the session
table (`show-environment -s -t legion-<project>`) so an attach landing in between cannot slip a
copy in behind the read, and `set-environment -u`s from each table every name that is not a key of
`paneEnv` (`PWD` and `SHLVL`, which tmux itself writes into the global table at server start, are
the only exemptions — checked as own properties, so a table entry named `constructor` is removed
like any other; a name ending in `;` is passed as `\;`, since tmux strips a trailing `;` from an
argv token). After the removals each table is listed again and two invariants checked, throwing
(names only) on a violation: every allow-listed name that was present is still present, and no
removed name remains — the guard against any argv re-tokenisation surprise on the unset side. One
line is logged with the de-duplicated names: `[legion] removed <n> variable(s) from the private
tmux server environment that panes may not inherit: <NAME1>, <NAME2>, …` — names, never values
(a tmux failure's message carries stderr only, never `show-environment`'s stdout). `openWindow`
creates the session and empties its `update-environment` in one tmux invocation (`new-session …
\; set-option -t <session> update-environment ''`), so no attach can ever copy a client's
environment into it. A server this daemon forked itself carries exactly `paneEnv` in its global
table and only markers in its session table, so it logs nothing; a variable the operator's
`tmux.conf` `set-environment -g`s (TPM's `TMUX_PLUGIN_MANAGER_PATH`) is removed and named like any
other. A tmux failure reading or writing either table, a dump the parser cannot read, or a
post-scrub invariant violation is as fatal as a failed probe. No server on the daemon's socket is not
(nothing to scrub: `openWindow` forks one under `paneEnv` with the option set); a server without
the daemon's session still has its global table scrubbed, and only the session step is skipped
(`openWindow` creates the session with the option set). A plain daemon restart is therefore
enough for *inheritance*: a pane opened after it gets nothing the allow-list does not pass, from
either table, and no `kill-server` is needed for that. It does not revoke what was already handed
out: the running server process and every pre-upgrade pane keep their fork-time environment —
readable through `/proc/<pid>/environ` by any same-uid process (a process's environment is copied
at exec and the scrub edits tmux's tables, not a process) — until `kill-server` (the server) or
retirement (the panes) ends them, or the key rotation revokes the material itself. `kill-server` is
needed for the socket move above, not for this change.

The daemon probes the OMP launch every pane will run (the `mise x <tool> -- omp` invocation, or `LEGION_OMP_PATH`) with an isolated extension and refuses to serve unless it confirms `pi.agents`. Both this probe and the plugin-load probe below start in `startDaemonLocked` right after the plugin contract gate (third paragraph below) — itself preceded by `resolveDaemonEnvironment` and `installWorkerGhShim` (`worker-bin.ts`), so the `gh` shim every pane's PATH puts first exists before any probe or pane runs, and an fs failure writing it refuses startup — but are awaited only at the launch hold, just before the first pane could open: state load, core NATS, the API bind, and the worker reconnect all proceed while a probe is still retrying, so `GET /legion/v1/state` answers and the durable lane keeps acking throughout. Each probe attempt runs under `slow_command_timeout_seconds`. A **transient** failure — the runner killed the probe at that budget, or OMP printed its marker and then exited non-zero (it died under host load) — is retried with exponential backoff from 10 s doubling to a 5 min cap, without limit (`DAEMON_PROBE_RETRY`), each attempt logged as `[legion] <name> probe failed transiently (attempt N); retrying in <delay>s: <detail>` (a timeout's detail reads `command timed out after <limit> s (ran <wall> s)`); the daemon waits the load out inside the process instead of handing the failure back to its supervisor's relaunch loop, which would add an OMP spawn per second to the load it was dying of. A **definitive** negative — the `LEGION_OMP_AGENTS=missing` marker, a clean exit without the marker, or the launch command failing before OMP ever ran (e.g. `secrets` denying a key) — still refuses: the daemon closes the event pump, API, worker stream, NATS, and the instance lock it had opened, `startDaemon` rejects with the probe's error, and `legion start` exits 1. An attempt the daemon itself abandoned — boot failed for another reason (state load, NATS, the API bind) while the attempt was running, so `startDaemon`'s abort signal made the runner kill it and report `aborted` — is neither: the chain ends at once with no `probe failed transiently` line and no `retrying in` line (a retry that will not happen is not announced), and the start-up error that caused the abort is the only thing logged; the same holds for a failed attempt that finished just as the signal aborted (a passed one still passes; the chain then stops at the next probe's loop-top check before anything is spawned). Both probes run through the same configured `omp_launch_prefix` as a spawned pane — one launch path, never a probe-only shortcut that could pass with credentials a real pane would lack. `legion probe-image` runs the same probes with a bounded policy (`IMAGE_PROBE_RETRY`: six attempts, about five minutes of waiting at worst) because an image build has no supervisor and must finish. The daemon also refuses startup with every missing required tool listed. Set `LEGION_MISE_PATH`, `LEGION_JJ_PATH`, `LEGION_GIT_PATH`, `LEGION_GH_PATH`, `LEGION_TMUX_PATH`, or `LEGION_OMP_PATH` to an absolute executable path to override discovery. The `mise x <tool> -- omp` form is required for `omp_invocation`; set `LEGION_OMP_PATH` when selecting a direct OMP binary. Supervisor note: `restart=on-failure` remains the right policy; the daemon simply no longer fails for a transient reason.

The second OMP probe, under the same start-after-the-gate/await-at-the-hold ordering and retry policy, proves that `@sjawhar/pi-legion-envoy` is what OMP actually loads: `verifyLegionPluginLoaded` (`boot-probes.ts`) runs `omp models --extension <probe.mjs> --json` through the same launch prefix and passes only when the probe prints `LEGION_PLUGIN_LOADED=yes` — the marker `legion.ts` sets on `globalThis[Symbol.for("legion.pi-envoy.legion-loaded")]` when OMP's ambient discovery loads it. A manifest on disk is never the gate: a disabled (`omp plugin disable`) or unregistered plugin has a manifest and still fails this probe. The installed manifest (`getPluginsNodeModules()/@sjawhar/pi-legion-envoy/package.json`, resolved through OMP's own `DirResolver` precedence: `OMP_PROFILE`/`PI_PROFILE` profile root, else `~/.omp/plugins`) is read only to name the version in the failure message. There is no minimum plugin version field; the plugin ships from this repo and the daemon spawns sessions without `--extension`, so they load `envoy.ts`/`legion.ts` solely from that installed copy. Both boot probes live in `boot-probes.ts` so `startDaemon` and the hidden `legion probe-image` subcommand — which the worker image build runs as its last step (`packages/daemon/docker/worker.Dockerfile`; see `docs/kubernetes.md`) — execute identical code.

Before loading state, opening core NATS, or serving the API, the daemon also reads the installed `@sjawhar/pi-legion-envoy` plugin's manifest (`~/.omp/plugins/node_modules/@sjawhar/pi-legion-envoy/package.json`, or the active `OMP_PROFILE`/`PI_PROFILE`'s profile root, or an existing `$XDG_DATA_HOME/omp` root — the same precedence OMP's own `DirResolver` uses) on every boot and refuses startup unless its `legion.daemonApiVersion` equals `LEGION_DAEMON_API_VERSION` (`packages/contracts/src/legion-daemon-api.ts`) — `verifyLegionPluginContract` in `boot-probes.ts`, beside the two launch probes; a missing or unreadable manifest, or one without the field, is the same refusal, never a fallback. The number covers two skews. The HTTP shapes: the plugin validates every daemon response against the strict `LegionDaemonApi` schemas it bundles, so a plugin built against another shape fails the controller/architect boot handshake (`daemon.state()` rejects the first unknown field) with nothing in the daemon's own log to say why. And the pane contract — every environment variable the daemon sets on a pane that the plugin reads or writes: `LEGION_GRANT_FILE`, `LEGION_BOOT_TOKEN_FILE`, `LEGION_CONTROLLER_SECRET_FILE`, `LEGION_CONTROL_SUBJECT`, `LEGION_DAEMON_URL`, `DISPATCH_URL`, `DISPATCH_TOKEN_FILE`, `ENVOY_NATS_URL`, `ENVOY_URL`, and the `LEGION_*` identity variables `LEGION_TREE`/`LEGION_ISSUE`/`LEGION_ROLE`/`LEGION_GENERATION`/`LEGION_WORKSPACE`/`LEGION_STATE_DIR`/`LEGION_CONTROLLER` (set by `processes.ts`'s three pane environments — root, worker, controller — plus the runtime's `<NAME>_FILE` pointer for the pane's one secret; read by the plugin's `extensions/legion.ts` and `src/legion/classify.ts` and by `@legion/envoy-client`'s Dispatch and Envoy config resolution) — so a plugin from before the credential file never writes the grant the daemon's `legion` commands read, and every worker the daemon spawns fails at its first `legion gh`/`jj git push`, after the work is done, with `grantFrom`'s (`cli/index.ts`) `LEGION_GRANT_FILE names <path>, which could not be read: ENOENT …: the pi-envoy extension in this pane did not write it — the installed plugin predates LEGION-54; install the released plugin in the profile and relaunch the pane`. The reverse skew — a plugin newer than the daemon, on a pane the daemon launched without `LEGION_GRANT_FILE` — is not something a daemon can gate (it cannot check a plugin newer than itself); the plugin blocks every bash command itself with `LEGION_GRANT_FILE is not set on this pane: the daemon that launched it predates this plugin; restart the daemon on the matching release` (`extensions/legion.ts`, the `tool_call` hook). The gate turns either skew into a named boot failure (`pi-legion-envoy at <manifest> (package <version>) speaks daemon API contract <n|none>; this daemon requires <N>`). Bump rule: any change to a `LegionDaemonApi` request or response shape, OR to the pane contract, bumps the constant and `packages/pi-envoy/package.json`'s `legion.daemonApiVersion` together in the same commit (`daemon-api-version.test.ts` pins them equal), and the deployment installs the plugin release built from the same commit into the active profile before the daemon restarts on the new code. Contract history: 1 was the `runtime` locator discriminant on `/legion/v1/state` (LEGION-21); 2 was introduced by LEGION-20 (PR #975) for the `stateGate` and `GatesRegister` shapes and, from LEGION-52, also covers the pane contract including the credential file `LEGION_GRANT_FILE` (LEGION-54) — plugin release 1.23.0 is the first to declare 2. What the gate does with each earlier release: 1.14.0 through 1.22.2 declare 1 and are refused as `speaks daemon API contract 1; this daemon requires 2` (1.20.1 through 1.22.2 are LEGION-54 builds that do write the credential file — they are refused only for declaring 1 after LEGION-20's HTTP-shape bump; 1.20.0 is not one: its tag `pi-legion-envoy-v1.20.0` was cut for #993 two minutes before #992 merged and its `dist/legion.js` has no `LEGION_GRANT_FILE`); releases before 1.14.0 have no `legion.daemonApiVersion` field and are refused as `contract none`. The load probe above then runs after this gate, so a plugin that is installed at the right contract but disabled or unregistered is still refused.
