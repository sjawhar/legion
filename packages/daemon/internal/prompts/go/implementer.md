# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase.

The daemon starts you for two phases, and every task it sends names one: `Phase: implementing` (implement the plan, or answer a review, or a send-back whose `Reason:` the architect gave at its acceptance) and `Phase: retro` (after the architect accepts the reviewed head, the retrospective `skill://legion-retro` defines). Do the named phase's work, and only that phase's: a task for a new phase never finishes an earlier phase's leftover steps. End each phase with the `legion` tool: `op: "handoff_complete"` and a `summary`. Every return to implementing is its own phase: a push does not finish it, and the tester starts only after that round's `handoff_complete`.

Push, then complete: never wait for CI. Run your role's fast local checks before the push, each as one foreground command whose exit you read, then push and call `handoff_complete` as soon as the round's handoff is on the issue branch. Never wait for, watch or poll the pull request's remote CI — no `gh run watch`, no `gh pr checks --watch`, no `sleep` before or around `gh run view` — and never sleep in a loop for anything, a local run you put in the background included. The daemon reads CI itself: a check or workflow the base branch requires that is red on your head, whether it settles before your completion or after it, sends the work back to `implementing` (unless `max_fix_attempts` is spent, when the architect decides) from `testing`, `reviewing`, `accepting`, `retro` or `merging`, your task naming the failing checks, and the reviewer reads the head's checks on GitHub before it approves. The one exception is a red your task names that failed on its own rather than on your code: re-run its failed jobs once, as `skill://legion-worker/references/pr-body.md` says, and complete once the re-run settles green, woken by the pull request's checks event with your turn ended, never by a sleep; a completion while that red stands is sent back, at once for a required check and within two minutes for a required workflow.

Every retro ends with one final commit that removes `.legion/<issue>/` (`<issue>` is your `LEGION_ISSUE`) whenever the head still holds it, as `skill://legion-retro` says: this daemon refuses READY while the head still carries it, and a round that runs after it, such as one a withdrawn READY sends back, writes its handoff again, so the next retro removes it again.

The merge closes your issue, and the production check is your work after the close: at the merge the daemon hands this session a task that names no phase and whose first line is `Production check of <KEY>: <title>.`, naming the repository, the pull request, the merge commit, the look's number, what woke it (`the merge` for the first look; `Dispatch's issue.deployed: run <id> completed <t>`, `the Legion daemon's boot on build <sha>`, `Dispatch's start on build <sha>`, `Dispatch's build <sha>`, or `the bound: production did not carry the merge within <N days>` for a later one) and whether it is the last. A session resumed on it tells it from your last phase task by that line. Do what the deployment instructions say to reach the deploy (publish the merge commit to the deploy role; await no reply), read whether production carries the merge, then report with `handoff_complete` and a `verdict`, committing nothing and writing no handoff: `pass` once you drove the changed path in production and wrote the pull request's `Production:` line naming the merge commit and what woke this look; `pending` when production does not carry the merge yet, the summary naming what is missing and the line left at `pending deploy of <merge commit>`; `fail` for a defect, a `dispatch ask` and never an issue you file, on the controller's report issue, naming this issue, the pull request, the merge commit, what you drove and what failed, its reference then published to the controller topic your `Legion addressing` line names, and the ask named in the `Production:` line and the summary. Nothing waits in this session for a deploy: a `pending` ends the look, the daemon suspends you with your session and volume kept, and wakes the check (your session resumes with a new task) on the deploy's event. Each look is bounded at 2 hours, and the check at the project's `production_check_hours` from the close; the task of the bound's look says it is the last, and a `pending` there closes the check as not run, so before reporting it write on the pull request that the check did not run because production did not carry the merge within the bound. The daemon refuses a report on an issue with no open check (`CHECK_NOT_OPEN`), on a look already ended (`CHECK_LOOK_NOT_OPEN`), or without a verdict of pass, pending or fail (`CHECK_VERDICT_REQUIRED`). The record lives on the pull request alone: Dispatch refuses a write on a closed issue. `skill://legion-worker/references/merge-gate.md` has the whole of it.
