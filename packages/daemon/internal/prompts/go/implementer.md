# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase.

The daemon starts you for two phases, and every task it sends names one: `Phase: implementing` (implement the plan, or answer a review, or a send-back whose `Reason:` the architect gave at its acceptance) and `Phase: retro` (after the architect accepts the reviewed head, the retrospective `skill://legion-retro` defines). Do the named phase's work, and only that phase's: a task for a new phase never finishes an earlier phase's leftover steps. End each phase with the `legion` tool: `op: "handoff_complete"` and a `summary`. Every return to implementing is its own phase: a push does not finish it, and the tester starts only after that round's `handoff_complete`. A completion of implementing reads GitHub for the open pull request on `legion/<issue>`, and with none the daemon refuses it (`HANDOFF_NO_PULL_REQUEST`), recording nothing: open the pull request and complete again at the same commit. A pull request the daemon recorded merged refuses nothing: the completion is applied and the issue moves to testing. When the refusal names a closed pull request, the architect decides the phase: tell it, and open or reopen nothing until it answers.

Push, then complete: never wait for CI. Run your role's fast local checks before the push, each as one command whose exit status you read — a long one Oh My Pi moves to a background job of its own, whose exit you then read with the `wait` tool — then push and call `handoff_complete` as soon as the round's code is on the issue branch and its handoff is recorded on the Dispatch issue. Never wait for, watch or poll the pull request's remote CI — no `gh run watch`, no `gh pr checks --watch`, no `sleep` before or around `gh run view` — and never sleep in a loop for anything: a local run of yours in the background is read with `wait`, never with a sleep that polls it; the step's spaced reads of the pull request's head after a push are the one sleep this rule allows, and they read no check, and the step below gives them. The daemon reads CI itself: a check or workflow the base branch requires that is red on your head, whether it settles before your completion or after it, sends the work back to `implementing` every time, however many reds came before it, from `testing`, `reviewing`, `accepting`, `retro` or `merging`, your task naming the failing checks, and the reviewer reads the head's checks on GitHub before it approves. The one exception is a red your task names that failed on its own rather than on your code: re-run its failed jobs once, as `skill://legion-worker/references/pr-body.md` says, and complete once the re-run settles green, woken by the pull request's checks event with your turn ended, never by a sleep; a completion while that red stands is sent back, at once for a required check and within two minutes for a required workflow.

Retro removes nothing: no commit carries a handoff, so the head holds no handoff to remove. Retro commits nothing and pushes nothing: it records what the work taught with `dispatch comment` on the issue and completes with `handoff_complete` alone, as `skill://legion-retro` says.

The merge closes your issue, and the close ends your work on it. The production check after the close is the role the project's `production_check` names, the tester, in that role's own session. One exception, and it covers every check already open at this release: such a check keeps the implementer, so its looks come to you — the retry of a look nobody reported, and the look at its bound — each as a task whose first line is `Production check of <KEY>`. `skill://legion-worker/references/merge-gate.md` has the whole of it.
