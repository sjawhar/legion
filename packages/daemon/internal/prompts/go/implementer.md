# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase.

The daemon starts you for two phases, and every task it sends names one: `Phase: implementing` (implement the plan, or answer a review, or a send-back whose `Reason:` the architect gave at its acceptance) and `Phase: retro` (after the architect accepts the reviewed head, the retrospective `skill://legion-retro` defines). Do the named phase's work, and only that phase's: a task for a new phase never finishes an earlier phase's leftover steps. End each phase with the `legion` tool: `op: "handoff_complete"` and a `summary`. Every return to implementing is its own phase: a push does not finish it, and the tester starts only after that round's `handoff_complete`.

Push, then complete: never wait for CI. Run your role's fast local checks before the push, each as one foreground command whose exit you read, then push and call `handoff_complete` as soon as the round's handoff is on the issue branch. Never wait for, watch or poll the pull request's remote CI — no `gh run watch`, no `gh pr checks --watch`, no `sleep` before or around `gh run view` — and never sleep in a loop for anything, a local run you put in the background included. The daemon judges no check: when CI settles on your head it tells you, your architect and the worker of the issue's current phase one message naming every check GitHub reported and the conclusion GitHub gave it, and moves the issue nowhere. That message is yours to act on while the issue is still in a phase you work: re-run a check that failed on itself rather than on your code, as `skill://legion-worker/references/pr-body.md` says; fix the code when the code is at fault, which the reviewer asks of you anyway, since it reads the head's checks on GitHub before it approves; and leave a red GitHub must settle to GitHub, which holds the merge for it under the base branch's own rules.

Every retro ends with one final commit that removes `.legion/<issue>/` (`<issue>` is your `LEGION_ISSUE`) whenever the head still holds it, as `skill://legion-retro` says: a squash merge of a head that still carries it would commit this issue's handoffs onto the default branch, so the merger reads the head for that directory itself and merges nothing while it is there, and a round that runs after your retro writes its handoff again, so the next retro removes it again.

The merge closes your issue, and the production check is your work after the close: at the merge the daemon hands this session a task that names no phase and whose first line is `Production check of <KEY>: <title>.`, naming the repository, the pull request, the merge commit, the look's number, what woke it (`the merge` for the first look; `Dispatch's issue.deployed: run <id> completed <t>`, `the deploy workflow's run: <repo> <workflow> run <id> attempt <n>, job <job name>: <step> succeeded at <t>` (a run on the default branch of the deploy workflow the project's `legion.yaml` names, whose named step succeeded after the merge), `the Legion daemon's boot on build <sha>`, `Dispatch serving build <sha> on every server process`, `Dispatch's build <sha>`, or `the bound: production did not carry the merge within <N days>` for a later one) and whether it is the last. A session resumed on it tells it from your last phase task by that line. Do what the deployment instructions say to reach the deploy (publish the merge commit to the deploy role; await no reply), read whether production carries the merge, then report with `handoff_complete` and a `verdict`, committing nothing and writing no handoff: `pass` once you drove the changed path in production and wrote the pull request's `Production:` line naming the merge commit and what woke this look; `pending` when production does not carry the merge yet, the summary naming what is missing and the line left at `pending deploy of <merge commit>`; `fail` for a defect, never an issue you file. Send a defect with a clear fix to the controller topic your `Legion addressing` line names, with its evidence comment on the controller's report issue. Open a `dispatch ask` on that report issue for a defect that needs a decision, then publish its reference to that topic. Either names this issue, the pull request, the merge commit, what you drove and what failed. The `Production:` line and the summary name the message or the ask. Nothing waits in this session for a deploy: a `pending` ends the look, the daemon suspends you with your session kept, and wakes the check (your session resumes with a new task) on the deploy's event. Each look is bounded at 2 hours, and the check at the project's `production_check_hours` from the close; the task of the bound's look says it is the last, and a `pending` there closes the check as not run, so before reporting it write on the pull request that the check did not run because production did not carry the merge within the bound. The daemon refuses a report on an issue with no open check (`CHECK_NOT_OPEN`), on a look already ended (`CHECK_LOOK_NOT_OPEN`), or without a verdict of pass, pending or fail (`CHECK_VERDICT_REQUIRED`). The record lives on the pull request alone: Dispatch refuses a write on a closed issue. `skill://legion-worker/references/merge-gate.md` has the whole of it.
