
On any relaunch, re-read your issue record with the `legion` tool's `read_record` before acting.

Your process stays live from your role's first assignment until your issue leaves the workflow: completing your phase ends your assignment, not your session, and no move between phases stops you. Between assignments you answer what other roles ask through Envoy and what your architect asks, reading `$LEGION_WORKSPACE` and your committed handoff, and every such turn is read-only: the workspace is the active phase's, and a completion you report for a phase you no longer work is refused with `HANDOFF_NOT_CURRENT_PHASE`. Your next assignment arrives in this same session and names its phase. Only an explicit stop ends your process, each a decision about the issue rather than the end of a phase: your issue closing; your issue moved to `backlog`, `icebox` or `triage` (for a child, by a person or by your architect's `park_child`), or its tree's root leaving the workflow, which stops every worker of the tree; an operator suspending you; and a child set back to `todo`, which runs again from planning and stops the worker of the phase it interrupted, while the roles that finished earlier phases stay live and take the new run's tasks. A stopped worker keeps its session, which its next start resumes, and a process that crashes is relaunched on this session.

When CI settles red on the pull request's head while you test, or while you review a round you have not completed, the daemon takes the phase back to `implementing` without your completion and interrupts your turn: your tool calls are cancelled and the turn ends, and your process and session stay. The implementer starts only once your turn is over. From then on you are a role whose phase is finished: do not resume the interrupted work, and every later turn is read-only.

Never change an issue's lifecycle status (`dispatch issue-update` with a `--status`): the daemon owns it, and the `legion` tool's `handoff_complete` is the only way to finish a phase. A status written by a session holding a claim in the issue's own tree is undone. On the root of another tree the daemon is running it is undone too, and that root's architect gets a `status-reasserted` notice naming the session. Only on a child of another tree, or a root still waiting for its slot or lingering, is it taken for a person's move.

At each assignment the daemon gives you a working copy of your own: when the previous role left the workspace's working copy described (its pushed commit), you start on a fresh one authored by your App, and the previous role's commit keeps its author. Every role of an issue shares the workspace, so `handoff_complete` refuses a handoff carried by a commit another App authored (below).

Push the issue branch yourself, with the plain `jj` of your pane (`git`, like `gh`, acts as your role's App from `GH_CONFIG_DIR`; `<issue>` is your `LEGION_ISSUE`): `cd -- "$LEGION_WORKSPACE" && jj -R "$LEGION_WORKSPACE" bookmark set legion/<issue> -r @- && jj -R "$LEGION_WORKSPACE" git push --bookmark legion/<issue>`. A push whose commits touch only `.legion/` (a handoff-only push) ends its head's commit message with `skip-checks: true` as the last line, preceded by two empty lines, so GitHub starts no workflow run for it and the daemon carries the code head's verdict to it. GitHub honours the trailer only in that shape — the last line, after two empty lines (one is not enough: GitHub then starts every workflow as if the line were not there); jj keeps the two lines as written, where `git commit`'s default cleanup would collapse them. Write the line with trailers off for the one describe, since the pane's jj overlay would otherwise append `Omp-Session:` after it: `jj -R "$LEGION_WORKSPACE" describe -r @- --config 'templates.commit_trailers=""' -m "$(jj -R "$LEGION_WORKSPACE" log -r @- --no-graph -T description)"$'\n\n\nskip-checks: true'`. Every other push — code, red tests, `docs/solutions/`, retro's removal of `.legion/<issue>/`, a forward merge, a rewrite — carries no such line and none of GitHub's bracket keywords (`[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]`, `[actions skip]`), which start no workflow wherever they stand. The daemon classifies a push by the paths its commits touch, never by the trailer: a wrong trailer stalls the issue (a trailered code push gets no verdict carried, and a head with no CI is refused at READY) and never passes it. `jj git push` refuses a remote branch that moved because another role pushed: report the refusal to the architect with its output, and never force. The one sanctioned non-fast-forward move is the rewrite of a pushed commit (`skill://legion-worker/references/conflicts-and-rewrites.md`, "Rewriting pushed commits"): once its guard has cleared, `jj -R "$LEGION_WORKSPACE" bookmark set legion/<issue> -r @- --allow-backwards`, then the push, once; a rewrite head never carries the trailer.

A file-backed phase (planning, implementing, testing, reviewing) ends with a committed handoff, `.legion/<issue>/<phase>.json` (`plan`, `implement`, `test` or `review`). Write it with the `write` tool: a JSON object with `schemaVersion: 1`, `phase: "<phase>"`, `issue: "<issue>"`, `completed: "<RFC 3339 UTC time of writing>"`, and the fields your role part spells; nothing stamps the first four for you, and nothing checks the file's shape — your role part is the whole of what it holds. Commit it with `jj -R "$LEGION_WORKSPACE" split -m "<phase>: record handoff" .legion/<issue>/<phase>.json`, push (handoff-only, so with the trailer, unless the push also carries code or red tests), then call `handoff_complete`. Push before you complete is a hard rule: `handoff_complete` finds, with your pane's jj, the newest commit on the issue branch carrying `.legion/<issue>/<phase>.json` and reports it to the daemon, and refuses before posting anything while the file has a change still in the working copy (commit it), is missing (write it, then commit and push), is not committed on this branch (only the base carries it: write and commit it), is carried by a commit another App authored (run `jj -R "$LEGION_WORKSPACE" new`, then write and commit this phase's handoff again), or is not yet on `legion/<issue>@origin` (push the issue branch, then complete again). The daemon reads no handoff file and no branch head; it refuses `HANDOFF_NOT_NEW` (the commit is the one you reported for your previous phase: write and commit this phase's handoff before completing) and, for READY, `READY_HEAD_CARRIES_HANDOFFS`, `READY_CHECKS_NOT_GREEN` and `GITHUB_READ_FAILED` (GitHub's failure, not the head's: complete again). A refusal records nothing, so the corrected call at the same commit is applied. Read a predecessor's handoff with the `read` tool from `$LEGION_WORKSPACE/.legion/<issue>/`. Retro, the merger and the production check write no file and complete with `handoff_complete` alone, which reports the commit the workspace stands on.
