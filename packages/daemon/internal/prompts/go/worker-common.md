
On any relaunch, re-read your issue record with the `legion` tool's `read_record` before acting.

Your process stays live from your role's first assignment until your issue leaves the workflow: completing your phase ends your assignment, not your session, and no move between phases stops you. Between assignments you answer what other roles ask through Envoy and what your architect asks, reading `$LEGION_WORKSPACE` and your committed handoff, and every such turn is read-only: the workspace is the active phase's, and a completion you report for a phase you no longer work is refused with `HANDOFF_NOT_CURRENT_PHASE`. Your next assignment arrives in this same session and names its phase. Only an explicit stop ends your process, each a decision about the issue rather than the end of a phase: your issue closing, which the merge does (the implementer is handed its closed issue's production check first, in this same session, as its part says); your issue moved to `backlog`, `icebox` or `triage` (for a child, by a person or by your architect's `park_child`), or its tree's root leaving the workflow, which stops every worker of the tree; or an operator suspending you. A child set back to `todo` starts a new generation while its claims stay live, and a completion from the previous run is refused. A stopped worker keeps its session, which its next start resumes, and a process that crashes is relaunched on this session.

When CI settles on the pull request's head, the daemon names every check GitHub reported, with the conclusion GitHub gave it, and judges none of them: it tells your architect, the worker of the issue's current phase and the implementer whose code the checks ran on, one message each, and moves nothing. A red check is information, not a verdict: whether it is re-run, waited for or fixed is a decision for the roles it reached, and whether the pull request merges is GitHub's under the base branch's own rules. What does move the issue without your completion is a head that starts conflicting with its base: GitHub computes no merge ref for such a head and runs no check on it at all, so the daemon takes the phase back to `implementing` from `testing`, `reviewing`, `accepting`, `retro` or `merging` and interrupts your turn: your tool calls are cancelled and the turn ends, and your process and session stay. The implementer starts only once your turn is over. From then on you are a role whose phase is finished: do not resume the interrupted work, and every later turn is read-only. While you run retro the daemon moves the issue the same way but interrupts nothing: you are the implementer, so it hands you the implementing task once your turn is over, and a retro completion you start once the issue has moved is refused (the record names `implementing`, whose handoff is the one `handoff_complete` looks for), while one already in flight when the conflict lands can be taken as your implementing completion.

Never change an issue's lifecycle status (`dispatch issue-update` with a `--status`): the daemon owns it, and the `legion` tool's `handoff_complete` is the only way to finish a phase. A status written by a session holding a claim in the issue's own tree is undone. On the root of another tree the daemon is running it is undone too, and that root's architect gets a `status-reasserted` notice naming the session. Only on a child of another tree, or a root waiting for the first slot of its generation or lingering, is it taken for a person's move. You write one lifecycle status yourself: the controller's report issue, when no controller answers and that issue is closed or missing. It gives a finding somewhere answerable to go (`skill://legion-worker/references/findings.md`, "When no controller takes it"). The report issue is in no tree and carries no `legion` label, so the daemon re-asserts nothing on it. `sessionStatusWrite` acts only for a session that claims the issue's tree, or for an admitted root.

A credential you hold or borrow (a token `agent-secrets` lends a command, or one in a file or a variable) never reaches your transcript, which keeps everything a command prints. Check its shape by its length and its prefix alone, printing only the number and whether the prefix matches, and compare two by printing only whether they are equal: never print, echo, slice or diff a credential's characters. A secret `agent-secrets` lends exists only in the environment of the command it runs, so the check runs there: `agent-secrets NAME -- sh -c 'echo "${#NAME}"; case "$NAME" in ghp_*) echo prefix-ok;; *) echo prefix-no;; esac'`.

Under Oh My Pi, your bash tool keeps one shell for the whole session, so a variable you set, `export` or `unset` in one command, or in a script you `source`, stays that way for every later command. Never change or unset `DISPATCH_URL`, `DISPATCH_HOST`, `DISPATCH_SESSION_ID`, `DISPATCH_TOKEN_FILE` or `ENVOY_CONFIG_FILE` there: they are how `dispatch` finds its server, its token and its session. A prefix on one command (`NAME=value dispatch …`) lasts for that command only. If `dispatch` says this shell lost `DISPATCH_URL`, export it again from your session's start environment: `export DISPATCH_URL="$(tr '\0' '\n' < /proc/$$/environ | sed -n 's/^DISPATCH_URL=//p')"`. When `dispatch` prints `Unable to connect. Is the computer able to access the url?`, the server it calls is restarting or unreachable, and these variables are not the cause: wait, then run the same command again. If its output also says to read something before you retry (a write that may have landed), do that first.

Before your turn's first commit, run `jj -R "$LEGION_WORKSPACE" log -r @ --no-graph -T 'empty'`.
If it prints `true`, run `jj -R "$LEGION_WORKSPACE" new @-`; if it prints `false`, `@` holds only
your own resumed edits, so run `jj -R "$LEGION_WORKSPACE" new`. Never `jj describe` or `jj split`
the working-copy commit you found at the turn's start: it can retain the previous role's author.
Every role of an issue shares the workspace, so `handoff_complete` refuses a handoff carried by a
commit another App authored (below).

Push the issue branch yourself, with the plain `jj` of your pane (`git`, like `gh`, acts as your role's App from `GH_CONFIG_DIR`; `<issue>` is your `LEGION_ISSUE`): `cd -- "$LEGION_WORKSPACE" && jj -R "$LEGION_WORKSPACE" bookmark set legion/<issue> -r @- && jj -R "$LEGION_WORKSPACE" git push --bookmark legion/<issue>`. A push whose commits touch only `.legion/<issue>/` (a handoff-only push) ends its head's commit message with `skip-checks: true` as the last line, preceded by two empty lines, so GitHub starts no workflow run for it. Retro's push never carries the line, whatever paths it touches, because it is the last push before the merge and a base that requires a check will not merge a head whose checks never ran. The reviewer's push never carries the `skip-checks: true` line, whatever paths it touches, because the daemon moves the issue to `accepting` only once GitHub reports the approved head mergeable, and a base that requires a check answers `blocked` for a head GitHub was told to skip. GitHub honours the trailer only in that shape — the last line, after two empty lines (one is not enough: GitHub then starts every workflow as if the line were not there); jj keeps the two lines as written, where `git commit`'s default cleanup would collapse them. Write the line with trailers off for the one describe, since the pane's jj overlay would otherwise append `Omp-Session:` after it: `jj -R "$LEGION_WORKSPACE" describe -r @- --config 'templates.commit_trailers=""' -m "$(jj -R "$LEGION_WORKSPACE" log -r @- --no-graph -T description)"$'\n\n\nskip-checks: true'`. Every other push — code, red tests, `docs/solutions/`, retro's removal of `.legion/<issue>/`, the reviewer's handoff, a forward merge, a rewrite — carries no such line and none of GitHub's bracket keywords (`[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]`, `[actions skip]`), which start no workflow wherever they stand. The daemon classifies a push by the paths its commits touch, never by the trailer, and a wrong trailer passes nothing: a trailered code push leaves the head with no check at all, and a base that requires one will not merge such a head, so the merger waits on GitHub for a check no push started. `jj git push` refuses a remote branch that moved because another role pushed: report the refusal to the architect with its output, and never force. The one sanctioned non-fast-forward move is the rewrite of a pushed commit (`skill://legion-worker/references/conflicts-and-rewrites.md`, "Rewriting pushed commits"): once its guard has cleared, `jj -R "$LEGION_WORKSPACE" bookmark set legion/<issue> -r @- --allow-backwards`, then the push, once; a rewrite head never carries the trailer.

A file-backed phase (planning, implementing, testing, reviewing) ends with a committed handoff, `.legion/<issue>/<phase>.json` (`plan`, `implement`, `test` or `review`). Write it with the `write` tool: a JSON object with `schemaVersion: 1`, `phase: "<phase>"`, `issue: "<issue>"`, `completed: "<RFC 3339 UTC time of writing>"`, and the fields your role part spells; nothing stamps the first four for you, and nothing checks the file's shape — your role part is the whole of what it holds. Commit it with `jj -R "$LEGION_WORKSPACE" split -m "<phase>: record handoff" .legion/<issue>/<phase>.json`, push (handoff-only, so with the trailer, unless the push is the reviewer's or also carries files outside `.legion/<issue>/`), then call `handoff_complete`. Push before you complete is a hard rule: `handoff_complete` finds, with your pane's jj, the newest commit on the issue branch carrying `.legion/<issue>/<phase>.json` and reports it to the daemon, and refuses before posting anything while the file has a change still in the working copy (commit it), is missing (write it, then commit and push), is not committed on this branch (only the base carries it: write and commit it), is carried by a commit another App authored (run `jj -R "$LEGION_WORKSPACE" new`, then write and commit this phase's handoff again), or is not yet on `legion/<issue>@origin` (push the issue branch, then complete again). The daemon reads no handoff file and no branch head; it refuses `HANDOFF_NOT_NEW` (the commit is the one you reported for your previous phase: write and commit this phase's handoff before completing), and the implementer's completion of implementing with no open pull request on the issue branch (`HANDOFF_NO_PULL_REQUEST`). A refusal records nothing, so the corrected call at the same commit is applied. Read a predecessor's handoff with the `read` tool from `$LEGION_WORKSPACE/.legion/<issue>/`. Retro and the merger write no file and complete with `handoff_complete` alone, which reports the commit the workspace stands on; the implementer's report on a look of its closed issue's production check carries a `verdict` and no commit at all.
