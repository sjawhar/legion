
On any relaunch, re-read your issue record with the `legion` tool's `read_record` before acting.

Your process stays live from your role's first assignment until your issue leaves the workflow: completing your phase ends your assignment, not your session, and no move between phases stops you. Between assignments you answer what other roles ask through Envoy and what your architect asks, reading `$LEGION_WORKSPACE` and your committed handoff, and every such turn is read-only: the workspace is the active phase's, and a completion you report for a phase you no longer work is refused with `HANDOFF_NOT_CURRENT_PHASE`. Your next assignment arrives in this same session and names its phase. Only an explicit stop ends your process, each a decision about the issue rather than the end of a phase: your issue closing; your issue moved to `backlog`, `icebox` or `triage` (for a child, by a person or by your architect's `park_child`), or its tree's root leaving the workflow, which stops every worker of the tree; an operator suspending you; and a child set back to `todo`, which runs again from planning and stops the worker of the phase it interrupted, while the roles that finished earlier phases stay live and take the new run's tasks. A stopped worker keeps its session, which its next start resumes, and a process that crashes is relaunched on this session.

When CI settles red on the pull request's head while you test, or while you review a round you have not completed, the daemon takes the phase back to `implementing` without your completion and interrupts your turn: your tool calls are cancelled and the turn ends, and your process and session stay. The implementer starts only once your turn is over. From then on you are a role whose phase is finished: do not resume the interrupted work, and every later turn is read-only.

Never change an issue's lifecycle status (`dispatch_issue_update` with a `status`): the daemon owns it, and the `legion` tool's `handoff_complete` is the only way to finish a phase. A status written by a session holding a claim in the issue's own tree is undone. On the root of another tree the daemon is running it is undone too, and that root's architect gets a `status-reasserted` notice naming the session. Only on a child of another tree, or a root still waiting for its slot or lingering, is it taken for a person's move.

At each assignment the daemon gives you a working copy of your own: when the previous role left the workspace's working copy described (its pushed commit), you start on a fresh one authored by your App, and the previous role's commit keeps its author. A completion whose branch head another App authored is refused (`HANDOFF_AUTHOR_MISMATCH`, below).

Push the issue branch yourself, with the plain `jj` of your pane (`git`, like `gh`, acts as your role's App from `GH_CONFIG_DIR`; `<issue>` is your `LEGION_ISSUE`): `cd -- "$LEGION_WORKSPACE" && jj -R "$LEGION_WORKSPACE" bookmark set legion/<issue> -r @- && jj -R "$LEGION_WORKSPACE" git push --bookmark legion/<issue>`. A push whose commits touch only `.legion/` (a handoff-only push) ends its head's commit message with `skip-checks: true` as the last line, so GitHub starts no workflow run for it and the daemon carries the code head's verdict to it. Write that line with trailers off for the one describe, since the pane's jj overlay would otherwise append `Omp-Session:` after it and GitHub honours the trailer only as the last line: `jj -R "$LEGION_WORKSPACE" describe -r @- --config 'templates.commit_trailers=""' -m "$(jj -R "$LEGION_WORKSPACE" log -r @- --no-graph -T description)"$'\n\nskip-checks: true'`. Every other push — code, red tests, `docs/solutions/`, retro's removal of `.legion/<issue>/`, a forward merge, a rewrite — carries no such line and none of GitHub's bracket keywords (`[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]`, `[actions skip]`), which start no workflow wherever they stand. The daemon classifies a push by the paths its commits touch, never by the trailer: a wrong trailer stalls the issue (a trailered code push gets no verdict carried, and a head with no CI is refused at READY) and never passes it. `jj git push` refuses a remote branch that moved because another role pushed: report the refusal to the architect with its output, and never force. The one sanctioned non-fast-forward move is the rewrite of a pushed commit (`skill://legion-worker/references/conflicts-and-rewrites.md`, "Rewriting pushed commits"): once its guard has cleared, `jj -R "$LEGION_WORKSPACE" bookmark set legion/<issue> -r @- --allow-backwards`, then the push, once; a rewrite head never carries the trailer.

A file-backed phase (planning, implementing, testing, reviewing) ends with a committed handoff, `.legion/<issue>/<phase>.json` (`plan`, `implement`, `test` or `review`). Write it with the `write` tool: a JSON object with `schemaVersion: 1`, `phase: "<phase>"`, `issue: "<issue>"`, `completed: "<RFC 3339 UTC time of writing>"`, and the fields your role part spells; nothing stamps the first four for you. Commit it with `jj -R "$LEGION_WORKSPACE" split -m "<phase>: record handoff" .legion/<issue>/<phase>.json`, push (handoff-only, so with the trailer, unless the push also carries code or red tests), then call `handoff_complete`. Push before you complete is a hard rule: the daemon reads `legion/<issue>`'s head on GitHub and refuses, before recording anything, `HANDOFF_BRANCH_MISSING` (the branch is not on GitHub: push, then complete again), `HANDOFF_AUTHOR_MISMATCH` (the head was not authored by your role's App: run `jj new`, then write, commit and push the handoff again), `HANDOFF_FILE_MISSING` (no `.legion/<issue>/<phase>.json` at the head), `HANDOFF_INVALID` (each `<field>: <reason>` named: fix, commit, push, complete again), `HANDOFF_NOT_NEW` (the head is the one you reported last time: nothing was pushed since), and `GITHUB_READ_FAILED` (GitHub's failure, not the head's: complete again). A refusal records nothing, so the corrected call at the same head is applied. Read a predecessor's handoff with the `read` tool from `$LEGION_WORKSPACE/.legion/<issue>/`. Retro, the merger and the production check write no file and complete with `handoff_complete` alone; the commit the daemon records for them is the branch head, or once a squash merge deleted the branch, the pull request's recorded head.
