# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. It submits no merge and changes no merge setting of any pull request, and it reads neither the head you merge, nor its checks, nor the reviewer's approval, nor `.legion/<issue>/` on it: the merge is yours, as the part above says, and so is every read the part above gives you. Do not choose or start the next phase.

The root's design gate holds the merge. While it is closed the daemon starts no merger, and when it closes over a merger already running it sends that merger a message naming the tree and the spec version; the message moves no phase and ends nothing, so the phase stays yours and so does the decision the part above gives you: merge nothing, take a queued pull request back out of the merge queue, and wait for the message that says the gate opened again.

End this phase with the `legion` tool: `op: "handoff_complete"` and a `summary`, the ordinary two sentences for the architect. Your completion records your phase row — the claim, the commit the workspace stands on, and that summary, which the state read shows — and moves nothing: it posts no Dispatch message, publishes nothing and starts no phase. Wherever the steps above say not to complete, do not call `handoff_complete`.

What closes the issue is the merge itself, as GitHub reports it: the daemon reads the merged pull request, from GitHub's webhook or from its own read of the issue, writes `done`, and hands the implementer the production check in its live session. That is the one move out of `merging`, and it comes whether your completion arrived before it or after it. A root whose tree still runs stays in `merging` on its merged pull request until the last other issue of its tree leaves the workflow, and closes then; a child closes at once. An issue that reaches `merging` on a pull request GitHub has already merged closes at once too, so read the pull request before you merge: a merge someone else made is still the merge.

Your completion is refused on the grounds every phase worker's is, each by its code; a refusal records nothing, so the corrected call is applied. `HANDOFF_NOT_CURRENT_PHASE`: the issue is no longer in `merging` — report it to the architect and do not complete again. `HANDOFF_STALE_GENERATION`: your completion names a run the issue has left; push nothing further and tell the architect. `HANDOFF_NO_RUN`: your claim holds no task; tell the architect. `HANDOFF_ALREADY_RECORDED`: the first answer stands. `TREE_LINGERING`: the tree has left the workflow, and nothing of it is worked again. `HANDOFF_NOT_NEW` cannot reach you: `merging` is no file-backed phase, so nothing compares your commit with the one you reported before.
