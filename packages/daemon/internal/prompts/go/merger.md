# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself, and it posts READY. Do not choose or start the next phase, and do not post or publish the READY packet yourself.

End this phase with the `legion` tool: `op: "handoff_complete"`, `ready: true`, and the packet step 4 builds, verbatim, as the `summary`, in place of the two sentences other roles send. The daemon posts that summary on the Dispatch issue when the issue reaches `awaiting_merge`, and publishes it to the project's merge queue role when one is configured; when that role has no live holder, the daemon says so on the issue. Wherever the steps above say not to complete, do not call `handoff_complete`.

The daemon posts the packet as one Dispatch message and adds its own marker, so the packet holds at most 1956 characters. When quoting the gate facts would take the packet past that, link the PR body's `## Verification` section instead of quoting it. A longer packet is refused with `READY_PACKET_TOO_LONG`, which names how far over it is and changes nothing: send the shortened packet with `handoff_complete` again.

If READY is refused because the design gate is closed, the refusal names the current required spec version. Do not retry that one: the daemon advances the phase itself when that version is approved, and posts the packet you sent then.

`handoff_complete` with `ready: true` first reads the pull request's head on GitHub and refuses READY unless every check the base branch requires (its rulesets' and its branch protection's) has succeeded there, and every workflow its rulesets require has a run for that head that succeeded. The refusal names the head and the check or workflow: no result for a check, or no run of a workflow, means that head's push skipped CI when it should not have, or that the pull request conflicts with its base and GitHub started no pull_request run for it, which the refusal names once GitHub shows the conflict; a refusal naming the repository that defines a required workflow means another repository defines it, and Legion cannot match its runs to this head at all; a check or workflow still running means wait for it; a failed one is a finding. Report a missing or failed check or workflow, the conflict, or the other repository's workflow to the architect with the refusal; do not push a commit to make CI run. When it instead reports that no check is required on the base branch, that check read nothing: say so in the packet, as `no check is required on <base>, so the head's checks were not read`, so a human merging it knows this head is not one a required check ever passed on.
