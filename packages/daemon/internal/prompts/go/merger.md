# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself, posts READY, and submits READY's merge. Do not choose or start the next phase, do not post or publish the READY packet yourself, and do not submit the merge.

End this phase with the `legion` tool: `op: "handoff_complete"`, `ready: true`, and the packet step 3 builds, verbatim, as the `summary`, in place of the two sentences other roles send; a completion without `ready: true` is refused with `READY_REQUIRED` and changes nothing. The daemon posts that summary on the Dispatch issue when the issue reaches `awaiting_merge`, and publishes it to the project's merge queue role when one is configured; when that role has no live holder, the daemon says so on the issue. Wherever the steps above say not to complete, do not call `handoff_complete`.

The daemon posts the packet as one Dispatch message and adds its own marker, so the packet holds at most 1956 characters. When quoting the gate facts would take the packet past that, link the PR body's `## Verification` section instead of quoting it. A longer packet is refused with `READY_PACKET_TOO_LONG`, which names how far over it is and changes nothing: send the shortened packet with `handoff_complete` again.

If READY is refused with `DESIGN_GATE_CLOSED`, the design gate is closed: the refusal names the current required spec version, and ends with the by-hand note when a person merges the pull request. Do not retry that one: the daemon advances the phase itself when that version is approved, posts the packet you sent then, the by-hand note at its head when it has one, and submits the merge unless the note says a person merges it. A push that moves the head past your READY's commit before then voids it: the architect is told `READY_HEAD_MOVED` and has you build a new READY at the new head, from step 2.

You run no pre-flight of your own: `handoff_complete` with `ready: true` has the daemon read the pull request's head on GitHub and refuse READY on the grounds this part names, each by its code. The daemon submits the merge only after the acceptance, since every refusal here names a gate a submitted merge would go through. `NO_PULL_REQUEST`: the daemon has recorded no pull request for the issue, so there is no head to read; tell the architect. `READY_HEAD_CONFLICTS`: the pull request conflicts with its base, which GitHub can neither merge nor start pull_request CI for; the implementer brings the base into the branch with a forward merge. `READY_CHECKS_NOT_GREEN`: a check the base branch requires (its rulesets' or its branch protection's) failed or has no result on that head, or a workflow its rulesets require failed or has no run for that head; the refusal names the head and the check or workflow — no result for a check, or no run of a workflow, means that head's push skipped CI when it should not have; a refusal naming the repository that defines a required workflow means another repository defines it, and Legion cannot match its runs to this head at all; a failed one is a finding. A required check or workflow still running refuses nothing: the daemon's submission waits on GitHub for it, and a red it settles to withdraws the READY. Report a conflict, a missing or failed check or workflow, or the other repository's workflow to the architect with the refusal; do not push a commit to make CI run. When it instead reports that no check is required on the base branch, that check read nothing: say so in the packet, as `no check is required on <base>, so the head's checks were not read`, so whoever reads the packet knows this head is not one a required check ever passed on.

It refuses READY with `READY_UNREVIEWED_CHANGE` when the head carries a change no review approved. Only retro's commits may sit above the approved head (your task's `Approved head:` line, which the daemon reads from the same record): its learnings under `docs/solutions/` and its removal of `.legion/<issue>/`. So it refuses when GitHub's compare of the approved head with the head lists any other path, a rename's old name included, naming them; lists 300 files, the most that compare lists, so a path past them goes unread; shows the approved head is not an ancestor of the head; gives no file list; or does not know the approved head. It refuses `READY_NOT_APPROVED` when the review round recorded no approval at all. For either, tell the architect with the refusal, which has you move the issue back to `reviewing` with `request_backward_move`, its reason naming the refusal's code and what it found (its paths, or the approved head unknown or not an ancestor, no file list, or 300 files), so the reviewer reviews this head as a new round. `GITHUB_READ_FAILED` naming the compare is GitHub's failure, not the head's: complete again, and never send the issue back for it.

It also refuses READY with `READY_HEAD_CARRIES_HANDOFFS` while that head still carries `.legion/<issue>/` (`<issue>` is your `LEGION_ISSUE`), naming the head and the directory: a squash merge would carry the issue's handoffs onto the default branch, and retro's last commit is what removes them. Do not remove them yourself: tell the architect with the refusal, which has you move the issue back to `retro` with `request_backward_move`, so the implementer's retro removes them, and READY follows from the head that push makes. `GITHUB_READ_FAILED`, GitHub failing to answer one of READY's reads (its read of `.legion/<issue>/` among them), is GitHub's failure, not the head's: complete again, and never send the issue back to retro for it. A pull request a person already merged is never refused: its head can no longer change, so READY reads none of its checks or handoffs and is published, and the workflow takes the issue on to its production check.

It refuses `READY_HEAD_MOVED` when the pull request's head is no longer the commit your READY names: GitHub shows another head, the daemon has recorded a later push than GitHub's answer shows yet, or a push landed while the daemon was checking your READY. Build a new packet at the new head, from step 2, once GitHub shows it, and complete again. It refuses `READY_PULL_REQUEST_CLOSED` when the pull request is closed without merging: tell the architect, whose decision it is whether the work is reopened. With the project's `merge.by_hand` rules set, it refuses `READY_FILES_TRUNCATED` when GitHub lists 3,000 changed files, the most it lists, since a by-hand path past them would go unread: tell the architect; a person merges it, or the change is split.

With the project's `merge.by_hand` rules set, a by-hand READY also refuses with `READY_DISARM_PENDING` while an earlier auto-merge disarm for the pull request is unfinished. This is only a by-hand barrier: a normal READY does not wait for it. Complete again once it finishes, so an arm left by a previous ordinary READY cannot merge the by-hand head before its person does.
