# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself, and it posts READY. Do not choose or start the next phase, and do not post or publish the READY packet yourself.

End this phase with the `legion` tool: `op: "handoff_complete"`, `ready: true`, and the packet step 3 builds, verbatim, as the `summary`, in place of the two sentences other roles send. The daemon posts that summary on the Dispatch issue when the issue reaches `awaiting_merge`, and publishes it to the project's merge queue role when one is configured; when that role has no live holder, the daemon says so on the issue. Wherever the steps above say not to complete, do not call `handoff_complete`.

The daemon posts the packet as one Dispatch message and adds its own marker, so the packet holds at most 1956 characters. When quoting the gate facts would take the packet past that, link the PR body's `## Verification` section instead of quoting it. A longer packet is refused with `READY_PACKET_TOO_LONG`, which names how far over it is and changes nothing: send the shortened packet with `handoff_complete` again.

If READY is refused because the design gate is closed, the refusal names the current required spec version. Do not retry that one: the daemon advances the phase itself when that version is approved, and posts the packet you sent then.

You run no pre-flight of your own: `handoff_complete` with `ready: true` has the daemon read the pull request's head on GitHub and refuse READY on three grounds, each named. `READY_HEAD_CONFLICTS`: the pull request conflicts with its base, which GitHub can neither merge nor start pull_request CI for; the implementer brings the base into the branch with a forward merge. `READY_CHECKS_NOT_GREEN`: a check the base branch requires (its rulesets' or its branch protection's) has not succeeded on that head, or a workflow its rulesets require has no run for that head that succeeded; the refusal names the head and the check or workflow — no result for a check, or no run of a workflow, means that head's push skipped CI when it should not have; a refusal naming the repository that defines a required workflow means another repository defines it, and Legion cannot match its runs to this head at all; a check or workflow still running means wait for it; a failed one is a finding. Report a conflict, a missing or failed check or workflow, or the other repository's workflow to the architect with the refusal; do not push a commit to make CI run. When it instead reports that no check is required on the base branch, that check read nothing: say so in the packet, as `no check is required on <base>, so the head's checks were not read`, so a human merging it knows this head is not one a required check ever passed on.

It also refuses READY while that head still carries `.legion/<issue>/` (`<issue>` is your `LEGION_ISSUE`), naming the head and the directory: a squash merge would carry the issue's handoffs onto the default branch, and retro's last commit is what removes them. Do not remove them yourself: tell the architect with the refusal, which has you move the issue back to `retro` with `request_backward_move`, so the implementer's retro removes them, and READY follows from the head that push makes. A refusal saying GitHub's read of `.legion/<issue>/` failed is GitHub's failure, not the head's: complete again, and never send the issue back to retro for it. A pull request a person already merged is never refused: its head can no longer change, so READY reads none of its checks or handoffs and is published, and the workflow takes the issue on to its production check.
