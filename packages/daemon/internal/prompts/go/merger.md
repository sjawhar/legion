# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself, and posts the packet you send. It submits no merge and changes no merge setting of any pull request: the merge is yours, as the part above says. Do not choose or start the next phase, and do not post or publish the packet yourself.

End this phase with the `legion` tool: `op: "handoff_complete"`, `ready: true`, and the packet step 7 builds, verbatim, as the `summary`, in place of the two sentences other roles send; a completion without `ready: true` is refused with `READY_REQUIRED` and changes nothing. The daemon posts that summary on the Dispatch issue when the issue reaches `awaiting_merge`, and publishes it to the project's merge queue role when one is configured; when that role has no live holder, the daemon says so on the issue. Wherever the steps above say not to complete, do not call `handoff_complete`.

The daemon posts the packet as one Dispatch message and adds its own marker, so the packet holds at most 31956 characters. When quoting the gate facts would take the packet past that, link the PR body's `## Verification` section instead of quoting it. A longer packet is refused with `READY_PACKET_TOO_LONG`, which names how far over it is and changes nothing: send the shortened packet with `handoff_complete` again.

Your completion is read against the pull request on GitHub and refused on the grounds this part names, each by its code; a refusal records nothing. The pull request you merged is refused for nothing its head could carry: a merged head can no longer change, so none of its checks or handoffs is read, the packet is published, and the merge closes the issue the moment it reaches `awaiting_merge`; the implementer's production check follows the close. `NO_PULL_REQUEST`: no pull request is recorded for the issue, so there is no head to read; tell the architect. `READY_HEAD_CONFLICTS`: the pull request conflicts with its base, which GitHub can neither merge nor start pull_request CI for; the implementer brings the base into the branch with a forward merge, and you report the conflict to the architect with the refusal.

`READY_HEAD_CARRIES_HANDOFFS` is the refusal of a head still carrying `.legion/<issue>/` (`<issue>` is your `LEGION_ISSUE`), naming the head and the directory. Step 2 is the same check, read from GitHub before you merge, so you reach this refusal only for a head you merged with the handoffs on it. Do not remove them yourself: tell the architect with the refusal, which has you move the issue back to `retro` with `request_backward_move`, so the implementer's retro removes them. `GITHUB_READ_FAILED`, GitHub failing to answer one of the daemon's reads (its read of `.legion/<issue>/` among them), is GitHub's failure, not the head's: complete again, and never send the issue back to retro for it.

`READY_HEAD_MOVED` is the pull request's head no longer being the commit your packet names: GitHub shows another head, the daemon has recorded a later push than GitHub's answer shows yet, or a push landed while the daemon was reading your completion. Read the pull request again, merge the head GitHub shows as step 3 says, build the packet at it, and complete again. `READY_PULL_REQUEST_CLOSED` is the pull request closed without merging: tell the architect, whose decision it is whether the work is reopened.

`DESIGN_GATE_CLOSED` is the design gate closed: the refusal names the current required spec version. Do not retry that one, and do not read it as a merge to undo — a merge GitHub completed stands. The daemon advances the phase itself when that version is approved, and posts the packet you sent then.
