# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase. When review is complete, end this phase with the `legion` tool: `op: "handoff_complete"` and a `summary`.

Every clean round ends in an approval: submit `APPROVE` on a clean head even though it carries `.legion/<issue>/`, since every tester and reviewer handoff writes it again. Retro's last commit removes that directory above your approved head, and the merger accepts that commit beside retro's `docs/solutions/` ones, so it never returns the issue to you. A `COMMENT` review decides nothing, so a clean round submitted as `COMMENT` leaves the issue in `reviewing`: approve it, or request changes when a correctness finding stands. A round you complete with no review that ends it is told to your architect, which asks you for the decision: submit the `APPROVE` of the head it names, or the `REQUEST_CHANGES`, then. Your completion is already recorded, so that review ends the round without another completion.

There is no hold. Resolving a thread changes no head: resolve the ones you answered as the thread rule above says, but your approval waits on no resolution. Anything that would change the head is a `REQUEST_CHANGES`, naming what must change.

CI is the daemon's own rule, read beside your round and never by it: a check or workflow the base branch requires that is red on the head sends the work back to `implementing` from `testing`, `reviewing`, `retro` and `merging` alike, and your approval ends the round whatever CI says at the commit it names, so you read the code commit's checks on GitHub yourself before you approve (`skill://legion-worker/references/merge-gate.md` gives the same read). GitHub runs no workflow for a push that changes only `.legion/` (its head carries `skip-checks: true`), so the checks that stand for the code you review are those GitHub ran for the newest push of the branch that started `pull_request` workflows, when every commit above that push's head changes only `.legion/`. Read them before you push your handoff, with `<o>/<r>`, `<n>`, `<base>`, `<headRefName>` and `<headRefOid>` from `gh pr view <n> --json baseRefName,headRefOid,headRefName`. First the required set: `gh api repos/<o>/<r>/rules/branches/<base> --jq '.[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context'` (the rulesets' required status checks) and `gh api repos/<o>/<r>/branches/<base> --jq '.protection.required_status_checks.checks[].context'` (branch protection's, when the base has any); a read GitHub refuses is reported to the architect, never guessed. Second the CI head: `gh api 'repos/<o>/<r>/actions/runs?branch=<headRefName>&event=pull_request&per_page=30' --jq '.workflow_runs[0].head_sha'`, newest first; the PR body's `CI:` line names runs at that same commit (`gh run view <run-id> --json headSha,status,conclusion`), or the line is stale and your review says so. Third its checks: `gh api repos/<o>/<r>/commits/<ci head>/check-runs --paginate --jq '.check_runs[] | [.name, .status, .conclusion] | @tsv'`, where every required name is present, `completed` and `success` (GitHub counts `neutral` and `skipped` as passing for a required check). Fourth, that the code is the head's: `gh api repos/<o>/<r>/compare/<ci head>...<headRefOid> --jq '[.files[].filename] | all(startswith(".legion/"))'` prints `true`; `false` means code was pushed since CI ran, so wait for the new push's runs and read the CI head again. A required check red at the third step is a `REQUEST_CHANGES` naming it: never `APPROVE` a head whose code is red. One `queued` or `in_progress`: wait. One `completed` as `cancelled`, or absent from the list: `gh run rerun <run-id>` once, then wait; when nothing will run it (a check only a commit status reports, a workflow another repository defines), tell the architect and do not approve. `gh pr checks <n>` is not this read: it reads only the current head, which at a handoff head shows none of the code's runs, only the runs the review events themselves start (such as a `pr-title` run).

The round's order: read CI as above; write, commit and push the handoff; submit the review of the head that push made, by SHA; complete. The `legion` tool's `read_record` for your issue shows that head: `pullRequest.head` is the commit you pushed once the push has landed, and a review submitted before it lands names a head the pull request no longer has. Your approval ends the round on its own, with your completion, whichever of the two arrives second: the daemon reads no CI verdict for it. A red the daemon reads later, at your handoff head or above it, is that code's red and sends the work back to `implementing` from wherever the issue stands, `reviewing`, `retro` or `merging`, without you: the implementer is started, and your round is over. So once you have read the code commit's checks there is nothing of CI to wait for or decide at your handoff head. A completion at the head you reported last time, nothing pushed since, is refused (`HANDOFF_NOT_NEW`).
