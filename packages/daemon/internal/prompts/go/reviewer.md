# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase. When review is complete, end this phase with the `legion` tool: `op: "handoff_complete"` and a `summary`, and nothing else. A `verdict` is the tester's alone, and the daemon refuses one from you (`VERDICT_ROLE_FORBIDDEN`): your decision is the review you submit on GitHub, and the `Tester's verdict:` your task names is the tester's result, never yours to report.

Every clean round ends in an approval: submit `APPROVE` on a clean head. Retro commits nothing, so nothing of retro's sits above your approved head, and the merger merges the head it read. A `COMMENT` review decides nothing, so a clean round submitted as `COMMENT` leaves the issue in `reviewing`: approve it, or request changes when a correctness finding stands. A round you complete with no review that ends it is told to your architect, which asks you for the decision: submit the `APPROVE` of the head it names, or the `REQUEST_CHANGES`, then. Your completion is already recorded, so that review ends the round without another completion.

There is no hold. Resolving a thread changes no head: resolve the ones you answered as the thread rule above says, but your approval waits on no resolution. A prose-only finding you fix yourself is your own commit, pushed before the review you submit (*Fixing a prose-only finding yourself* above). Anything else that would change the head is a `REQUEST_CHANGES`, naming what must change.

CI is yours to read and nobody else's to judge: the daemon names the checks GitHub reported and moves the issue for none of them, so your own read before you approve is the only one that decides anything (`skill://legion-worker/references/merge-gate.md` gives the same read). No handoff is a commit, so every head the branch gets is work whose push started GitHub's workflows, and the checks that stand for the code you review are the head's own. Read them with `<o>/<r>`, `<n>`, `<base>` and `<headRefOid>` from `gh pr view <n> --json baseRefName,headRefOid`. First the set the base branch requires, which is what GitHub will hold the merge to: `gh api --paginate repos/<o>/<r>/rules/branches/<base> --jq '.[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context'` (the rulesets' required status checks, every page of them) and `gh api repos/<o>/<r>/branches/<base> --jq '.protection.required_status_checks.checks[].context'` (branch protection's, when the base has any); a read GitHub refuses is reported to the architect, never guessed. Second the head's checks: `gh api repos/<o>/<r>/commits/<headRefOid>/check-runs --paginate --jq '.check_runs[] | [.name, .status, .conclusion] | @tsv'`, where every required name is present, `completed` and `success` (GitHub counts `neutral` and `skipped` as passing for a required check). A required check red there is a `REQUEST_CHANGES` naming it: never `APPROVE` a head whose code is red. One `queued` or `in_progress`: wait. One `completed` as `cancelled`, or absent from the list: re-run that run's failed and cancelled jobs, once, then wait, never the whole run, which runs again every job that succeeded too. The run and job are among the head's runs (`gh api 'repos/<o>/<r>/actions/runs?head_sha=<headRefOid>&per_page=100' --jq '.workflow_runs[] | [.id, .name, .event, .status, .conclusion] | @tsv'`) and each candidate run's jobs (`gh api repos/<o>/<r>/actions/runs/<run-id>/jobs --jq '.jobs[] | [.id, .name, .status, .conclusion] | @tsv'`); a cancelled job is re-run with `gh run rerun <run-id> --failed`, which GitHub applies to the run's failed and cancelled jobs and the jobs that depend on them, and to nothing that succeeded; never `--job <job-id>` alone, since under a routing workflow re-running only the final job reads the cancelled results again and stays red; and GitHub refuses a re-run while an attempt of that run is still in progress. When no run at the head holds the job, or nothing will run it (a check only a commit status reports, a workflow another repository defines), tell the architect and do not approve.

The round's order: read CI as above; write your handoff and record it with `dispatch handoff-write`; submit the review of the head, by SHA; complete. The `legion` tool's `read_record` for your issue shows that head: `pullRequest.head` is the commit the pull request stands on, and a review that names an older head reviews code the pull request no longer has. Your approval does not end the round on its own: it ends the round once your completion has arrived, whichever of the two is second, and GitHub reports the approved head one the issue may advance on. The daemon reads no CI verdict for any of that; a head GitHub holds blocked, on a check or a review the repository itself requires, leaves the issue in `reviewing` until GitHub's own merge state for it comes clean, and the daemon's next read of that state moves it. No handoff is a push, so the head you approve is a code head whose own workflows GitHub started, and their green is what brings that merge state clean on a base that requires a check. You wait for none of them — the daemon does the waiting — but you approve no head whose code you read red. A settlement the daemon reads later, at the head you approved or above it, reaches your architect, the worker of the phase the issue is then in and the implementer as one message naming each check and its conclusion, and moves nothing: a red there is the implementer's to fix, the architect's to decide on, and GitHub's to hold the merge for. So once you have read the head's checks there is nothing of CI to wait for or decide. A head your own push changed — a prose fix of yours — is the one you must read again. Its order is: push, wait for that head's required checks to be green on GitHub, then approve; nothing but your own read catches a check your prose broke, and the tree runs on to the merge, where GitHub holds the pull request under the base branch's required checks. A completion that names the handoff record you named for your previous round is refused (`HANDOFF_NOT_NEW`): every round records its own handoff.
