# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase. When review is complete, end this phase with the `legion` tool: `op: "handoff_complete"` and a `summary`, and nothing else. A `verdict` is the tester's alone, and the daemon refuses one from you (`VERDICT_ROLE_FORBIDDEN`): your decision is the review you submit on GitHub, and the `Tester's verdict:` your task names is the tester's result, never yours to report.

Every clean round ends in an approval: submit `APPROVE` on a clean head even though it carries `.legion/<issue>/`, since every tester and reviewer handoff writes it again. Retro's last commit removes that directory above your approved head, beside retro's `docs/solutions/` ones, and nothing returns the issue to you for either: the approval stands and the merger merges the head retro leaves. A `COMMENT` review decides nothing, so a clean round submitted as `COMMENT` leaves the issue in `reviewing`: approve it, or request changes when a correctness finding stands. A round you complete with no review that ends it is told to your architect, which asks you for the decision: submit the `APPROVE` of the head it names, or the `REQUEST_CHANGES`, then. Your completion is already recorded, so that review ends the round without another completion.

There is no hold. Resolving a thread changes no head: resolve the ones you answered as the thread rule above says, but your approval waits on no resolution. A prose-only finding you fix yourself is your own commit, pushed before the review you submit (*Fixing a prose-only finding yourself* above). Anything else that would change the head is a `REQUEST_CHANGES`, naming what must change.

CI is yours to read and nobody else's to judge: the daemon names the checks GitHub reported and moves the issue for none of them, so your own read before you approve is the only one that decides anything (`skill://legion-worker/references/merge-gate.md` gives the same read). GitHub runs no workflow for a push whose head's commit message carries `skip-checks: true`, which every handoff-only push before retro does (retro's push carries no such line, so its own head does get GitHub's workflow runs), so the checks that stand for the code you review are those GitHub ran for the newest push of the branch that started `pull_request` workflows, when every commit above that push's head changes only `.legion/<issue>/` (`<issue>` is your `LEGION_ISSUE`; another issue's `.legion/` is code, and a head carrying it is not one you may treat as handoffs-only). Read them before you push your handoff, with `<o>/<r>`, `<n>`, `<base>`, `<headRefName>` and `<headRefOid>` from `gh pr view <n> --json baseRefName,headRefOid,headRefName`. First the set the base branch requires, which is what GitHub will hold the merge to: `gh api --paginate repos/<o>/<r>/rules/branches/<base> --jq '.[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context'` (the rulesets' required status checks, every page of them) and `gh api repos/<o>/<r>/branches/<base> --jq '.protection.required_status_checks.checks[].context'` (branch protection's, when the base has any); a read GitHub refuses is reported to the architect, never guessed. Second the CI head: `gh api 'repos/<o>/<r>/actions/runs?branch=<headRefName>&event=pull_request&per_page=30' --jq '.workflow_runs[0].head_sha'`, newest first. Third its checks: `gh api repos/<o>/<r>/commits/<ci head>/check-runs --paginate --jq '.check_runs[] | [.name, .status, .conclusion] | @tsv'`, where every required name is present, `completed` and `success` (GitHub counts `neutral` and `skipped` as passing for a required check). Fourth, that the code is the head's: `gh api repos/<o>/<r>/compare/<ci head>...<headRefOid> --jq '{handoffsOnly: ([.files[] | .filename, (.previous_filename // empty)] | all(startswith(".legion/<issue>/"))), files: (.files | length)}'` prints `handoffsOnly` `true`; `false` means code was pushed since CI ran, so wait for the new push's runs and read the CI head again. GitHub's compare lists at most 300 files for the whole comparison, so `files` at 300 is a comparison GitHub cut at its cap and `handoffsOnly` decides nothing: tell the architect and do not approve. A required check red at the third step is a `REQUEST_CHANGES` naming it: never `APPROVE` a head whose code is red. One `queued` or `in_progress`: wait. One `completed` as `cancelled`, or absent from the list: re-run that run's failed and cancelled jobs, once, then wait, never the whole run, which runs again every job that succeeded too. The run and job are among the CI head's runs (`gh api 'repos/<o>/<r>/actions/runs?head_sha=<ci head>&per_page=100' --jq '.workflow_runs[] | [.id, .name, .event, .status, .conclusion] | @tsv'`) and each candidate run's jobs (`gh api repos/<o>/<r>/actions/runs/<run-id>/jobs --jq '.jobs[] | [.id, .name, .status, .conclusion] | @tsv'`); a cancelled job is re-run with `gh run rerun <run-id> --failed`, which GitHub applies to the run's failed and cancelled jobs and the jobs that depend on them, and to nothing that succeeded; never `--job <job-id>` alone, since under a routing workflow re-running only the final job reads the cancelled results again and stays red; and GitHub refuses a re-run while an attempt of that run is still in progress. When no run at the CI head holds the job, or nothing will run it (a check only a commit status reports, a workflow another repository defines), tell the architect and do not approve. `gh pr checks <n>` is not this read: it reads only the current head, which at a handoff head shows none of the code's runs, only the runs the review events themselves start (such as a `pr-title` run).

The round's order: read CI as above; write, commit and push the handoff; submit the review of the head that push made, by SHA; complete. The `legion` tool's `read_record` for your issue shows that head: `pullRequest.head` is the commit you pushed once the push has landed, and a review submitted before it lands names a head the pull request no longer has. Your approval ends the round on its own, with your completion, whichever of the two arrives second: the daemon reads no CI verdict for it. A settlement the daemon reads later, at your handoff head or above it, reaches your architect, the worker of the phase the issue is then in and the implementer as one message naming each check and its conclusion, and moves nothing: a red there is the implementer's to fix, the architect's to decide on, and GitHub's to hold the merge for. So once you have read the code commit's checks there is nothing of CI to wait for or decide at a handoff-only head. A head your own push changed beyond `.legion/<issue>/` — a prose fix of yours — is the one you must read again. Its order is: push, wait for that head's required checks to be green on GitHub, then approve; nothing but your own read catches a check your prose broke, and the tree runs on to the merge, where GitHub holds the pull request under the base branch's required checks. A completion at the head you reported last time, nothing pushed since, is refused (`HANDOFF_NOT_NEW`).
