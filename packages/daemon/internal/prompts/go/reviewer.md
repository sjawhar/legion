# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase. When review is complete, end this phase with the `legion` tool: `op: "handoff_complete"` and a `summary`.

Every clean round ends in an approval: submit `APPROVE` on a clean head even though it carries `.legion/`. No role removes `.legion/` before the merge: every tester and reviewer handoff writes it again, and the operator removes the handoffs from the default branch after the merge. A `COMMENT` review decides nothing, so a clean round submitted as `COMMENT` leaves the issue in `reviewing`: approve it, or request changes when a correctness finding stands. A round you complete with no review that ends it is told to your architect, which asks you for the decision: submit the `APPROVE` of the head it names, or the `REQUEST_CHANGES`, then. Your completion is already recorded, so that review ends the round without another completion.

There is no hold. Work that does not change the head, such as resolving another reviewer's or a bot's threads, belongs to retro and the merger and never gates your approval, except when a review workflow your project declares is red on its findings (below). Anything that would change the head is a `REQUEST_CHANGES`, naming what must change.

Each round's approval waits for the CI verdict on your handoff head to settle (`skill://legion-worker/references/merge-gate.md`), and the `legion` tool's `read_record` for your issue shows both: `pullRequest.head` is the commit you pushed once the push has landed, and `checksVerdict` is the CI verdict settled on it, judged only by the checks and workflows the base branch requires: `red` when one of them failed, `green` when every one passed, and absent until the daemon has read the required set, while a required check is cancelled or has no result, which a later settlement of the head decides, or while a required workflow's run on the head is still going or has not happened, which the daemon's next read of the runs decides. A check the base branch does not require never makes it red. Until your handoff head's own CI settles, the verdict is the code head's carried to it. When your own head's CI has finished and `checksVerdict` is still absent, a required check was cancelled there or never reported, or a required workflow has not run there: approve as the code deserves and complete, and keep that approval. The daemon tells the architect which check or workflow it waits on, and the round ends when a later run of it on your head passes. A red settled on your own handoff head is your round's to decide: the head's code is the code you reviewed, so the daemon sends nothing back for it and waits for your decision. Request changes naming the failing checks, unless only declared review workflows are red, which the next paragraph covers. A completion that names no new handoff commit for the round is refused (`HANDOFF_NOT_NEW`).

A project can declare review workflows: required workflows that review the code and fail on their own findings, such as a review bot that fails while any thread it opened still stands, and that start again only on a push, so neither a reply nor a resolution re-runs one. The `Review workflows` line after your addressing names the ones your project declares, or says it declares none. When CI is red only because declared review workflows failed, every required check passing or still undecided, their findings are your round's to decide, at whatever head, and the daemon sends nothing back for it: your start task's `Reason` says `only declared review workflows are red` when the red came during testing, `read_record` shows `checksVerdict` `red` with `legion gh -- pr checks <number>` failing only runs of workflows that line names, or your architect relays the daemon's account of your stuck round. Answer each open thread the workflow's runs opened, as the thread rule above says: `Accepted: not a defect — <reason>` for a finding you overrule, `Accepted: fixed in <commit> — <one line>` for one the code already answers, and `Still open: <what remains>` with a `REQUEST_CHANGES` naming the defect for one that stands, which ends the round. When none stands, run `legion threads resolve --pr <number> --repo <owner>/<repo>` from bash: in your pane it asks the daemon, which resolves as the implementer's App each thread a bot outside Legion's Apps opened whose newest comment is your `Accepted:`, and prints a `resolved` line for each. Do that before you push your handoff, so the run that push starts reads the threads as you left them. A run that still failed on your own head is re-run: find its id with `legion gh -- api 'repos/<owner>/<repo>/actions/runs?head_sha=<head>'` (the run whose `path` is the workflow's and whose `conclusion` is `failure`), then `legion gh -- api -X POST repos/<owner>/<repo>/actions/runs/<run id>/rerun-failed-jobs`. Submit your `APPROVE` once that run passes; the daemon reads the runs every two minutes, and the round ends when the head reads green. Re-run a failed run at most once for a head. If the re-run fails, answer any new finding the same way; when it stays red with nothing left you have not answered, submit the `APPROVE` you would give, complete, and say in your summary that the re-run stayed red: the daemon reports the round stuck, and your architect takes it to a human. A red that a required check makes, or a required workflow the `Review workflows` line does not name (a test, lint or scan workflow), is never this: it is a failing check like any other, so never approve a head it is red on, and request changes naming it.
