# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase. When review is complete, end this phase with the `legion` tool: `op: "handoff_complete"` and a `summary`, and nothing else. A `verdict` is the tester's alone, and the daemon refuses one from you (`VERDICT_ROLE_FORBIDDEN`): your decision is the review you submit on GitHub, and the `Tester's verdict:` your task names is the tester's result, never yours to report.

Every clean round ends in an approval: submit `APPROVE` on a clean head. Where that approval leaves text threads open, the implementer's one commit of the text fixes follows it, and your approval of the head that commit made is the one READY reads, so nothing of anyone's sits above the head you approved last. The daemon refuses nothing for a commit above the approved head: it compares the two heads nowhere, and the repository's branch rules decide the merge, which is the owner's ruling (dispatch://INFRA-714/ask/beea7685). A `COMMENT` review decides nothing, so a clean round submitted as `COMMENT` leaves the issue in `reviewing`: approve it, or request changes when a behavioural finding stands, one whose closing changes code that runs. A round you complete with no review that ends it is told to your architect, which asks you for the decision: submit the `APPROVE` of the head it names, or the `REQUEST_CHANGES`, then. Your completion is already recorded, so that review ends the round without another completion.

There is no hold. Resolving a thread changes no head: resolve the ones you answered as the thread rule above says, but your approval waits on no resolution. A reviewer submits `REQUEST_CHANGES` only when a behavioural finding stands — one whose closing changes code that runs — and otherwise approves the head it read, named by SHA, leaving every text finding as the inline review thread it already writes. The request names what must change. You resolve each thread you opened once you have read the fix that closed it, one call per thread, and then approve the head the fix landed on, by SHA, reading that head's checks as you read any head's; a thread the fix cannot close is a message to the architect, who moves the issue back to `implementing`. That approval of the fix's head ends no phase of yours and needs no completion, since the round that approved the head below it is already complete.

CI is the daemon's own rule, read beside your round and never by it: a check or workflow the base branch requires that is red on the head sends the work back to `implementing` from `testing`, `reviewing`, `retro` and `merging` alike, and your approval ends the round whatever CI says at the commit it names, so you read the head's checks on GitHub yourself before you approve (`skill://legion-worker/references/merge-gate.md` gives the same read). No handoff is a commit, so every head the branch gets is work whose push started GitHub's workflows, and the checks that stand for the code you review are the head's own. Read them with `<o>/<r>`, `<n>`, `<base>` and `<headRefOid>` from `gh pr view <n> --json baseRefName,headRefOid`. First the required set: `gh api --paginate repos/<o>/<r>/rules/branches/<base> --jq '.[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context'` (the rulesets' required status checks, every page of them) and `gh api repos/<o>/<r>/branches/<base> --jq '.protection.required_status_checks.checks[].context'` (branch protection's, when the base has any); a read GitHub refuses is reported to the architect, never guessed. Second the head's checks: `gh api repos/<o>/<r>/commits/<headRefOid>/check-runs --paginate --jq '.check_runs[] | [.name, .status, .conclusion] | @tsv'`, where every required name is present, `completed` and `success` (GitHub counts `neutral` and `skipped` as passing for a required check). A required check red there is a `REQUEST_CHANGES` naming it: never `APPROVE` a head whose code is red. One `queued` or `in_progress`: wait. One `completed` as `cancelled`, or absent from the list: re-run that run's failed and cancelled jobs, once, then wait, never the whole run, which runs again every job that succeeded too. The run and job are among the head's runs (`gh api 'repos/<o>/<r>/actions/runs?head_sha=<headRefOid>&per_page=100' --jq '.workflow_runs[] | [.id, .name, .event, .status, .conclusion] | @tsv'`) and each candidate run's jobs (`gh api repos/<o>/<r>/actions/runs/<run-id>/jobs --jq '.jobs[] | [.id, .name, .status, .conclusion] | @tsv'`); a cancelled job is re-run with `gh run rerun <run-id> --failed`, which GitHub applies to the run's failed and cancelled jobs and the jobs that depend on them, and to nothing that succeeded; never `--job <job-id>` alone, since under a routing workflow re-running only the final job reads the cancelled results again and stays red; and GitHub refuses a re-run while an attempt of that run is still in progress. When no run at the head holds the job, or nothing will run it (a check only a commit status reports, a workflow another repository defines), tell the architect and do not approve.

The round's order: read CI as above; write your handoff and record it with `dispatch handoff-write`; submit the review of the head, by SHA; complete. The `legion` tool's `read_record` for your issue shows that head: `pullRequest.head` is the commit the pull request stands on, and a review that names an older head reviews code the pull request no longer has. Your approval ends the round on its own, with your completion, whichever of the two arrives second: the daemon reads no CI verdict for it. A red the daemon reads later, at the head you approved or above it, is that code's red and sends the work back to `implementing` from wherever the issue stands, `reviewing`, `retro` or `merging`, without you: the implementer is started, and your round is over. So once you have read the head's checks there is nothing of CI to wait for or decide. A completion that names the handoff record you named for your previous round is refused (`HANDOFF_NOT_NEW`): every round records its own handoff.
