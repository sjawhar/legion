The cross-package automation no single package owns: the router `ci.yaml`, the pull-request and merge-queue gate that selects its jobs by the paths a change touched, with the pull-request and merge-queue docs build and the pull-request worker-image build among them and `ci-ok` condensing their results into one check, and whose Go caches `ci-caches.yaml` fills on a push to main; the docs site's build (`docs-site.yaml`), the one reusable workflow that holds its steps, which `ci.yaml`'s `docs` job calls for a pull request and a merge group and `docs-pages.yaml`'s `build` job calls for a push to main the router's docs filter selects, one at a time and, of those waiting, the newest alone, before its `deploy` job publishes the build to GitHub Pages; the PR-title check (`pr-title.yaml`); the bypass check (`main-bypass-check.yaml`), which dispatches a full `ci.yaml` run for a commit that reached main without a passing merge-group `ci-ok`, and the dequeue watch (`dequeued.yaml`), which stops the run of a group whose pull request left the queue; the code scan (`codeql.yaml`); the release workflows (`release.yaml` for the `legion` binary and the npm plugins, `release-envoy-listener.yaml` for the Envoy listener, `release-envoy-infra.yaml` for the `envoy-infra` Pulumi plugin); and the worker-image build (`worker-image.yaml`) that publishes `ghcr.io/sjawhar/legion-worker` by digest for the Kubernetes runtime to pin. The changelog fold (`changelog-fold.yaml`) runs after each release, once a day and by hand, and folds each package's changelog fragments into its `CHANGELOG.md` on main. Every container image a CI job fetches is a copy in one package this repository publishes, `ghcr.io/sjawhar/legion/ci`, named by digest: `.github/ci-images.yaml` holds one row per image, and `ci.yaml`'s `ci-images` job publishes the rows the package does not hold yet with the `crane` that `.github/actions/install-crane` installs, which keeps the digest. That job is the one copy path, on every event the router runs. `.github/scripts` holds the checks those workflows run and the version-bump and release-push scripts they call, with their shell tests. `check-ci-images.sh` is the gate on the images, and it takes one mode: its `tree` mode, which `lint` runs on every change, refuses a reference in CI's reach that names anything but a digest `.github/ci-images.yaml` holds, and names each file outside CI's reach that keeps the mirror CI read before, with the one ground that admits it; its `package` mode, which the `ci-images` job runs after the copy, reads ghcr.io and refuses a row the package does not hold. Every workflow's Postgres service is that package's copy of the pgvector-on-PostgreSQL-18 image Envoy's `internal/testpg` pins, by the same digest, and `envoy-go` prints the server's version and pgvector's before its tests.

Every path that depends on the repository's own owner and name is derived from `$GITHUB_REPOSITORY` by one script, `.github/scripts/repo-paths.sh`, which answers `sjawhar/legion` off a runner, refuses anything that is not `<owner>/<name>`, and is tested by `.github/scripts/repo-paths.test.sh` in `ci.yaml`'s `test` job: the worker image `worker-image.yaml` pushes (`worker_image`), the Envoy image `release-envoy-listener.yaml` pushes, tags, attests and reads `latest` back from (`envoy_image`), the release download URL `release-envoy-infra.yaml` stamps into the `envoy-infra` plugin and asserts on in its schema (`plugin_download_url`), the `repository.url` `release.yaml`'s `pi_envoy_build` and `pi_legion_build` write into each plugin manifest before `bun pm pack` and read back out of the packed tarball, since npm refuses a publish with provenance whose url is not the publishing repository's (`repository_url`), and the site, base and edit links the docs build takes through the ten-line adapter `docs/site/repo-paths.ts` that `astro.config.mjs` and `generators/legion-skills.ts` import (`docs_site`, `docs_base`, `docs_edit_base`). A job holding a credential runs the script not at all: `.github/scripts/check-release-credentials.sh` refuses a `scripts/` path in a job holding `contents: write`, `packages: write`, `id-token: write`, `attestations: write` or the deploy key, so such a job reads the value from the output of an upstream job that holds `contents: read` alone — `release-envoy-listener.yaml`'s `targets` job, whose `envoy_image` output `docker`, `image_index`, `attest` and `release_publish` each name in their own `needs`, since `needs` carries no transitive output, and `worker-image.yaml`'s `build` job, whose `image` output its `attest` job takes, or, when that build job is skipped, the `image` input `release.yaml`'s `worker_image_attest` passes from the build-only call's output.
