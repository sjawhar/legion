The cross-package automation no single package owns: the router `ci.yaml`, the pull-request and main gate that selects its jobs by the paths a change touched, with the pull-request and merge-queue docs build and the pull-request worker-image build among them and `ci-ok` condensing their results into one check; the docs site's build (`docs-site.yaml`), the one reusable workflow that holds its steps, which `ci.yaml`'s `docs` job calls for a pull request and a merge group and `docs-pages.yaml`'s `build` job calls for each push to main the router's docs filter selects, one at a time in push order, before its `deploy` job publishes the build to GitHub Pages; the PR-title check (`pr-title.yaml`); the release workflows (`release.yaml` for the `legion` binary and the npm plugins, `release-envoy-listener.yaml` for the Envoy listener, `release-envoy-infra.yaml` for the `envoy-infra` Pulumi plugin); and the worker-image build (`worker-image.yaml`) that publishes `ghcr.io/sjawhar/legion-worker` by digest for the Kubernetes runtime to pin. The changelog fold (`changelog-fold.yaml`) runs after each release, once a day and by hand, and folds each package's changelog fragments into its `CHANGELOG.md` on main. Every container image a CI job fetches is a copy in one package this repository publishes, `ghcr.io/sjawhar/legion/ci`, named by digest: `.github/ci-images.yaml` holds one row per image, and `ci.yaml`'s `ci-images` job publishes the rows the package does not hold yet with the `crane` that `.github/actions/install-crane` installs, which keeps the digest. That job is the one copy path, on every event the router runs. `.github/scripts` holds the checks those workflows run and the version-bump and release-push scripts they call, with their shell tests. `check-ci-images.sh` is the gate on the images, and it takes one mode: its `tree` mode, which `lint` runs on every change, refuses a reference in CI's reach that names anything but a digest `.github/ci-images.yaml` holds, and names each file outside CI's reach that keeps the mirror CI read before, with the one ground that admits it; its `package` mode, which the `ci-images` job runs after the copy, reads ghcr.io and refuses a row the package does not hold. Every workflow's Postgres service is that package's copy of the pgvector-on-PostgreSQL-18 image Envoy's `internal/testpg` pins, by the same digest, and `envoy-go` prints the server's version and pgvector's before its tests.
