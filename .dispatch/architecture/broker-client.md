The TypeScript half of this repository's one client of the secrets broker's RFC 8693 token exchange (`@legion/broker-client`): a machine trades the platform identity it already holds for a DPoP-bound access token, which Dispatch and the Envoy listener read back at the broker's introspection route. The Go half is `packages/envoy/internal/brokerclient`, and the two are held to one wire by the corpus in that package's `testdata/wire.json`, which both suites replay; each asserts set equality, not containment, over the form posted, the proof's header and claim set and the fields read out of the answer, so a field either client sends or reads without an entry in that file fails its own test and a field added to that file fails the client that does not send it yet.

One module per thing, no barrel: `src/wire.ts` holds the names the exchange is spoken in (the Go side's `internal/broker/oauthwire`), `src/source.ts` the identity interface, `src/projected-token.ts` a pod's projected Kubernetes service-account token read from its file at every trade (the kubelet rewrites it in place), `src/metadata-identity.ts` a Compute Engine machine's Google identity token asked for with `format=full`, `src/dpop.ts` the proof signer, `src/token-client.ts` the exchange itself, and `src/environment.ts` the variables a deployment writes (`AGENT_SECRETS_URL`, `AGENT_SECRETS_MACHINE_IDENTITY` of `kubernetes` or `metadata`, `AGENT_SECRETS_MACHINE_TOKEN_FILE`, `AGENT_SECRETS_MACHINE_AUDIENCE`, `AGENT_SECRETS_SESSION`), the same names the Go client reads. A machine that federates through a workload identity pool trades through the Go client, which `agent-secrets` runs; this one refuses `pool` naming that command.

`openid-client` makes the exchange request and validates the answer, and `jose` signs every proof: `typ: dpop+jwt`, `alg: ES256`, the public JWK in the header, and `jti`, `htm`, `htu` and `iat` in the claims, with `nonce` only after the broker has sent one (the token endpoint's `use_dpop_nonce` retry lives here) and `ath` only on a request that presents an access token. The key is made inside the process, one per client (`brokerTokenClient`), and is non-extractable, so only its public half can ever reach the wire. `token_type` is the one member read from the answer's own body rather than from the library's result, because the library lowercases it (RFC 6749 Section 7.1) while the corpus names the spelling the broker wrote.

The metadata reader uses `node:http` with an agent of its own and never `fetch`: the metadata server's address is link-local, Bun's `fetch` honours `$HTTP_PROXY`, a Node host can install a proxying global dispatcher, and Node 24 proxies `node:http` through its global agent when `NODE_USE_ENV_PROXY` is set — any of which would hand whatever a proxy variable names this machine's identity token, fetched afresh before every renewal. The Go reader's bare transport exists for the same reason.

The grant issues no refresh token, so a renewal is a fresh subject token traded again: `token()` answers the token in hand until it is within five minutes of lapsing, trades inside the call after that with nothing of the caller's restarted, single-flights concurrent callers, keeps answering a live token while the broker is merely unreachable, and throws a plain error — `BrokerRefusedError` for an identity the broker refused, which no retry cures — rather than letting a caller write with no identity.

`packages/envoy-client`'s `src/broker-credential.ts` is its one caller: it makes one client and one key for each session a process acts as (`CLIENTS`, dropped by `forgetBrokerSession` when the host leaves that session), traded under that session's own name, which both that session's Dispatch client and its listener client present as `Authorization: DPoP <token>` with a proof of their own for each request.
