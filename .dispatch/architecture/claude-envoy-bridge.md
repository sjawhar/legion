The Claude Code plugin that delivers Envoy and Dispatch traffic into Claude Code sessions and carries the session's own conversation to Dispatch's live view. Its `dist/` bundles the envoy-client `dispatch` command, so a change there, such as `dispatch search` printing each ask hit's answer state, reaches Claude Code only with `dist/` rebuilt. It takes the session's messages from the listener's relay of the session's own durable consumer, asked for at every registration and acknowledged once the plugin has put the message into the session's conversation: the row the plugin's mod added in a terminal session, or the user message Claude Code re-emitted in a Legion pane (`packages/envoy/AGENTS.md`, "Session consumers"). It reaches the session through a Claude Code mod of its own (`hooks/mod.ts`) over a Unix socket, which is also where the live view's frames and a person's model and thinking picks go, and it advertises the delivery modes that link can carry. It dials NATS with the client's shared connection options (a ping every 10 s, so a frozen path is left within 30 s), runs the core path's catch-up of missed messages (`POST /v1/replay`) only on a listener that answers `core`, and registers as `plugin` `@sjawhar/claude-envoy` with the install's commit (the version directory Claude Code's plugin cache holds it under) as `plugin_version`, or `source` outside the plugin cache. Its session hooks add context at every session start, resume, compaction and subagent start: the session's open asks, the `dispatch-first` skill, and what people wrote to the session in the last 72 hours, read from Dispatch's `GET /api/v1/agents/{session_id}/answers` through `@legion/envoy-client/session-answers` within 800 ms of the hook's start, a subagent reading its parent's. A test runs the Claude Code release `.claude-code-pin` pins against a stand-in model and Dispatch.

The channel-server process mints one client instance id when it starts and sends it on every registration and on each deregistration, so a `/clear` handoff removes the old session's registry entry only while that entry is still this process's. Its role claims are soft and name the session they continue, and the listener grants one only when that predecessor has no live entry, when its live entry carries this process's instance id, or when either side carries no instance id. A refusal that names the predecessor itself keeps that session's role record, because the record belongs to the live holder. A refusal naming any other session removes it.

Its bundles inline `@legion/broker-client` with the rest of the workspace, so the bundled `dispatch` command, `envoy-send` and the channel server all take a Dispatch or listener credential from the secrets broker when no bearer is configured; `scripts/build-inputs.txt` lists that package, since a change there changes this build.
