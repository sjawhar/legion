The Claude Code channel plugin that delivers Envoy and Dispatch traffic into Claude Code sessions. Its `dist/` bundles the envoy-client `dispatch` command, so a change there, such as `dispatch search` printing each ask hit's answer state, reaches Claude Code only with `dist/` rebuilt. It takes the session's messages from the listener's relay of the session's own durable consumer, asked for at every registration and acknowledged once Claude Code re-emitted the message (`packages/envoy/AGENTS.md`, "Session consumers"). It dials NATS with the client's shared connection options (a ping every 10 s, so a frozen path is left within 30 s), runs the core path's catch-up of missed messages (`POST /v1/replay`) only on a listener that answers `core`, and registers as `plugin` `@sjawhar/claude-envoy` with the install's commit (the version directory Claude Code's plugin cache holds it under) as `plugin_version`, or `source` outside the plugin cache. Its session hooks add context at every session start, resume, compaction and subagent start: the session's open asks, the `dispatch-first` skill, and what people wrote to the session in the last 72 hours, read from Dispatch's `GET /api/v1/agents/{session_id}/answers` through `@legion/envoy-client/session-answers` within 800 ms of the hook's start, a subagent reading its parent's. A test runs the Claude Code release `.claude-code-pin` pins against a stand-in model and Dispatch.

The channel-server process mints one client instance id when it starts and sends it on every registration, on every claim and release, and on each deregistration, so a `/clear` handoff removes the old session's registry entry only while that entry is still this process's. Its role claims are soft and name the session they continue, and the listener grants one only when that predecessor has no live entry, when its live entry carries this process's instance id, or when either side carries no instance id. A claim of a role already held under this session's own id is decided on the standing claim: granted to the process that claim names, granted once nobody renewed it inside the live window, and otherwise refused. The role record on disk names the process that wrote it, so a record another process wrote is pressed only while this process holds no role, and the heartbeat's re-assertion confirms the role only when the lookup names this session and this process and the claim carries no hand-back mark. Those two readings are the client contract's own rather than this bridge's: `mayActOnRoleRecord` and `roleHeldBy` in `@legion/envoy-client/transport`, which `packages/pi-envoy` calls too and which read an empty instance id as none, since the lookup leaves `client_instance_id` out where the claim names no process. A lookup that answers `handed_back` is a role this process does not hold, so a hold an older client's hand-back marked is claimed again on the next heartbeat and the grant, a fresh record, clears the mark. A refusal that names the predecessor itself keeps that session's role record, because the record belongs to the live holder, and a refusal naming this session under another process keeps the role, refreshes the record and asks again on the next heartbeat. A refusal naming any other session ends the role and removes the record. This process hands no role lane back — it releases a role only by deregistering the whole session — so the release the listener may have to fail against its own holder's renewal is not a path it takes, and the hand-back mark an older client's release leaves is not one it writes either; the registration that renews its claims is what keeps them, whatever topics that registration carries, and only a claim the listener has marked handed back goes unrenewed.

Its bundles inline `@legion/broker-client` with the rest of the workspace, so the bundled `dispatch` command, `envoy-send` and the channel server all take a Dispatch or listener credential from the secrets broker when no bearer is configured; `scripts/build-inputs.txt` lists that package, since a change there changes this build.
