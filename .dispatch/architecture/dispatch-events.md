The append-only event log every Dispatch write lands in. An append (`Broker.QueueAppend`) puts its statements on the write phase's batch (`store.WriteBatch`): the event owner's advisory lock (`store.LockOwner`, which returns at once when the transaction took it in its read phase), then the owner's row `for no key update`, which takes the transaction id (`pg_current_xact_id`) in the same statement and is the write-phase statement that gives a transaction appending its first event its transaction id before the insert takes an id, then one insert that takes the next sequence from the owner row and, in the same statement, advances the row's `last_seq` (and an issue's `updated_at`) to the row it inserted. It takes no other lock (an ownerless, session-addressed event takes neither, only its transaction id, in a statement of its own queued before the insert), so one owner's events commit in id order while two owners' writes never wait for each other and can commit out of id order. An `ask.opened` payload records its own event id through the events id sequence's `currval` (`store.LatestEventID`), the same expression a stamp of the source's references uses right after its event. So nothing is read back in Go between the statements, and the whole append goes to Postgres with the rest of the write phase in one round trip; the appended event (id, sequence, time, project) reaches the caller through a callback once the batch has run. `Broker.Append` is the same statements sent at once as a batch of their own. `LockOwners` takes the locks of several owners up front, sorted and deduplicated by lock key (`store.LockOwners`), so two transactions never take shared owners in opposite orders. An append a document ledger queues runs in the transaction's write phase, in the order the transaction made it. The broker writes through the transaction its caller hands it and imports `dispatch-store` for the owner lock and the write batch. `internal/dispatch/envoy` is the small outbound client that calls the Envoy listener's API; it exists only to carry broker-produced events onward, so the two are one component.

Since a lower id can still be open after a higher one has committed, every reader that pages the log by a global id cursor (the SSE relay and its `Last-Event-ID` resume, the delivery hub, `GET /api/v1/references?since=`) reads only up to the safe horizon of the server's one `events.Horizon`, and delivers in id order. An observation is one statement in a transaction of its own that reads A, the newest id its snapshot sees, that snapshot's xmin, its xmax and whether its in-progress list is empty, and X, its own transaction id, assigned after that snapshot. A later observation whose snapshot xmin is above X proves that no transaction below X still runs, so every id at or below A is final; the horizon is the A of the newest observation proven so. The proof rests on two writer invariants: an append takes its transaction id (`pg_current_xact_id`) before the insert draws the event id, and `events_id_seq` keeps `CACHE 1`, so a transaction holding an id at or below A holds a transaction id below X. An observation's own snapshot proves it when the snapshot lists nothing in progress and its xmax is X: every id below that xmax had ended when the snapshot was taken, and xmax = X leaves no id between, so the horizon reaches A in that one observation. Both conditions are needed: a transaction whose id is at or above the snapshot's xmax is not listed in it as in progress, and the observer's X is then above that xmax.

Snapshots are instance-wide, so a transaction that holds a transaction id anywhere on the Postgres instance delays events to live readers until it ends, and it never blocks a writer. An event waits for every transaction holding an id when the first observation that sees the event takes its own transaction id, which is after the event's commit (the live stream's relay reads 25 ms after the event's notification): so it also waits for transactions that began after it committed, and for id holders that write no event, such as a `SELECT ... FOR UPDATE` or another database's job on the instance. A read whose own observation proved itself publishes in that same read (`Horizon.Gap` reports `GapNone`), so a read taken while nothing on the instance holds a transaction id costs one observation, not two; otherwise a reader (the relay, the delivery hub, `Horizon.Await`) whose read leaves only its own observation unproven (`GapUnproven`) observes again at once, which proves it unless an older transaction id still runs; a gap an older transaction holds (`GapHeld`) is read again on the next commit notification, without the 25 ms window, or after a fallback of 10 ms doubling to 250 ms for a holder that ends without notifying, which runs only while such a gap is open, so an idle process observes nothing. A Dispatch write transaction holds its id only in its write phase, one pipelined batch of statements before its commit, so its document work and write advice never delay a live event. A pending observation older than five seconds logs the oldest holder. A live event stream that resumes from an id opens at once and heartbeats while the horizon is held, a cold one opens once its subscription is in place, and shutdown ends a stream still waiting. A cold stream starts at the relay's published cursor. The relay's first cursor in a process is the log's newest id when the relay starts, or the last event below the lowest gap among the ids that filled while the start waited for every id to be final, so an event that commits while the relay starts still reaches the stream, and it may be sent the few events that committed just before it connected above that gap. The first start reads only the ids written since a mark: the newest of the marks the process keeps (one at boot, and the recent ones its readers take) that is older than every transaction holding a write lock on events, so its cost follows recent writes, not the size of the log. A transaction that holds a transaction id but has inserted no event holds no event id, so it keeps no mark from counting, however long it stays open; only an event insert open since before every mark does, and then the first start reads the log above the horizon this process proved or the newest one any process persisted (the one-row event_horizon table, written at most once a second as the horizon advances, with the created_at of the event at it so a value from before a reset of the log is passed over): on a deploy under load, the horizon the process before it proved. Only with neither, a first boot or a reset log, does it read the whole log, which it logs. GET /auth/whoami's event_head, which a page resumes its first feed from, comes from the same marks or those horizons and waits on nothing, except on a process with no mark counting and no horizon proven or persisted, which waits up to 2 s and then answers 503 EVENT_HEAD_UNAVAILABLE rather than an event_head of 0, and the page asks again while it does. After the event log is reset, a cold stream that finds the relay still on the old log's cursor opens once the relay has moved its cursor, replayed from the newest id below which the new log has no gap. The delivery hub is ready and takes delivery changes while the horizon is held, and starts acting on events once the first event cursor is proven. Each observation uses one transaction id; concurrent callers share one, and an idle process takes none. The server observes through a two-connection pool of its own (`store.Pool.Horizon`), so the horizon never waits behind requests for a shared connection. A failed observation is logged, and a reader waiting on the horizon gets the error back once every observation has failed for ten seconds, so a horizon that cannot be read never stalls a reader silently. Observations and every read capped at the horizon run on the primary.
