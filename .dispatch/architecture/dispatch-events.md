The append-only event log every Dispatch write lands in. An append (`Broker.QueueAppend`) puts its statements on the write phase's batch (`store.WriteBatch`): the event owner's advisory lock (`store.LockOwner`, which returns at once when the transaction took it in its read phase), then the owner's row `for no key update`, the write-phase statement that gives a transaction appending its first event its transaction id before the insert takes an id, then a global advisory lock that orders event ids as their transactions commit, then one insert that takes the next sequence from the owner row and, in the same statement, advances the row's `last_seq` (and an issue's `updated_at`) to the row it inserted. An `ask.opened` payload records its own event id through the events id sequence's `currval` (`store.LatestEventID`), the same expression a stamp of the source's references uses right after its event. So nothing is read back in Go between the statements, and the whole append goes to Postgres with the rest of the write phase in one round trip; the appended event (id, sequence, time, project) reaches the caller through a callback once the batch has run. `Broker.Append` is the same statements sent at once as a batch of their own. `LockOwners` takes the locks of several owners up front, sorted and deduplicated by lock key (`store.LockOwners`), so no owner lock is waited for after the commit-order lock. An append a document ledger queues runs in the transaction's write phase, in the order the transaction made it. The broker writes through the transaction its caller hands it and imports `dispatch-store` for the owner lock and the write batch. `internal/dispatch/envoy` is the small outbound client that calls the Envoy listener's API; it exists only to carry broker-produced events onward, so the two are one component.
