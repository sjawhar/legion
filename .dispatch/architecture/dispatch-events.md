The append-only event log every Dispatch write lands in: `Broker.Append` allocates each owner's sequence under that owner's row lock and takes no other lock (none at all for an ownerless, session-addressed event), so one owner's events commit in id order while two owners' writes never wait for each other and can commit out of id order; `LockOwners` takes multiple owners deterministically. It writes through the transaction its caller hands it rather than importing the store, so it carries no edge to `dispatch-store`. `internal/dispatch/envoy` is the small outbound client that calls the Envoy listener's API; it exists only to carry broker-produced events onward, so the two are one component.

Since a lower id can still be open after a higher one has committed, every reader that pages the log by a global id cursor (the SSE relay and its `Last-Event-ID` resume, the delivery hub, `GET /api/v1/references?since=`) reads only up to the safe horizon of the server's one `events.Horizon`, and delivers in id order. An observation is one statement in a transaction of its own that reads A, the newest id its snapshot sees, and X, its own transaction id, assigned after that snapshot. A later observation whose snapshot xmin is above X proves that no transaction below X still runs, so every id at or below A is final; the horizon is the A of the newest observation proven so. The proof rests on two writer invariants: `Append` takes its transaction id (`pg_current_xact_id`) before the insert draws the event id, and `events_id_seq` keeps `CACHE 1`, so a transaction holding an id at or below A holds a transaction id below X. One snapshot cannot prove its own A: a transaction whose id is at or above the snapshot's xmax is not listed in it as in progress.

Snapshots are instance-wide, so a transaction that holds a transaction id anywhere on the Postgres instance delays events to live readers until it ends, and it never blocks a writer. An event waits for every transaction holding an id when the first observation that sees the event takes its own transaction id, which is after the event's commit (the live stream's relay reads 25 ms after the event's notification): so it also waits for transactions that began after it committed, and for id holders that write no event, such as a `SELECT ... FOR UPDATE` or another database's job on the instance. A pending observation older than five seconds logs the oldest holder. A live event stream that resumes from an id opens at once and heartbeats while the horizon is held, a cold one opens once its subscription is in place, and shutdown ends a stream still waiting. A cold stream starts at the relay's published cursor. The relay's first cursor in a process is the log's newest id when the relay starts, or the last event below the lowest gap among the ids that filled while the start waited for every id to be final, so an event that commits while the relay starts still reaches the stream, and it may be sent the few events that committed just before it connected above that gap. The first start reads only the ids written since a mark: the newest of the marks the process keeps (one at boot, and the recent ones its readers take) that is older than every transaction holding a write lock on events, so its cost follows recent writes, not the size of the log. A transaction that holds a transaction id but has inserted no event holds no event id, so it keeps no mark from counting, however long it stays open; only an event insert open since before every mark does, and then the first start reads the log above the horizon this process proved or the newest one any process persisted (the one-row event_horizon table, written at most once a second as the horizon advances, with the created_at of the event at it so a value from before a reset of the log is passed over): on a deploy under load, the horizon the process before it proved. Only with neither, a first boot or a reset log, does it read the whole log, which it logs. GET /auth/whoami's event_head, which a page resumes its first feed from, comes from the same marks or those horizons and waits on nothing, except on a process with no mark counting and no horizon proven or persisted, which waits up to 2 s and then answers 503 EVENT_HEAD_UNAVAILABLE rather than an event_head of 0, and the page asks again while it does. After the event log is reset, a cold stream that finds the relay still on the old log's cursor opens once the relay has moved its cursor, replayed from the newest id below which the new log has no gap. The delivery hub is ready and takes delivery changes while the horizon is held, and starts acting on events once the first event cursor is proven. Each observation uses one transaction id; concurrent callers share one, and an idle process takes none. The server observes through a two-connection pool of its own (`store.Pool.Horizon`), so the horizon never waits behind requests for a shared connection. A failed observation is logged, and a reader waiting on the horizon gets the error back once every observation has failed for ten seconds, so a horizon that cannot be read never stalls a reader silently. Observations and every read capped at the horizon run on the primary.
