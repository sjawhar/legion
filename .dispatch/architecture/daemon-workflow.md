Planned: the issue-cap admission line, durable Dispatch and GitHub event intake, classification, the transition table, status and notice effects, and the Go Dispatch client — `internal/admit`, `internal/intake`, `internal/workflow`, `internal/classify`, `internal/dispatch`, `internal/notify`, `internal/phase`. LEGION-219 (Stage 3) carries them; none exists on `main` yet, so this component has no paths. The planned workflow advances phases from facts the coordinator observes; agents do not choose the next phase.

Admission and the workflow read the deployment's repository equivalence (`repository_renames`, `config.Config.RepositoryRenames`, a `ghrepo.Renames`) wherever they compare a repository's name, so a transfer that renames a repository leaves the trees already recorded under the old name running: in intake, `DeployOf` matches a `deploys:` entry naming the repository as it was against a run on the one it moved to, and `ConsumerSpec.Renames` carries the pair into the consumer's `recordedPullRequest` read; in `workflow`, one `Engine.sameRepository` stands where `strings.EqualFold` stood, at `issueForBranch`, `ownPullRequest`, the opened handler's redelivery test, `check.go`'s comparison of a recorded check, `issueDeployed`, `compareBuilds` against `Config.BuiltFrom`, `deployRunCompleted` and `NoteRepositoryKept`, which therefore says nothing when Dispatch re-points an issue at the repository the one it is recorded on moved to. The reads keyed on the `pull_requests` table's `repo` column — the engine's `pullRequest` and `pullRequestByBranch`, `internal/daemon`'s `reviewedRepository` and intake's `recordedPullRequest` — ask under each name `Renames.Lookups` gives, the fact's own first and the pair's other name only when the first finds nothing, which is what lets a pull request already open at the transfer go on taking its CI, its review and its merge. The equivalence is read-side only: no record is rewritten, every record keeps the repository it was written under for its whole life, and so the pair must stay configured for as long as any record names the old repository. It serves no repository of its own either — the served set is Dispatch's mapping alone, and no rename is read from GitHub — so a pair may be configured before the transfer and simply answers nothing until the events arrive under the new name.
