The Go coordinator is Legion's deterministic half: admission, workflow, the issue record, process supervision across tmux and Agent Sandbox, and credentials. It is developed separately from the current TypeScript daemon until the Stage 7 cutover. `scripts/e2e` holds each stage's live proof — the daemon booting on a real Postgres, and real Oh My Pi panes under its private tmux server. The `scripts/e2e` proofs that run Dispatch start the pgvector-on-PostgreSQL-18 image Envoy's `internal/testpg` pins, by the same digest.

A repository that moved is configured as the top-level `legion.yaml` key `repository_renames` (`- from: … / to: …`), which settles onto `config.Config.RepositoryRenames`, the one equivalence `internal/ghrepo/renames.go` holds (`Same`, `Partner`, `Under`, `Pairs`; the zero value a deployment configuring none carries answers exactly as `strings.EqualFold` does). A configured pair's two names are one repository wherever the daemon compares a name: intake's `recordedPullRequest` read, the repository mapping's `lookup` and `kept`, `heardRepositories`, which puts both subjects on the consumer's filters so neither side goes deaf over a transfer, the boot's backfill, the pull-request listing reads and `githubrest.PullRequest.HeadIn`, `reviewedRepository`, and the whole of the workflow engine's comparisons; `appauth.GitHubCredential` still gives a role's gh bundle one directory per owner, named for the owner the record keeps, which no transfer moves, with a `<owner>/<repo>` directory under the write owner for each other repository it serves, and what a resolving pair changes is the token in them: the directory named for the recorded owner and the directory of the owner that serves that repository now hold one lease, minted for that serving owner, so the directory a role writes through authorises nothing by its name and everything by the token in it, while `legion gh`, `legion git-credential` and both runtimes are unchanged. The equivalence is read-side only — nothing it answers rewrites a record, and a tree keeps the repository name it was recorded under for its whole life — so the pair must stay configured for as long as any record names the old repository. It adds no repository to the served set, which is Dispatch's mapping alone, and reads nothing from GitHub, so a pair may be configured before the transfer, the boot logging once that the project serves nothing under the name the repository moved to; `legion start --check-config` prints one line per pair and `legion state --json` carries them (`settings.repository_renames`).

Which repository the daemon's own GitHub calls name is the same file's second rule: `Serving` is the repository GitHub holds a recorded one under now — the pair's other name exactly when the recorded name is that pair's `from`, the project serves the pair's `to` and the project does not serve the pair's `from`, every other recorded name, the pair's `to` among them, answered unchanged — and `OwnerAliases` is each owner a pair moved a repository away from, by the owner it moved to, for the pairs that resolve by that same rule (a pair inside one owner is no alias, since a rename inside one owner moves nothing between installations). Both read the repositories the project serves, one repository at a time (`repositories.servesRepository` over the mapping's own map, `ghrepo.Serves` over a served slice), and never the set of owners those repositories have: a project that serves one more repository of the old owner serves no more of the moved one, while the owner predicate this replaces read that as the old owner being the project's own and stopped resolving the pair, which is how adding one repository to a project's mapping turned a live pair off and left 47 trees unable to push for 42 minutes. No set of owners the project serves stops a pair from resolving. `internal/daemon`'s `repositories.serving` reads the rule over the mapping and is the deployment's one copy of it: the boot hands it to `internal/api` as `Options.Serving` and to the Sandbox runtime's token source as `implementTokens`' own map, so neither reads the mapping a second time, while `appauth`'s `bundleDirs` reads both halves over the served repositories themselves, once per bundle, for `GitHubCredential`, `ControllerCredential` and `GitHubDirs` alike — the write lease for the role's own repository stands in two directories and no others, the one named for the owner its record keeps and the one named for the owner that serves it, which are one directory wherever no pair resolves, each other repository that serving owner holds gets a `<owner>/<repo>` directory with a read lease that names it alone, every other owner the project serves a repository of under its own name keeps one read lease over its own repositories, and an owner only a resolving rename puts in the bundle holds the lease of the owner that serves the moved repository. `NewRenames` still refuses one owner's repositories moved to two owners, and its reason is now that `OwnerAliases` is keyed by the owner a pair moved a repository away from, so two such pairs write that key twice and the last wins, silently. The mapping load reads the pair's other name only when GitHub answers that no App of the deployment is installed on the mapped one (`checkMapping`, over `Partner`) — a mapped name that holds one of the two Apps and not the other is the operator's own gap rather than a transfer, so the entry is left out naming the App that is missing and the pair is not read — and serves and records the entry under the name both Apps answered for, two mapping entries that name one repository being served as one and keeping the default (`set`). Where the call is a REST read or write or a GraphQL query — the issue branch's create, `readyMerge` and `autoMergeDisable`, the required-checks pass's reads, the API's read of a completing implementer's pull request, the merger's READY checks and the commit identity every launch and adoption mints — both the App token's owner and the address are the serving repository's. The daemon makes no GitHub call of its own for a production check: it reads no deployment's production workflows, and a check's next look is the one the role the project's `production_check` names asked for with `wake_at` on a `pending` report. The default-branch read is mapped inside `defaultBranches.fetch`, the one place that mints for it, so the boot's backfill of a record written under the old name, the mapping's own naming and an unrecorded issue's default repository all read the repository GitHub holds it under now, while what is kept stays keyed by the name the caller asked for. The token is the half that has to move: after a transfer the installation covering the repository is the new owner's, and the old owner's token reaches nothing. The address need not, since GitHub answers an API call at the old name too (measured: `GET /repos/twitter/bootstrap` answers 301 to `/repositories/2126244`, and GraphQL's `repository(owner:"twitter",name:"bootstrap")` answers `twbs/bootstrap`), but naming the served repository keeps a write off a redirect and names the right repository in a log line. Where the address is a git remote, the token alone follows the pair and the address stays the name the record keeps: the outbox's workspace provisioning and `implementTokens`, the one source the Sandbox runtime's three mint sites share, whose addresses also key a pod's feed, its clone and the repository cache's volume and Service, which a rename must not move.

A project's per-tree memory setting is `legion.yaml`'s `projects.<KEY>.memory`, read by `internal/config/memory.go` onto `config.Project.Memory`: `mode` is `off`, `on` or `random`, and the zero value a project naming no block leaves is off, whose recorded word is `Memory.Word`'s `off`; `config_files` are the Oh My Pi settings overlays and `instructions` the one markdown file, each a clean absolute path taken as written, since the daemon and a pane read them from wherever they start. `checkMemory` refuses, once the rest of the file is settled, a mode other than off that names no overlay, a block that names overlays while `worker_backends` puts an issue role on a harness other than Oh My Pi (which reads no `PI_CONFIG_FILES`), and, under `runtime: kubernetes`, an overlay outside every `runtime.kubernetes.pod` mount (`checkRoleConfigMount`, the role overlays' own check); `internal/daemon`'s `checkRoleConfigFiles` refuses under tmux an overlay no pane could read, and `readBoot` an `instructions` file it cannot read or that holds nothing. Only the first of those reads the mode: the launch follows the record, so a tree already drawn into the memory group names the block's files under any mode, and every check of the files themselves holds at `off` too. `off` beside both paths is accepted and keeps them, so a move to `on` moves one key, and a project with no block at all is the pane and the pod every deployment built before the block existed.

The group a tree runs under is drawn once, by `internal/memorygroup`'s `draw` (`off` gives `none`, `on` gives `memory`, and `random` a fair coin read from `crypto/rand`, never a seeded sequence; the empty mode a project naming no block leaves is turned into `off` by `config.Memory.Word` alone, and `draw` refuses any other word), at the one moment a tree's lifecycle row is first created (`treelifecycle.Lifecycle.Created`), inside that row's own transaction, on both paths that open a tree: admission's `promoteHolds` and the operator's spawn, whose draw `internal/api`'s `drawMemory` runs inside `store.Store.OpenOperatorTreeLifecycle`. Both paths draw and record through one helper, `memorygroup.DrawAndRecord`, the package's one way in. `record.Store.DrawMemory` writes the group, the mode it was drawn under and the instant onto the tree's root issue row and never again, and `PutIssue` names none of the three, so a re-admission, a new generation, `ClearTreeGeneration` and the next epoch after a cleanup all keep the draw; `readmit` settles a handed-over child's memory at the hand-over (`CarryMemory`), with the answer of the tree it leaves — that tree's triple verbatim, the draw time included, where it had one, so the work goes on under the group it has been running under, and no draw at all where it had none. A root first opened before the migration carries no draw and is drawn for by nothing later, so it runs without memory for its whole life, and a change of a project's mode reaches only the trees opened after it; a child handed over out of such a tree takes that answer with it, written at the hand-over as `issues.memory_carried` (`20261104153554_issue_memory_carried`), which is what `DrawMemory` refuses on, so the draw reads nothing that moves and the order the two roots are promoted in changes nothing. The carry's driver row is the old tree's `tree_lifecycles` row, matched on the tree and the normalized runtime token, since `tree_lifecycles.project` is that token while `issues.project` is the Dispatch key; the old tree's own issue record is joined in rather than required, because an operator's tree the daemon recorded no root for was opened all the same and hands over the answer it has. A tree with no such row was never opened, so the carry writes nothing and the child's own first open draws it like any other new tree. An operator spawn whose tree has no issue record writes no draw, which is refused nothing and invents no record.

At launch the group is the tree's: `internal/daemon`'s `specs` asks the tree root's record for it (`treeMemoryGroup`, over the daemon's own store, so a tree the operator's spawn drew with no workflow configured is launched with the group it drew), and sets `runtime.SpawnSpec.Memory` and `PromptParts.MemoryInstructionsPath` on a worker spawn alone. Both runtimes then name `Options.MemoryConfigFiles` last in `PI_CONFIG_FILES`, after the operator's own overlays and the role's own (`tmux`'s `panePairs`, `sandbox`'s `launch.overlays` through `roleOperatorEnv`), and end the one `--append-system-prompt` value with the daemon's own copy of the instructions (`config.ReadMemoryInstructions` at boot and `config.WriteMemoryInstructions`, `<state_dir>/memory-instructions.md`), after the deployment's own; a pane reads that copy with `$(cat …)` and a pod is given its text inlined, since a pod reads no file of the daemon's. `controllerSpawnSpec` sets neither and `validateControllerShape` refuses either, because a memory group is a tree's and the controller runs in none, and `mode: on` with no `instructions` appends nothing. Every issue of the tree is shown the root's draw (`internal/projection`, `api.Issue`, daemon API contract 49), and `legion state` prints one line counting the issues drawn under each group and mode: the state names no tree, and a tree handed over as one of its own carries its old tree's draw verbatim, so no draw is a tree's name.
