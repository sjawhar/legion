The Go coordinator is Legion's deterministic half: admission, workflow, the issue record, process supervision across tmux and Agent Sandbox, and credentials. It is developed separately from the current TypeScript daemon until the Stage 7 cutover. `scripts/e2e` holds each stage's live proof — the daemon booting on a real Postgres, and real Oh My Pi panes under its private tmux server. The `scripts/e2e` proofs that run Dispatch start the pgvector-on-PostgreSQL-18 image Envoy's `internal/testpg` pins, by the same digest.

A repository that moved is configured as the top-level `legion.yaml` key `repository_renames` (`- from: … / to: …`), which settles onto `config.Config.RepositoryRenames`, the one equivalence `internal/ghrepo/renames.go` holds (`Same`, `Partner`, `Under`, `Pairs`; the zero value a deployment configuring none carries answers exactly as `strings.EqualFold` does). A configured pair's two names are one repository wherever the daemon compares a name: intake's deploy matching (`DeployOf`, which `config`'s `checkDeployRenames` holds to one entry per workflow of a pair) and its `recordedPullRequest` read, the repository mapping's `lookup` and `kept`, `heardRepositories`, which puts both subjects on the consumer's filters so neither side goes deaf over a transfer, the boot's backfill, the pull-request listing reads and `githubrest.PullRequest.HeadIn`, `reviewedRepository`, and the whole of the workflow engine's comparisons; `appauth.GitHubCredential` gives a renamed pair one bundle entry, minted for the owner the repository moved to, written into both owners' gh directories and carrying the write lease whenever either owner is the bundle's `Default`, while `legion gh`, `legion git-credential` and both runtimes are unchanged. The equivalence is read-side only — nothing it answers rewrites a record, and a tree keeps the repository name it was recorded under for its whole life — so the pair must stay configured for as long as any record names the old repository. It adds no repository to the served set, which is Dispatch's mapping alone, and reads nothing from GitHub, so a pair may be configured before the transfer, the boot logging once that the project serves nothing under the name the repository moved to; `legion start --check-config` prints one line per pair and `legion state --json` carries them (`settings.repository_renames`).

Which repository the daemon's own GitHub calls name is the same file's second rule: `OwnerAliases` is each owner a pair moved a repository away from, by the owner it moved to, over the owners the project serves repositories of (a pair inside one owner and a pair between two of the project's owners are no alias, the latter warned of once per mapping load by `logRenameOwnerConflicts`), and `Serving` is the repository GitHub holds a recorded one under now. `internal/daemon`'s `repositories.serving` reads it over the mapping, and `internal/api`'s `server.serving` over `GitHubOwners`. Where the call is a REST read or write or a GraphQL query — the production check's compare, the issue branch's create, `readyMerge` and `autoMergeDisable`, the required-checks pass's reads, the API's read of a completing implementer's pull request, the merger's READY checks and the commit identity every launch and adoption mints — both the App token's owner and the address are the serving repository's. The default-branch read is mapped inside `defaultBranches.fetch`, the one place that mints for it, so the boot's backfill of a record written under the old name, the mapping's own naming and an unrecorded issue's default repository all read the repository GitHub holds it under now, while what is kept stays keyed by the name the caller asked for. The token is the half that has to move: after a transfer the installation covering the repository is the new owner's, and the old owner's token reaches nothing. The address need not, since GitHub answers an API call at the old name too (measured: `GET /repos/twitter/bootstrap` answers 301 to `/repositories/2126244`, and GraphQL's `repository(owner:"twitter",name:"bootstrap")` answers `twbs/bootstrap`), but naming the served repository keeps a write off a redirect and names the right repository in a log line. Where the address is a git remote, the token alone follows the pair and the address stays the name the record keeps: the outbox's workspace provisioning and `implementTokens`, the one source the Sandbox runtime's three mint sites share, whose addresses also key a pod's feed, its clone and the repository cache's volume and Service, which a rename must not move.

A project's per-tree memory setting is `legion.yaml`'s `projects.<KEY>.memory`, read by `internal/config/memory.go` onto `config.Project.Memory`: `mode` is `off`, `on` or `random`, and the zero value a project naming no block leaves is off, whose recorded word is `Memory.Word`'s `off`; `config_files` are the Oh My Pi settings overlays and `instructions` the one markdown file, each a clean absolute path taken as written, since the daemon and a pane read them from wherever they start. `checkMemory` refuses, once the rest of the file is settled, a mode other than off that names no overlay, a block that names overlays while `worker_backends` puts an issue role on a harness other than Oh My Pi (which reads no `PI_CONFIG_FILES`), and, under `runtime: kubernetes`, an overlay outside every `runtime.kubernetes.pod` mount (`checkRoleConfigMount`, the role overlays' own check); `internal/daemon`'s `checkRoleConfigFiles` refuses under tmux an overlay no pane could read, and `readBoot` an `instructions` file it cannot read or that holds nothing. Only the first of those reads the mode: the launch follows the record, so a tree already drawn into the memory group names the block's files under any mode, and every check of the files themselves holds at `off` too. `off` beside both paths is accepted and keeps them, so a move to `on` moves one key, and a project with no block at all is the pane and the pod every deployment built before the block existed.

The group a tree runs under is drawn once, by `internal/memorygroup`'s `draw` (`off` gives `none`, `on` gives `memory`, and `random` a fair coin read from `crypto/rand`, never a seeded sequence; the empty mode a project naming no block leaves is turned into `off` by `config.Memory.Word` alone, and `draw` refuses any other word), at the one moment a tree's lifecycle row is first created (`treelifecycle.Lifecycle.Created`), inside that row's own transaction, on both paths that open a tree: admission's `promoteHolds` and the operator's spawn, whose draw `internal/api`'s `drawMemory` runs inside `store.Store.OpenOperatorTreeLifecycle`. Both paths draw and record through one helper, `memorygroup.DrawAndRecord`, the package's one way in. `record.Store.DrawMemory` writes the group, the mode it was drawn under and the instant onto the tree's root issue row and never again, and `PutIssue` names none of the three, so a re-admission, a new generation, `ClearTreeGeneration` and the next epoch after a cleanup all keep the draw; `readmit` copies a handed-over child's old tree's triple onto its new root verbatim, the draw time included (`CarryMemory`), so the work goes on under the group it has been running under. A root first opened before the migration carries no draw and is drawn for by nothing later, so it runs without memory for its whole life, and a change of a project's mode reaches only the trees opened after it; a child handed over out of such a tree takes that answer with it, since `DrawMemory` draws no root whose `handed_over_from` names a tree that holds a `tree_lifecycles` row, carried or not — the store's own fact that the old tree was really opened, matched on the tree alone, since `tree_lifecycles.project` is the normalized runtime token while `issues.project` is the Dispatch key. A root whose old tree was never opened has run under nothing, so its own first open draws it like any other new tree, and an empty `handed_over_from` matches no row. An operator spawn whose tree has no issue record writes no draw, which is refused nothing and invents no record.

At launch the group is the tree's: `internal/daemon`'s `specs` asks the tree root's record for it (`treeMemoryGroup`, over the daemon's own store, so a tree the operator's spawn drew with no workflow configured is launched with the group it drew), and sets `runtime.SpawnSpec.Memory` and `PromptParts.MemoryInstructionsPath` on a worker spawn alone. Both runtimes then name `Options.MemoryConfigFiles` last in `PI_CONFIG_FILES`, after the operator's own overlays and the role's own (`tmux`'s `panePairs`, `sandbox`'s `launch.overlays` through `roleOperatorEnv`), and end the one `--append-system-prompt` value with the daemon's own copy of the instructions (`config.ReadMemoryInstructions` at boot and `config.WriteMemoryInstructions`, `<state_dir>/memory-instructions.md`), after the deployment's own; a pane reads that copy with `$(cat …)` and a pod is given its text inlined, since a pod reads no file of the daemon's. `controllerSpawnSpec` sets neither and `validateControllerShape` refuses either, because a memory group is a tree's and the controller runs in none, and `mode: on` with no `instructions` appends nothing. Every issue of the tree is shown the root's draw (`internal/projection`, `api.Issue`, daemon API contract 47), and `legion state` prints one line counting the issues drawn under each group and mode: the state names no tree, and a tree handed over as one of its own carries its old tree's draw verbatim, so no draw is a tree's name.
