The Go coordinator is Legion's deterministic half: admission, workflow, the issue record, process supervision across tmux and Agent Sandbox, and credentials. It is developed separately from the current TypeScript daemon until the Stage 7 cutover. `scripts/e2e` holds each stage's live proof — the daemon booting on a real Postgres, and real Oh My Pi panes under its private tmux server. The `scripts/e2e` proofs that run Dispatch start the pgvector-on-PostgreSQL-18 image Envoy's `internal/testpg` pins, by the same digest.

A repository that moved is configured as the top-level `legion.yaml` key `repository_renames` (`- from: … / to: …`), which settles onto `config.Config.RepositoryRenames`, the one equivalence `internal/ghrepo/renames.go` holds (`Same`, `Partner`, `Lookups`, `Pairs`; the zero value a deployment configuring none carries answers exactly as `strings.EqualFold` does). A configured pair's two names are one repository wherever the daemon compares a name: intake's deploy matching (`DeployOf`) and its `recordedPullRequest` read, the repository mapping's `lookup` and `kept`, `heardRepositories`, which puts both subjects on the consumer's filters so neither side goes deaf over a transfer, the boot's backfill, the pull-request listing reads and `githubrest.PullRequest.HeadIn`, `reviewedRepository`, and the whole of the workflow engine's comparisons; `appauth.GitHubCredential` gives a renamed pair one bundle entry, minted for the owner the repository moved to, written into both owners' gh directories and carrying the write lease whenever either owner is the bundle's `Default`, while `legion gh`, `legion git-credential` and both runtimes are unchanged. The equivalence is read-side only — nothing it answers rewrites a record, and a tree keeps the repository name it was recorded under for its whole life — so the pair must stay configured for as long as any record names the old repository. It adds no repository to the served set, which is Dispatch's mapping alone, and reads nothing from GitHub, so a pair may be configured before the transfer, the boot logging once that the project serves nothing under the name the repository moved to; `legion start --check-config` prints one line per pair and `legion state --json` carries them (`settings.repository_renames`).

Which repository the daemon's own GitHub calls name is the same file's second rule: `OwnerAliases` is each owner a pair moved a repository away from, by the owner it moved to, over the owners the project serves repositories of (a pair inside one owner and a pair between two of the project's owners are no alias, the latter warned of once per mapping load by `logRenameOwnerConflicts`), and `Serving` is the repository GitHub holds a recorded one under now. `internal/daemon`'s `repositories.serving` reads it over the mapping, and `internal/api`'s `server.serving` over `GitHubOwners`. Where the call is a REST read or write or a GraphQL query — the production check's compare, the issue branch's create, `readyMerge` and `autoMergeDisable`, the required-checks pass's reads, the API's read of a completing implementer's pull request — both the App token's owner and the address are the serving repository's, since GitHub redirects `git clone`, `git fetch` and `git push` on a transferred repository but no API call. Where the address is a git remote, the token alone follows the pair and the address stays the name the record keeps: the outbox's workspace provisioning and `implementTokens`, the one source the Sandbox runtime's three mint sites share, whose addresses also key a pod's feed, its clone and the repository cache's volume and Service, which a rename must not move.
