The live document surface: the collaborative websocket room, two-phase settlement that mints block ids before it persists and compares what it rendered, the agent edit operations (`replace`, `delete`, `insert`, `retype`, `move`, `delete_row`, `delete_column`) and the ask blocks an edit adds, which the API checks for related items, block tokens and preconditions, and ask and comment anchor refresh.

A transaction a handler joins (`Docs.Join`) or a settlement opens has a read phase and a write phase. The read phase takes the document owner's advisory lock (`lockArtifactOwner`), the in-memory writer slot, the copy lock where one is needed and the document's advisory lock, in that order - none of them a row lock, so none gives the transaction a transaction id - reads, and does every operation's work: forks and renders, `refreshAnchors`' walk, version capture, reference extraction, the approval carry. Every write an operation makes goes through `write`, which queues it on the transaction's ledger (`WriteStep`; a handler queues its own writes in the same queue with `Ledger.Queue`), and a read that would have seen the transaction's own write is answered from the ledger: pending appends count toward the document head (`withOwnAppends`), pending anchors toward a refresh's walk (`RegisterPendingAnchor`), a pending version's number, time and markdown (`NextVersion`, `Now`, `PendingVersionMarkdown`). The write phase is one pipelined batch: `Ledger.Commit` has each queued step put its statements on one `store.WriteBatch`, in the order the transaction made them, so statements and events keep that order, appends the settlement credit's statements, and sends the batch in one round trip; Postgres runs the statements back to back and the client reads their results once, so no Go code - and no wait for this process to be scheduled - runs between two of them while the transaction holds its id. A step reads no result: a value a later statement needs is derived in SQL (an event's sequence from its owner row, a stamp's or a review's event from the events id sequence's `currval`, `store.LatestEventID`) or read in the read phase (a row's time, its id), and a value needed after `Commit` is filled by the statement's callback. The first statement that fails or callback that refuses its result (a guarded answer of an approval request, an edit-notice claim that no longer matches, a decided-wording restoration that restored other asks) stops it, the transaction rolls back, no room sees its changes, and `Commit` returns that error unchanged; then `Commit` commits and publishes to the rooms. `Discard` drops the queue. Settlement, the block-index backfill and decided-wording restoration queue their writes on a ledger of their own (`queueWrites`) and send them as one batch right before they commit; a write outside any ledger sends its statements as a batch of its own (`store.RunWrite`). The anchor-refresh writes, an update and a `*.anchor_refreshed` append per changed anchor, ride in the batch, so they cost server time but no round trip; folding them into one statement is INFRA-605's.
