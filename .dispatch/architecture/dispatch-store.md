The schema every other package reads and writes through: ordered migrations applied in one transaction each at boot, the connection pools, and the session and people rows — which is why it imports `auth`. `internal/pgmigrate` holds the runner's rules, which the secrets broker's runner shares: the whole migration set is refused before anything applies when two files share a version or a file is misnamed or unreadable, and every migration's lock waits are bounded at five seconds. `internal/pgmigrate` reads migration and census SQL as Postgres 18's lexer does. A process's connections are one budget of 89 (`store.ConnectionsPerProcess`), partitioned into pools sized in code so no side can starve another: requests 48, background loops 6, live-update readers 4, settlements 4, document loads 4, the event log's safe horizon 2, the health probe 1, the 3 LISTEN connections (the listener pool's one dial is one of them redialling), leases 15 (one per name on `duty`'s lease list, thirteen, and two spare), the outbox 1 and the server process registry 1 (opened and closed by `processes.Register` from `store.Pool.OpenRegistry`), each pool's connections named `dispatch-<pool>` in `application_name`. Every way a guarded pool hands out a connection refuses a second one to a caller already holding one (`ErrNestedAcquire`), its request's pinned connection included: the pool that pinned it runs its calls on that connection, and every other guarded pool refuses it. Each pool's acquires are counted by an acquire tracer and bounded at that pool's bound, past which the pool answers `ErrPoolBusy` — the guarded pools and the raw ones a caller works through as pgx pools alike (`store.RawPool`: document loads, leases, LISTEN, the horizon, the registry and the health probe), so no caller has to read a want of connections off a bare `context.DeadlineExceeded` — all but the outbox's, the registry's and the health probe's, which have no bound because each of those pools has one caller that holds at most its one connection (`store/acquire.go`; the probe bounds its wait, dial and query together instead). An admitted read of weight one runs every request-pool statement of its handler on one pinned connection, held for the handler's whole length (`PinConnection`, `api.apiRoute.pinsConnection`); a read of weight two, whose two reads run side by side, and the four file version downloads, which hold no connection while their bytes move, pin none. A transaction a guarded pool opened commits apart from its caller's cancellation, within ten seconds (`CommitContext`), where a `RawPool` transaction is the pgx transaction itself and commits on its caller's own context; a commit the database does not answer within that bound is `ErrCommitTimeout`, whose outcome is unknown, where a busy pool's is that nothing ran. `internal/dispatch/admission` travels with the pools it is sized to: it admits each request only while the request pool has room for its class and for both classes together (14 read units and 12 write units per CPU the process may use, capped at 28 and 24, so 28 and 24 on two CPUs or more, and at most 40 units of the two together — `MaxAdmittedUnits`, the 48 of the request pool less the 8 its uncounted users need, which the class caps alone would oversubscribe by 12; 22 of the 40 kept for the reads while a read is queued for room — `ReservedReadUnits`, which holds the writes to 18 under read pressure and lets them reach their whole 24 only while the reads are light; a queue twice as long as the class limit and at most 1 s of waiting), refuses the rest at once with `429 OVERLOADED` and `Retry-After`, and answers a busy pool or a read past its deadline with a retryable `503 DATABASE_BUSY` or `503 REQUEST_TIMEOUT`. A request whose client went away is answered nothing and its access-log line carries `status=499` (`accesslog.ClientGone`), wherever the client left: queued for room, with its body half sent, or under the handler. A commit of unknown outcome is the API's own answer rather than admission's: `500 COMMIT_OUTCOME_UNKNOWN` to a client still there, and an ERROR line naming the unknown outcome whether or not one is (`api.writeHandlerError`).

The schema also announces the changes the background loops wake on: `embeddings_enqueue` notifies `dispatch_embeddings` when it writes a row (0151), a row trigger on `refs` notifies `dispatch_excerpts_owed` for each document mention left owed an excerpt (0153), `delivery_settings_changed` notifies `dispatch_delivery_settings` for a settings change other than freshness (0156), a row trigger on `document_edit_notices` notifies `dispatch_edit_notices` for each notice given a due time (0157), and every event commit notifies `dispatch_events` (0107). The loops' own state is three additions: `reference_excerpt_backoff` (0152), each failing document's version, failures in a row and next attempt; `suggestion_outcome_cursor` (0154), the one row holding the highest event id the outcome sweep has judged by; and `write_suggestions.swept` (0155), whether a pass has judged a suggestion against all its events, with the partial indexes `write_suggestions_unswept` and `write_suggestions_pending_artifact`. The pool's listener pool dials the held LISTEN connections, the background loops' shared wake listener among them.

The store also holds what the related-item check reads and writes: each project's term statistics (`search_term_stats`, `search_term_totals`, rebuilt under the `search-term-stats` lease), one `related_checks` row per check, and the trigger that embeds an issue as its title and spec (migrations 0139 and 0140).
