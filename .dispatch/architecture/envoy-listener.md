Ingests GitHub, Slack and Ghost Wispr webhooks, publishes ordinary notifications through JetStream, and role lanes and ad-hoc `notifications.` topics the stream does not capture through core NATS, resolves live sessions and delivers by `prompt_async`; keeps a durable consumer per session (`s-<session id>`) and relays it in stream order, as core frames on `notifications.envoy.deliver.<session id>` acknowledged on the session's `done`, or by `prompt_async` to a serving port; forwards each role message once from one shared role-lane queue group; tracks PR check settlement. Its publish route answers a role or ad-hoc topic message once each recipient confirmed it (the role's holder, or each self-subscribed session registered on the topic), or 504 naming who did not. The CI store's summary loop is event-driven: the store's cache marks each record that changes, the loop keeps the records waiting out their debounce, a claim or the handover grace in a queue ordered by deadline, and it runs a pass only on a one-second tick at which a record changed or fell due, so with nothing changed it does no work and a change costs the same at any cache size. The `ENVOY_NOTIFICATIONS` stream and each KV bucket hold the deployment's replica count (`ENVOY_NATS_REPLICAS`), and the stream has a byte limit (`ENVOY_STREAM_MAX_BYTES`) past which it refuses new publishes (`DiscardNew`, a retryable `bus.ErrStreamFull` the webhook answers 503) and keeps every stored message until its 72-hour age; a clustered server's duplicate acknowledgement with no sequence, for a retry of a refused message (`bus.ErrNotStored`), has the bus publish the message once more without its `Nats-Msg-Id`, which the stream stores once it has room, and is never a success. A start raises a stream or bucket found with fewer copies, and a stream with a smaller byte limit or none, never lowers either, and keeps the stream's metadata, `envoy_stream_id` included, and its other limits on every update. JetStream's stream update has no compare-and-swap, so a concurrent start with other or no settings can put back the copies, limit and metadata it read; every owning program (the listener, Dispatch's server) therefore runs a keeper that every 30 seconds raises the stream's copies and byte limit back to its settings, puts back the discard policy and `envoy_stream_id`, and raises its own buckets' copies. An operator's raise of the limit stands, and the stream holds the most copies and the largest limit any program of a deployment carries. The small packages that instrument that path belong to it rather than to components of their own: OpenID Connect token verification for service accounts and the authorization code flow Dispatch's sign-in runs (`oidc`), the signature and duplicate-delivery guards (`verify`, `dedupe`), `metrics`, `id`, `logging`, listener bootstrap (`config`), the `natstail` diagnostic tail, and the listener's own harnesses (`integration`, `smoke`, `testnats`). `internal/dispatch/config` sits under the Dispatch tree but belongs here: it loads the shared `envoy.json` shape — NATS URLs, the Dispatch server URL and token — that `natstail`, the Dispatch server and the Envoy plugin all read. A session's registry entry, and its row in `GET /v1/sessions` and `GET /v1/registry/<id>`, carry the `plugin` and `plugin_version` its registration sent; a session from a plugin older than those fields has neither key.

The listener keeps the interest, session and CI buckets in memory through watcher-fed caches (`kvwatch`, shared by `store`, `session` and `cistore`). A start reads each bucket in full; a rewatch after a NATS reconnect or a self-health rebuild resumes after the last revision its cache applied, so it delivers only what was written since, and reads in full again for a recreated bucket, after a scan that did not complete, or when its resuming watcher cannot be created (logged at WARN). The session cache gives each entry a deadline one `MaxAge` after its write, since JetStream delivers no event when the bucket's `MaxAge` expires a key: the entry leaves the cache at that deadline on a timer, and a read that misses it goes through to the bucket. That deadline bounds the cache alone and decides no session's state.

A session is `live`, `unresponsive` or `gone`, computed from its registration record's `UpdatedAt` and never from cache or bucket membership: within `ENVOY_SESSION_LIVE_WINDOW` (5m by default); past it but within `ENVOY_SESSION_GONE_HORIZON` (1h by default); or past the horizon, or with no record at all. An `unresponsive` session is not dead — it keeps its role claims and its issue claims, a message sent to it is stored for it, and nothing starts a replacement for it — so every list row, every lookup, every refusal that names a session and every role answer carries `state` and `last_seen`, a role answer the holder's `holder_state` and `claim_released`. No lookup, publish, role-lane delivery or daemon probe releases a role claim for an `unresponsive` holder: only the session reaper does, once the holder is `gone`, running every `ENVOY_SESSION_REAP_INTERVAL` (1m by default). A Legion role whose agent process exits is `gone` at once. `ENVOY_SESSION_MAX_AGE` sets the `envoy_sessions` bucket's `MaxAge` when it is set and leaves the bucket as it is when it is not; `/healthz` reports the age in use as `session_max_age`.

The listener's interest reaper deletes a gone session's interest from the `envoy_interests` bucket only 15 minutes after the row's last write: the grace window it is given, `store.InterestReapGrace` (10 minutes), plus `store.InterestRefreshAge` (5 minutes), the most a row's last write may lag the session's last heartbeat.

A session's registry entry also carries the `client_instance_id` its registration sent: one Oh My Pi Envoy extension instance, one Claude Code channel-server process, each minting that id when it starts. A soft claim on `POST /v1/roles/set` takes the role from a holder that is not `live`, and from the predecessor it names (`previous_session_id`) when that predecessor is not `live` either, when its live entry carries the claimant's own instance id, or when either entry carries no instance id, which the listener logs with both session ids. Any other live holder keeps the role, a live predecessor of another client instance among them, and the claim is a 409 naming it. The predecessor's entry is read from the `envoy_sessions` bucket itself rather than from the trailing cache, and the claimant's entry is read from the bucket too, falling back to the cached entry when that read does not answer. `DELETE /v1/sessions/<id>` takes the same id as the `client_instance_id` query parameter and then removes the entry only while it carries that id or none, answering `200 {"deleted":true}` or `200 {"deleted":false,"reason":…}`.
