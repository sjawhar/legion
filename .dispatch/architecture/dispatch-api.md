Every HTTP route body: issues, artifacts, asks, comments, messages, projects, search, and the assignee, rank, label and component-attachment writes. Search reads each ask hit's answer state from its row, and a resolved ask's last answer from its `ask.answered` events, before it answers. The largest package in the server (87 files) and the one every Dispatch feature touches. It resolves an agent's actor through the listener's OIDC and routing packages, hence the edge to `envoy-listener`. The edge to `contracts` is the wire contract rather than a Go import: `contracts/src/dispatch-api.ts` declares the response shapes these handlers produce and the web app consumes, and code generation covers only the event envelope, so there is no Go type to import.

A write route's transaction runs in two phases. Its read phase holds no transaction id: it takes the owner's advisory lock as its first statement (`requireOpenOwner[Status]`, `requireOpenIssue`, `lockIssueRows`, through `store.LockOwner` and `LockOwners`), reads what the write decides on in the statements after that lock - never in the lock's own statement, whose READ COMMITTED snapshot is taken before the wait and would miss a close committed meanwhile - and does all its document work through `Docs.Join` and its write advice (`writeAdvice`, which counts the counted event the write is about to append). Its writes are queued on the ledger in the order it makes them (`api/write_queue.go`: `queueWrite`, `queueExec`, `queueEvent`, `queueStampedEvent`, `queueReferences`), and `ledger.Commit` sends them as one pipelined batch, the write phase (`store.WriteBatch`): Postgres runs every statement back to back and the route waits on the batch once. No statement's result is read in Go before a later statement is sent: an event's stamp names the event's id as the events id sequence's `currval` (`store.LatestEventID`), a row's time and id are read in the read phase, and what the response needs (the appended event) is filled by the statement's callback after the batch has run. The first failing statement or refusing callback (a guarded update's `ALREADY_ACTIONED`) stops the write phase and `Commit` returns that error unchanged, so the route answers what it answers for that error. A route with no document work (issue patch, claim) reads and advises before its first write and keeps its writes inline; message create sends its insert, references, event and stamp as one batch of its own (`store.RunWrite`); a write whose result steers the route (issue create's `update projects` and external-link insert) stays inline. `putThreadRead` takes the owner's lock in shared mode, so a thread read waits for a writer in its read phase rather than race that writer's trigger. The read phase still holds its pooled connection, idle in transaction.
