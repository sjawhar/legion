Every HTTP route body: issues, artifacts, asks, comments, messages, projects, search, and the assignee, rank, label and component-attachment writes, and the per-session list of what people wrote to an agent (`GET /api/v1/agents/{session_id}/answers`, `session_answers.go`), which every agent host reads on each model request. Search reads each ask hit's answer state from its row, and a resolved ask's last answer from its `ask.answered` events, before it answers. The per-session list's read model is the small package `sessionanswers` (`List`), which travels with its one route: a person's events whose `published_destinations` hold the session's own topic (`contracts.AgentSubject`), its sent message and comment deliveries, each item at its current words as a `model.SessionAnswer` with its relation to the session and its `dispatch://` and deep-link place; the outbox's tests read back through it, so the route reads what the publisher records. The largest package in the server (87 files) and the one every Dispatch feature touches. It resolves an agent's actor through the listener's OIDC and routing packages, hence the edge to `envoy-listener`. The edge to `contracts` is the wire contract rather than a Go import: `contracts/src/dispatch-api.ts` declares the response shapes these handlers produce and the web app consumes, and code generation covers only the event envelope, so there is no Go type to import. It also runs the related-item check every issue create, ask and new decision block gets once its write commits (a search by the text's rarest words and by meaning, waited on for at most 5 s and recorded in `related_checks`), the no-write route and the records route over it, and the term-statistics refresh its keyword picker reads.

The named person read (`GET /api/v1/people/{login}/nodes`) lists authored nodes through `graph_person_edges` and received nodes through indexed recorded-delivery sources, newest first with offset pagination.
It resolves proved session aliases first; received nodes default to the last 30 days of deliveries, with an optional RFC3339 `since` lower bound, while authored nodes are not time-limited.
The whole route is private to people: its `routeScopes` row needs the `person` scope, and that row is the only gate, so a credential the deployment configured is refused before the handler runs. Direct messages have no `dispatch://` reference.
`persongraph.Census` compares recorded delivery sets independently of the view SQL; `envoy-dispatch census --deliveries` runs it in a read-only snapshot without migrating.

The own-inbox read (`GET /api/v1/me/inbox`, `authOwnInbox`) joins indexed candidates to `delivered_to -> person` through that shared graph.
It preserves canonical thread/read identities and raw Clear identities, includes direct and broadcast replies, and accepts no person selector.
The default-off mention expansion is separate from legacy membership.
`RunInboxShadowSweep` compares every signed-in person's legacy and graph sets in one snapshot each minute; one locked control row serializes observations, and only counts are persisted.
`GET /api/v1/me/inbox/shadow` refreshes and reports counts, cause categories and user coverage without inbox content.
The dashboard's comparison and opt-in unified pages do not change the current Inbox, Replies or CLI.


It also runs the suggestion outcome sweep (`RunSuggestionOutcomeSweep`), which judges whether a write's `advice.suggestions` were acted on or overridden: a woken loop (`duty.RunWoken`, with no lease: each page holds the `suggestion_outcome_cursor` row `for update`, which serialises two processes) on `dispatch_events`, passes at least a minute apart, each reading only the events after its cursor (`suggestion_outcome_cursor`) and at or below the safe horizon of the server's one `events.Horizon`, which the server hands it (`Background.EventHorizon`) and which the live event feed reads through too, and the suggestions not yet swept (`write_suggestions.swept`), so its work follows what changed rather than how many suggestions are still pending, and its cursor never passes an event that could still commit. The keyed writes' maintenance sweep (`RunMaintenanceSweep`: the Idempotency-Keys past their window, then the deliveries a dead process left owed) is a timer of its own, once a minute across the processes under lease `suggestion-outcomes`, because no commit announces either.
