Stages 1 and 2 on `main` provide the `legion` command (including `worker-shim` and `claims`), configuration, boot and shutdown assembly, the state and health routes, and the claim-registration and operator routes. Stages 3 and 4 complete the agent API and CLI commands. Its API compatibility with the language-neutral contracts is not a Go source dependency.

`legion.yaml`'s top-level `repository_renames` (a list of `from`/`to` pairs) settles onto `config.Config.RepositoryRenames`, the `ghrepo.Renames` every consumer takes; `legion start --check-config` prints one line per pair after its `Config OK:` line, and `api.SettingsOf` carries them as `settings.repository_renames`, so `legion state --json` reads back what the daemon treats as one repository.

`legion.yaml`'s `projects.<KEY>.memory` (`mode`, `config_files`, `instructions`) settles onto `config.Project.Memory`, which boot reads once and every launch of a tree in the memory group takes through `runtime.SpawnSpec.Memory`; `api.SettingsOf` carries the block as `settings.projects.<KEY>.memory`, and `GET /legion/v1/state` carries on every issue its tree's `memoryGroup`, `memoryDrawMode` and `memoryDrawnAt`, the three absent together while nothing has drawn for that tree (`api.Issue`, daemon API contract 49; a caller in a pod whose claims record a contract below 49 is served the state without them, `stateFor`'s `withoutMemory`). So `legion state --json` reads back each issue's draw, under which mode and when, and `legion state` prints one `memory:` line counting the issues drawn under each group and mode, naming no issue, since the state names no tree and a handed-over tree carries its old tree's draw verbatim.

`legion controller start` hands the controller's session the secrets broker's route to a Dispatch credential where the controller's own file asks for it (`controller_dispatch_token.go`): `dispatch_token_broker: true`, the alternative to `dispatch_token_file` and never set beside it, has the session's own Envoy client trade this machine's identity for a DPoP-bound access token and renew it, so nobody copies a person's Dispatch token onto a machine. The start writes no token and hands the session no `DISPATCH_TOKEN_FILE` or `DISPATCH_TOKEN` — Dispatch refuses such a token presented as a bearer (RFC 9449 Section 7.2) — and drops an inherited one; it hands it `DISPATCH_TOKEN_BROKER=1` instead, under which the Envoy client reads no bearer from any source and turns Dispatch off with an error rather than falling back, because the controller keeps the operator's HOME and the envoy.json there is that person's own, `dispatch.token` and all, which would otherwise resolve first and write Dispatch as the operator. It trades once itself through `github.com/sjawhar/envoy/brokerclient`, before the daemon mints a capability, so a machine that proves no identity (`AGENT_SECRETS_MACHINE_IDENTITY`), a deployment that names no broker (`AGENT_SECRETS_URL`), or a broker that refuses this machine refuses the start, in the broker's own words where they are the broker's. With `dispatch_token_file` instead, the controller reads that bearer, as it always has; the loader reads no environment, so it takes a `dispatch_url` naming neither credential and the start is what refuses it. That import is this component's one Go source dependency on Envoy.
