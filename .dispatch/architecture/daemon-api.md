Stages 1 and 2 on `main` provide the `legion` command (including `worker-shim` and `claims`), configuration, boot and shutdown assembly, the state and health routes, and the claim-registration and operator routes. Stages 3 and 4 complete the agent API and CLI commands. Its API compatibility with the language-neutral contracts is not a Go source dependency.

`legion controller start` hands the controller's session the secrets broker's route to a Dispatch credential where the controller's own file asks for it (`controller_dispatch_token.go`): `dispatch_token_broker: true`, the alternative to `dispatch_token_file` and never set beside it, has the session's own Envoy client trade this machine's identity for a DPoP-bound access token and renew it, so nobody copies a person's Dispatch token onto a machine. The start writes no token and hands the session no `DISPATCH_TOKEN_FILE` or `DISPATCH_TOKEN` — Dispatch refuses such a token presented as a bearer (RFC 9449 Section 7.2), and the client consults the broker only where no bearer resolves — and drops an inherited one; it trades once itself through `github.com/sjawhar/envoy/brokerclient`, before the daemon mints a capability, so a machine that proves no identity (`AGENT_SECRETS_MACHINE_IDENTITY`), a deployment that names no broker (`AGENT_SECRETS_URL`), or a broker that refuses this machine refuses the start, in the broker's own words where they are the broker's. With `dispatch_token_file` instead, the controller reads that bearer, as it always has; the loader reads no environment, so it takes a `dispatch_url` naming neither credential and the start is what refuses it. That import is this component's one Go source dependency on Envoy.
