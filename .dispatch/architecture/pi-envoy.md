The Oh My Pi plugin every session loads (`@sjawhar/pi-envoy`): Envoy subscriptions and delivery, the `dispatch` command on every shell's `PATH`, the per-request context (the `dispatch-first` skill at the head of every model request, and at the tail of each main-loop request, never of a side turn, the handoff prompt or a remote compaction's request, what people wrote to the session in the last 72 hours, read from Dispatch's `GET /api/v1/agents/{session_id}/answers` through `@legion/envoy-client/session-answers`, a subagent reading its parent's), and the eight skills every session with Dispatch reads (the Dispatch and Envoy skills, `asd-ste100`, `outside-message`, `plain-words`, and `agent-secrets`, the secrets broker's client). It publishes the in-process interface in `pi-shared` that the Legion plugin claims its roles through. It takes the session's messages from the listener's relay of the session's own durable consumer, asked for at every registration and acknowledged once the session wrote the message (`packages/envoy/AGENTS.md`, "Session consumers"). It dials NATS with the client's shared connection options (a ping every 10 s, so a frozen path is left within 30 s), runs the core path's catch-up of missed messages (`POST /v1/replay`) only on a listener that answers `core`, and registers as `plugin` `@sjawhar/pi-envoy` with its package version as `plugin_version`.

The plugin's two serial task queues, each task's deadline and fence, and the registration and role state those tasks write live in one module, `packages/pi-envoy/src/registration-state.ts`. The extension entry declares none of it. A queued task acts through a handle that refuses every step — a state write, a listener request, a NATS subscribe or the acquisition of the NATS connection — past that task's deadline, or once its session is no longer the open session, and the first refusal latches. The module also mints this extension instance's client instance id and sends it on every registration, on every claim and release, and on the shutdown deregistration. That id is what lets the listener tell this instance's own predecessor from another process's live session: a soft claim naming a predecessor takes the role only when that predecessor has no live registry entry, when its live entry carries this instance's id, or when either side carries no instance id. A claim of a role already held under this session's own id is decided on the standing claim instead: the listener grants it to the process that claim names, grants it once nobody renewed that claim inside its live window, and otherwise refuses it 409 naming this very session. A refused session keeps running and stays registered, without the role; a refusal naming another live session stays latched until a session event lands on the session, while one naming this very session's id is never latched and nothing is written about it — it is another process's standing claim, which the listener grants the moment that process stops renewing it, so the next pass claims again. The heartbeat's re-assertion of a role this process already holds confirms it only when the lookup names this session and this process and the claim carries no hand-back mark, a holder naming no process being read as this one's, and the refusal it may get is weighed the same way: one naming this very session's id is another process's standing claim, so the role stays held here with nothing latched and the next heartbeat asks again, while one naming a different session ends the role here as any refusal does. A lookup that answers `handed_back` is read as a role this process does not hold, however exactly it names this session and this process, so a hold an older client's hand-back marked is claimed again on that same pass and the grant, which writes a fresh record, clears the mark. Both readings are the client contract's own rather than this plugin's: `roleHeldBy` and `mayActOnRoleRecord` in `@legion/envoy-client/transport`, which `packages/claude-envoy` calls too and which read an empty instance id as none. The `envoy-role-claim` transcript entry records the session claimed for and this process, so a release another process wrote on the same transcript ends no role here, and a claim another process wrote is pressed only while this process holds none. A hand-back the listener could not make — the release route fails rather than reporting a release its own holder's renewal beat under each of its conditional deletes — leaves the hold abandoned rather than forgotten: this process's next registration of that session takes it back and the pass behind it sends the release again, so a role given up here is not left standing while those registrations renew its claim.

`src/dispatch-session.ts` and the extension's listener client present the `credential` that `ActiveDispatchConfig` and `EnabledEnvoySettings` carry (`.dispatch/architecture/envoy-client.md`), traded under the session this process is acting as at that moment, so a pod with no Dispatch bearer gets its token from the secrets broker with nothing else of the session changed.
