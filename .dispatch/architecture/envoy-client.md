Shared TypeScript HTTP layer and `dispatch` command for every agent host: Dispatch config resolution, command execution, the text of each result (`dispatch search` prints each ask hit's answer state under it), inbound envelope rendering, the list of what people wrote to a session in the last 72 hours (`src/session-answers.ts`), which every host carries on each model request within an 800 ms deadline from one process-wide read and a memory and disk cache, and which `dispatch answers` prints in full, the forms in which a write, or `dispatch related`, prints the related-item check's result, the relay protocol of consumer delivery (`consumer-delivery`: `received` at decode, `done` once the host wrote the frame, the resume point), and the replay of what a session missed on the core path (`replay`). It also holds the NATS connection options every session plugin dials with (`nats-connection`: a ping every 10 s, a path dropped after two unanswered pings, so a frozen path is left within 30 s; reconnect forever, 2 s apart), and the session registration, whose `subscribe()` sends the plugin's npm package name and build as `plugin` and `plugin_version` on every registration.

`subscribe()` also sends the host's client instance id as `client_instance_id`, and `unregisterSession({sessionID, clientInstanceID?})` sends it as a query parameter, so the listener removes a registration only while it carries that id or none. The registration is also the holder's heartbeat for its role claims, and the listener renews every unmarked claim that registration's own process holds whatever topics the registration carries; one that states no instance renews the claims of its session that name no process and adopts none, so a claim standing at a deploy is kept by the client that cannot say which process it is. `setRole` and `unsubscribe` take a `clientInstanceID` of their own, sent as `client_instance_id` and omitted from the wire when the caller states none: the claim records that process as the role's holder, and a release frees only the role claims naming it — freeing a claim that names no process outright — so a second process that resumed this session id can neither take the role nor hand it back. The unsubscribe answer's `removed` is the topics that left the record rather than the ones the request named: a role lane topic whose claim the release did not free stays in the record, because one record serves every process running under one session id. A release that states no process and names a role's own lane topic is a hand-back, and the listener marks the claim it could not free. A release the holder's own renewal beat under each of the route's three conditional deletes fails rather than answering success, so `unsubscribe` rejects and the caller hands the role back again rather than reading it as given up. A `setRole` soft claim naming `previousSessionID` takes the role from that predecessor only when the predecessor has no live registry entry, when its live entry carries this client instance's own id, or when either side carries no instance id. A soft claim of a role already held under the claimant's own session id is decided on the standing claim: granted when that claim names this very process, granted when nobody renewed it inside the listener's live window, and otherwise answered `{claimed: false, holder}` naming that same session. Any other live holder keeps the role and is answered `{claimed: false, holder}`. A role lookup's `RoleInfo` carries the holder's `client_instance_id` where the claim names a process and leaves the field out where it names none, which is how a refused claimant tells its own session id held by another process from a different session, and `handed_back` where the claim carries the listener's hand-back mark. The two rules every client keeps over those ids are exported beside `RoleInfo`: `roleHeldBy(info, sessionID, clientInstanceID)`, whether a lookup's answer is this caller's own hold of the role, and `mayActOnRoleRecord(writer, clientInstanceID, holdsRole)`, whether a persisted role record another process may have written is this one's to act on. Both read an empty id as no process named, exactly as an absent one. A marked claim is no hold of anyone's, whoever `roleHeldBy` is asked for: the mark says the role was handed back and nothing renews the claim any more, so a holder an older client's hand-back marked claims the role again at its next heartbeat and has it back, rather than reading the lookup as confirmation until the reaper frees it.

A session's credential is a bearer or this machine's own identity. `src/bearer.ts` holds both as one `RequestCredential` — a scheme and the headers one request presents — and `src/broker-credential.ts` makes the second out of `@legion/broker-client`: one client and one DPoP key per session a process acts as, shared by that session's Dispatch client and listener client and traded under that session's own name, presented as `Authorization: DPoP <token>` with a proof naming each request and hashing the token it goes beside. The broker route is the last source either section consults, reached only when no bearer is configured at all (`DISPATCH_TOKEN`, `DISPATCH_TOKEN_FILE`, `ENVOY_TOKEN`, `ENVOY_TOKEN_FILE` and an envoy.json's own token are resolved first and unchanged), so every session that has a bearer today behaves exactly as it did. Dispatch's section has one exception, `DISPATCH_TOKEN_BROKER=1`: a deployment sets it on a session whose Dispatch credential must be this machine's own identity and nothing else (`legion controller start` under `dispatch_token_broker`, where the chosen envoy.json is the operator's own and holds that person's `dispatch.token`), and under it no bearer is read from any source, while a session that can trade none turns Dispatch off with an error rather than falling back to a person's token. Any other value of that variable is refused by name. A resolution carries that credential as its one `credential` field (`ActiveDispatchConfig`, `EnabledEnvoySettings`), and `DispatchClient` takes only a `RequestCredential`, so no caller can send a bare `Bearer ` to Dispatch. Each write attempt presents the credential afresh, since a resource server that keeps a proof replay store refuses one it has already seen.
