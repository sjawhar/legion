Shared TypeScript HTTP layer and `dispatch` command for every agent host: Dispatch config resolution, command execution, the text of each result (`dispatch search` prints each ask hit's answer state under it), inbound envelope rendering, the list of what people wrote to a session in the last 72 hours (`src/session-answers.ts`), which every host carries on each model request within an 800 ms deadline from one process-wide read and a memory and disk cache, and which `dispatch answers` prints in full, the forms in which a write, or `dispatch related`, prints the related-item check's result, the relay protocol of consumer delivery (`consumer-delivery`: `received` at decode, `done` once the host wrote the frame, the resume point), and the replay of what a session missed on the core path (`replay`). It also holds the NATS connection options every session plugin dials with (`nats-connection`: a ping every 10 s, a path dropped after two unanswered pings, so a frozen path is left within 30 s; reconnect forever, 2 s apart), and the session registration, whose `subscribe()` sends the plugin's npm package name and build as `plugin` and `plugin_version` on every registration.

`subscribe()` also sends the host's client instance id as `client_instance_id`, and `unregisterSession({sessionID, clientInstanceID?})` sends it as a query parameter, so the listener removes a registration only while it carries that id or none. A `setRole` soft claim naming `previousSessionID` takes the role from that predecessor only when the predecessor has no live registry entry, when its live entry carries this client instance's own id, or when either side carries no instance id. Any other live holder keeps the role and is answered `{claimed: false, holder}`.

A session's credential is a bearer or this machine's own identity. `src/bearer.ts` holds both as one `RequestCredential` — a scheme and the headers one request presents — and `src/broker-credential.ts` makes the second out of `@legion/broker-client`: one client and one DPoP key per process, shared by the Dispatch client and the listener client, presented as `Authorization: DPoP <token>` with a proof naming each request and hashing the token it goes beside. The broker route is the last source either section consults, reached only when no bearer is configured at all (`DISPATCH_TOKEN`, `DISPATCH_TOKEN_FILE`, `ENVOY_TOKEN`, `ENVOY_TOKEN_FILE` and an envoy.json's own token are resolved first and unchanged), so every session that has a bearer today behaves exactly as it did. `dispatchCredential(config)` and `envoyCredential(settings)` are what a caller presents; a resolution's `token` is "" under the broker route, and `DispatchClient` refuses an empty credential rather than sending `Bearer ` to Dispatch. Each write attempt presents the credential afresh, since a resource server that keeps a proof replay store refuses one it has already seen.
