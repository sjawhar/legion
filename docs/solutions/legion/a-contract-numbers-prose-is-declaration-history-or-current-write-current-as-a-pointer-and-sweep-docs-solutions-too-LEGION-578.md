# A contract number's prose is declaration, history or current: write current as a pointer to the declaring file, sweep docs/solutions too, and prove a renumber held with a pair

Extends docs/solutions/legion/daemon-api-contract-collision-renumber-when-the-release-declaring-the-number-lacks-your-shapes.md.

- Classify every sentence that names a daemon API contract number. **Declaration** (three sites the
  gate compares, each a literal): `DaemonAPIVersion` in `packages/daemon/internal/api/version.go`,
  `legion.daemonApiVersion` in `packages/pi-legion/package.json`, the golden
  `packages/contracts/fixtures/daemon-api/version.json` (regenerated by `go test ./internal/api -update`).
  **History** (a literal, true forever): `version.go`'s numbered list, a `CHANGELOG.md` entry about the
  release that shipped that number, an `AGENTS.md` clause "after contract N's …". **Current** (what
  the gate wants, what an operator installs, what a comment calls "this shape"): never a literal.
  Write it as a pointer — "the contract `DaemonAPIVersion` in `internal/api/version.go` declares",
  "the `legion.daemonApiVersion` entry above" — which stays true through every renumber and is
  checkable (`test -f` the path, grep the symbol) where a literal is not.
- A sentence that enumerates a transition ("15 for the shared issue pod, 16 once the capability report
  lands") is a literal twice and a trap for the reader who takes the first number.
- The sweep's grep in the collision note (`contract N|daemonApiVersion.*N`) is too narrow. Use
  `grep -rnE 'contract N|currently N|at N\b|to N\b|declares N|declaring N|daemonApiVersion.{0,12}\bN\b|N for the'`
  over `packages`, `docs`, `skills`, `scripts`, `AGENTS.md` and the pull request body, and classify
  each hit before deciding it stays.
- `docs/solutions/**` is in the sweep. The unchanged-diff fingerprint's fileset
  (`'~(.legion | docs/solutions)'`, `skill://legion-worker/references/conflicts-and-rewrites.md`)
  excludes it, so a retro note from an earlier round that states the old number has no diff, no CI
  job and no fingerprint change to show it — only a reviewer's grep. A retro note writes a number as
  history ("at the branch's then-unreleased number") or as a pointer, never as current.
- The renumber is not "one line on each side": census the sites a textual merge cannot renumber — the
  golden fixture, a rig or stand-in's hand-written state body, the `(contract N)` comments in the
  schema, the Go state type and the test that pins the golden — and record that renumber set in the
  handoff. On a long-lived pull request the next renumber is live: when sibling branches claim the
  same number before any release carries it, no gate sees it (npm has no release at that number;
  each branch's three declarations agree), so the architect's arrangement and the handoff are the
  record, and the branch that merges first keeps the number.
- Prove a renumber held with a pair that needs no rig, beside the merged binary refusing the installed
  plugin by name: `jj file show -r main@origin packages/contracts/src/legion-api.ts` parsing your
  regenerated `fixtures/daemon-api/state.json` must fail (`unrecognized_keys` on your new member —
  `main`'s reader cannot take your state), and the released tarball's bundled schema
  (`dist/legion.js` from registry.npmjs.org) must lack the member (the release that took your old
  number cannot read it either).

## Evidence

sjawhar/legion#1846 renumbered 15 → 16 in its forward merge of `main` (38e27ad3) after
`@sjawhar/pi-legion@8.3.0` shipped 15 without `capabilities`. The implementer swept by hand
(`CHANGELOG.md`, `packages/pi-legion/AGENTS.md`, `docs/kubernetes.md`) and the review at 256a856b
found five current-state sentences still at 15: the plugin's npm README ("currently 15"), the
LEGION-462 upgrade runbook — where the sweep had *written* the two-number sentence — the forward
clause of `main`'s own LEGION-462 CHANGELOG entry ("beside a daemon at 15"), and two retro notes from
the first retro (b855a3d4), one saying "contract 15, which no release had shipped" after 8.3.0 had.
The two notes sat outside the fingerprint's fileset; the other three were inside it. f98f84e7
replaced each with a pointer, keeping `main`'s LEGION-462 entry opening and its 15 verbatim as
history; the tester's check was `test -f` on each pointed-at path and the three declaration sites
agreeing at 16. The cost of the miss was a whole review round for no behaviour change — implementer
f98f84e7, a tester round, review 5463772787 → the re-approval 5463972815 — and that round was the
root's third rejection, the daemon's `review_round_cap`.

The renumber set at 38e27ad3 was nine files, not two: `version.go`, `package.json`, `version.json`
(regenerated), `legion-api.ts` (the `(contract 16)` comments at its `capabilities` members),
`state.go`'s comment, `daemon-standin.ts`'s state body, the CHANGELOG, `AGENTS.md`, `docs/kubernetes.md`;
at 5ffc69c5 the comments naming 16 as this branch's shape — `legion-api.ts:228,241`,
`legion-api.test.ts:291`, `state.go:48`, `daemon-standin.ts:53`, `docs/kubernetes.md:916` — plus the
three declarations and `version.go`'s `16:` entry are what a move to 17 touches. LEGION-631 (#1843)
and LEGION-632 (#1842) also declared 16 on their branches at the time; the architect told their
implementers, and the handoff's `openQuestions` carries the arrangement. The pair: the tester showed
`main@origin`'s `legion-api.ts` parsing the merged state fixture → `unrecognized_keys@<root>:
Unrecognized key: "capabilities"`, and 8.3.0's `dist/legion.js` `LegionStateResponse` as a
`strictObject` ending at `agentSecretsLogin`; the implementer showed the merged `legion probe-image`
refusing this pod's plugin "speaks daemon API contract 14; this daemon requires 16", exit 1.
